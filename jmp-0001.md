## Abstract

This specification defines the base JoinMarket peer-to-peer protocol used for
coordinating CoinJoin transactions. It covers the transport layer, message
framing, handshake, nick identity, peer discovery, message routing, CoinJoin
transaction flow, and the feature negotiation framework that enables backward-
compatible extensions.

## Motivation

JoinMarket enhances Bitcoin transaction privacy through CoinJoin -- a technique
where multiple users combine their funds into a single transaction, making it
difficult to trace ownership. The protocol coordinates untrusted parties
(makers and takers) through directory servers, handles encrypted communication,
and ensures atomic transaction construction.

This specification documents the protocol as implemented across joinmarket-
clientserver, [joinmarket-ng](https://github.com/joinmarket-ng/joinmarket-ng),
and [joinmarket-rs](https://github.com/joinmarket-rs/joinmarket-rs), providing
a single normative reference for interoperability.

## Specification

### Roles

**Maker**: A liquidity provider that publishes offers to perform CoinJoin
transactions. Makers are compensated with fees and run continuously. A maker
maintains a persistent connection to directory servers and listens for incoming
connections on a Tor hidden service.

**Taker**: Initiates a CoinJoin transaction by selecting makers from the
orderbook, negotiating parameters, constructing the transaction, and
broadcasting it. Takers connect to directory servers and optionally directly to
makers.

**Directory Server (DN)**: Routes messages between peers, maintains a list of
connected makers, and responds to peer discovery requests. Directory servers do
not participate in CoinJoin transactions.

### Transport

Communication between peers uses TCP connections, typically over Tor onion
services. The default virtual port is `5222`.

Each TCP connection carries a bidirectional stream of JSON-encoded messages. The
wire format is one JSON object per line, terminated by `\r\n`:

```
{"type": <integer>, "line": "<payload>"}\r\n
```

Fields:

- `type` (integer, REQUIRED): Message type code from the table below.
- `line` (string, REQUIRED): Message payload. Contents depend on the message type.

Implementations SHOULD enforce a maximum line length. The reference
implementation uses 40,000 bytes. Messages exceeding this limit SHOULD cause
the connection to be dropped.

### Message Types

| Code | Name | Direction | Description |
|------|------|-----------|-------------|
| 685 | PRIVMSG | Any | Private message between two peers |
| 687 | PUBMSG | Any | Public broadcast to all peers |
| 789 | PEERLIST | DN -> Peer | List of connected peers |
| 791 | GETPEERLIST | Peer -> DN | Request peer list |
| 793 | HANDSHAKE | Any | Peer handshake request |
| 795 | DN_HANDSHAKE | DN -> Peer | Directory handshake response |
| 797 | PING | DN -> Peer | Heartbeat probe (see JMP-0004) |
| 799 | PONG | Peer -> DN | Heartbeat response (see JMP-0004) |
| 801 | DISCONNECT | Any | Graceful disconnect notification |

Additionally, the following codes are used locally within implementations and
MUST NOT be sent over the wire:

| Code | Name | Description |
|------|------|-------------|
| 785 | CONNECT | Internal: outgoing connection established |
| 797 | CONNECT_IN | Internal: incoming connection received |

Note: CONNECT_IN shares code 797 with PING. This collision exists in the
reference implementation and is safe because CONNECT_IN is never serialized.

### Handshake

Every connection begins with a handshake that establishes identity, verifies
network compatibility, and advertises capabilities.

#### Client -> Directory

1. The client sends a HANDSHAKE (793) message. The `line` field contains a JSON
   object:

```json
{
  "app-name": "joinmarket",
  "directory": false,
  "location-string": "<onion_host>:<port>",
  "proto-ver": 5,
  "features": {},
  "nick": "<nick>",
  "network": "<network>"
}
```

2. The directory responds with a DN_HANDSHAKE (795):

```json
{
  "app-name": "joinmarket",
  "directory": true,
  "proto-ver-min": 5,
  "proto-ver-max": 5,
  "features": {},
  "accepted": true,
  "nick": "<nick>",
  "network": "<network>",
  "motd": "<message of the day>"
}
```

#### Taker -> Maker (Direct Connection)

When a taker connects directly to a maker's onion service, both sides send
HANDSHAKE (793) with `"directory": false`. This is a **symmetric** exchange --
neither side sends DN_HANDSHAKE (795).

Implementations MUST NOT send DN_HANDSHAKE unless they are a directory server.
The reference implementation rejects DN_HANDSHAKE from non-directory peers.

#### Handshake Fields

**Client handshake (HANDSHAKE, 793):**

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `app-name` | string | Yes | MUST be `"joinmarket"` |
| `directory` | boolean | Yes | `false` for clients, `true` for directories |
| `location-string` | string | Yes | Onion address with port, or `"NOT-SERVING-ONION"` |
| `proto-ver` | integer | Yes | Protocol version. MUST be `5` |
| `features` | object | Yes | Feature flags (see Feature Negotiation) |
| `nick` | string | Yes | Peer's nick (see Nick Format) |
| `network` | string | Yes | Bitcoin network: `"mainnet"`, `"testnet"`, `"signet"`, `"regtest"` |

**Directory handshake response (DN_HANDSHAKE, 795):**

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `app-name` | string | Yes | MUST be `"joinmarket"` |
| `directory` | boolean | Yes | MUST be `true` |
| `proto-ver-min` | integer | Yes | Minimum supported protocol version |
| `proto-ver-max` | integer | Yes | Maximum supported protocol version |
| `features` | object | Yes | Feature flags (see Feature Negotiation) |
| `accepted` | boolean | Yes | Whether the connection is accepted |
| `nick` | string | Yes | Directory's nick |
| `network` | string | Yes | Bitcoin network |
| `motd` | string | No | Message of the day |

#### Validation Rules

- The `network` field MUST match between peers. A directory MUST reject clients
  on a different network.
- `proto-ver` MUST be `5`. The reference implementation rejects other versions.
- The `nick` MUST conform to the nick format (see below).
- If `accepted` is `false`, the client SHOULD disconnect.

### Nick Format

JoinMarket nicks encode the protocol version and a hash of the peer's ephemeral
public key:

```
J + <version> + <base58(SHA256(hex(pubkey))[:10])> + <padding>
```

Format details:

- **Prefix**: Single character `J`
- **Version**: Single digit, currently `5` (from `JM_VERSION`)
- **Hash**: `SHA256` of the hex-encoded public key, truncated to 10 bytes,
  then base58-encoded (no checksum)
- **Padding**: Right-padded with `O` (capital letter O, not zero) to reach
  exactly 14 characters for the hash portion
- **Total length**: 16 characters (1 + 1 + 14)

Example: `J5abc123OdefgOO`

The nick serves as a short stable identifier for a peer during a session. It
enables:

- **Anti-spoofing**: Messages include `<hex_pubkey> <signature>` that can be
  verified against the nick's embedded hash
- **Nick recovery**: A peer can re-derive the same nick from its keypair after
  reconnecting to a different directory

#### Nick Signature Verification

Every private message includes a signature for anti-impersonation. The wire
format of a signed private message body is:

```
!<command> <message_body> <hex_pubkey> <base64_signature>
```

The signed plaintext is `<message_body> + <hostid>` where `hostid` is the
directory's onion address (for relayed messages) or `"onion-network"` (for
direct connections). This prevents replay across channels.

Verification steps:

1. Extract the last two space-separated tokens as `hex_pubkey` and `signature`
2. Verify that `SHA256(hex(pubkey))[:10]` matches the nick's hash portion
3. Verify the ECDSA signature over `message_body + hostid` using `pubkey`

### Peer Discovery

#### Peer List Request

A client sends GETPEERLIST (791) with an empty `line` field to request the
current list of connected makers. The directory responds with PEERLIST (789).

#### Peer List Format

The `line` field of a PEERLIST (789) message contains a comma-separated list of
peer entries:

```
nick1;location1,nick2;location2,...
```

Each entry uses `;` (semicolon) as the field separator:

- **Join entry**: `nick;host:port` -- a peer is available
- **Disconnect entry**: `nick;host:port;D` -- a peer has disconnected

The directory SHOULD include itself in the peer list. Takers MUST NOT appear in
peer list responses -- only makers and directories are listed.

Disconnect notifications are broadcast to all connected peers when a maker
disconnects. The notification includes the disconnected peer's entry with `;D`
appended, plus the directory's own entry.

#### Peer List on PRIVMSG Relay

When a directory relays a PRIVMSG, it also sends a PEERLIST to the recipient
containing the sender's location. This allows the recipient to establish a
direct connection for future messages.

### Message Routing

#### Public Messages (PUBMSG, 687)

The `line` field format:

```
<from_nick>!PUBLIC<message>
```

The message content starts with `!` for JoinMarket commands. Example:

```
J5alice00000000!PUBLIC!orderbook
```

When a directory receives a PUBMSG, it broadcasts it to all connected peers.
The `from_nick` in the line MUST match the sender's authenticated nick.

#### Private Messages (PRIVMSG, 685)

The `line` field format:

```
<from_nick>!<to_nick>!<command> <arguments>
```

When a directory receives a PRIVMSG, it forwards it to the peer identified by
`to_nick`. If the target peer is not connected, the message is silently
dropped.

For direct connections (taker <-> maker), the same format is used but routing
is implicit -- the message goes to the connected peer.

### CoinJoin Protocol

CoinJoin transactions proceed through five phases. All commands use the `!`
prefix.

#### Phase 1: Orderbook Discovery

Makers publish offers as public messages. A taker requests offers by
broadcasting:

```
!orderbook
```

Makers respond with offer announcements via PRIVMSG (when responding to a
specific taker) or PUBMSG (periodic re-announcements):

```
!<ordertype> <oid> <minsize> <maxsize> <txfee> <cjfee>
```

Order types:

| Command | Segwit | Fee Type |
|---------|--------|----------|
| `!sw0reloffer` | Native (v0) | Relative (fraction) |
| `!sw0absoffer` | Native (v0) | Absolute (satoshis) |
| `!swreloffer` | Wrapped | Relative |
| `!swabsoffer` | Wrapped | Absolute |
| `!reloffer` | Legacy (non-segwit) | Relative |
| `!absoffer` | Legacy (non-segwit) | Absolute |

Fields:

| Field | Type | Description |
|-------|------|-------------|
| `oid` | integer | Unique order ID for this maker |
| `minsize` | integer | Minimum CoinJoin amount in satoshis |
| `maxsize` | integer | Maximum CoinJoin amount in satoshis |
| `txfee` | integer | Maker's contribution to mining fee (satoshis) |
| `cjfee` | integer or float | Fee: absolute (satoshis) or relative (fraction, e.g. 0.001) |

A maker MAY publish multiple offers simultaneously. Multiple offer commands can
be concatenated in a single message, separated by `!`:

```
!sw0reloffer 0 50000 10000000 0 0.00025!sw0absoffer 1 50000 10000000 0 250
```

Makers cancel offers by broadcasting:

```
!cancel <oid>
```

#### Fidelity Bonds

Makers MAY attach a fidelity bond proof to their offer announcements using the
`!tbond` command, concatenated after the offer:

```
!sw0reloffer 0 50000 10000000 0 0.00025!tbond <base64_proof>
```

The proof is a 252-byte binary structure, base64-encoded:

| Offset | Size | Field | Description |
|--------|------|-------|-------------|
| 0 | 72 | nick_sig | ECDSA DER signature, right-padded with `0xFF` |
| 72 | 72 | cert_sig | Certificate signature, right-padded with `0xFF` |
| 144 | 33 | cert_pubkey | Compressed public key for the certificate |
| 177 | 2 | cert_expiry | Unsigned 16-bit integer (little-endian) |
| 179 | 33 | utxo_pubkey | Compressed public key controlling the bonded UTXO |
| 212 | 32 | txid | Transaction hash of the bonded UTXO |
| 244 | 4 | vout | Output index, unsigned 32-bit (little-endian) |
| 248 | 4 | timelock | Lock time, unsigned 32-bit (little-endian) |

The `nick_sig` signs the message `<taker_nick>|<maker_nick>` using the
certificate key. The `cert_sig` signs
`fidelity-bond-cert|<cert_pubkey>|<cert_expiry>` using the UTXO key.

#### Phase 2: Fill Request

The taker selects makers and sends a fill request to each:

```
!fill <oid> <amount> <taker_nacl_pubkey_hex> <commitment>
```

Fields:

| Field | Type | Description |
|-------|------|-------------|
| `oid` | integer | Order ID from the maker's offer |
| `amount` | integer | CoinJoin amount in satoshis |
| `taker_nacl_pubkey_hex` | string | Taker's NaCl public key for encrypted communication |
| `commitment` | string | PoDLE commitment (hex) |

The maker responds with its NaCl public key:

```
!pubkey <maker_nacl_pubkey_hex>
```

After this exchange, both sides derive a shared NaCl encryption box. All
subsequent private messages in this session use NaCl authenticated encryption
with the message body base64-encoded.

#### Phase 3: Authentication

The taker sends its PoDLE proof and inputs (encrypted):

```
!auth <commitment_revelation>
```

The `commitment_revelation` is a JSON string containing the PoDLE proof
components needed for the maker to verify the taker controls real UTXOs without
revealing which specific UTXOs will be used.

The maker verifies the proof and responds with its CoinJoin inputs (encrypted):

```
!ioauth <utxo1,utxo2,...> <auth_pubkey> <cj_address> <change_address> <btc_signature>
```

Fields:

| Field | Type | Description |
|-------|------|-------------|
| `utxo_list` | string | Comma-separated UTXOs in `txid:vout` format |
| `auth_pubkey` | string | Maker's Bitcoin public key for signature verification |
| `cj_address` | string | Maker's CoinJoin output address |
| `change_address` | string | Maker's change output address |
| `btc_signature` | string | Bitcoin signature proving key ownership |

##### PoDLE Commitment Broadcast

After processing `!auth`, the maker broadcasts the used commitment to prevent
reuse:

```
!hp2 <commitment>
```

This is sent as a PUBMSG. For privacy, the broadcast SHOULD be performed using
an ephemeral identity (fresh nick, separate Tor circuit) so that observers
cannot correlate the broadcast with the participating maker.

#### Phase 4: Transaction Signing

The taker constructs the unsigned CoinJoin transaction and sends it to each
maker (encrypted):

```
!tx <base64_transaction>
```

Each maker verifies the transaction and returns signatures for its inputs
(encrypted, one message per input):

```
!sig <signature>
```

The taker collects all signatures and assembles the fully signed transaction.

#### Phase 5: Broadcast

The taker broadcasts the signed transaction. Broadcast policy is
implementation-defined. Options include:

- Broadcasting via the taker's own Bitcoin node
- Requesting a maker to broadcast via `!push <base64_transaction>`
- Broadcasting through multiple makers for redundancy

#### Error Handling

Either side may send an error at any point:

```
!error <message>
```

### Encryption

Commands are classified as encrypted or plaintext:

| Category | Commands |
|----------|----------|
| Encrypted | `auth`, `ioauth`, `tx`, `sig` |
| Plaintext | `fill`, `error`, `pubkey`, `orderbook`, `push`, offers, `hp2`, `cancel` |

Encrypted commands use NaCl authenticated encryption (Curve25519-XSalsa20-
Poly1305). The encrypted ciphertext is base64-encoded before transmission.
The NaCl keypair exchange happens during Phase 2 (`!fill` / `!pubkey`).

### Feature Negotiation

The `features` field in the handshake is a JSON object mapping feature names
(strings) to boolean values. Only features set to `true` are considered
advertised.

```json
{"features": {"neutrino_compat": true, "ping": true}}
```

This mechanism allows implementations to advertise capabilities without
changing the protocol version. The reference implementation sends `features: {}`
and ignores the field on receipt, ensuring backward compatibility.

Features are negotiated per-session:

- **At handshake**: Both peers exchange their supported features
- **During CoinJoin**: The taker MAY advertise features in `!fill` and the
  maker MAY respond with features in `!pubkey` (via optional JSON suffix)
- **Effective features**: The intersection of both peers' advertised features

Individual features are specified in separate JMP documents.

### Disconnect

A peer sends DISCONNECT (801) with an empty or descriptive `line` before
closing the connection. This allows the directory to immediately update its
peer list and broadcast a disconnect notification, rather than waiting for TCP
timeout detection.

## Backward Compatibility

This specification documents the protocol as currently implemented. All
implementations MUST support protocol version 5. The feature negotiation
framework allows extensions without breaking existing peers.

Key compatibility constraints:

- The reference implementation only accepts `proto-ver=5`
- Unknown features in the `features` dict MUST be silently ignored
- Extended peerlist entries (with `F:` suffix) are ignored by implementations
  that do not understand them
- Encrypted and plaintext command categories are fixed and MUST NOT change

## Security Considerations

- **Tor dependency**: The protocol assumes Tor for transport privacy. Running
  without Tor exposes IP addresses to directory servers and direct peers.
- **Nick spoofing**: Mitigated by per-message signatures, but implementations
  MUST verify signatures to benefit from this protection.
- **Replay attacks**: The `hostid` in signed messages prevents cross-channel
  replay but does not prevent replay within the same channel. Implementations
  SHOULD use nonce-based deduplication.
- **Directory trust**: Directories see connection metadata (which nicks are
  connected, message timing). Connecting to multiple directories limits the
  impact of a malicious directory.
