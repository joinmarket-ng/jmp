## Abstract

This specification defines `flex_fee`, a maker capability indicating that the
maker accepts a CoinJoin fee greater than or equal to the fee in its selected
offer. This lets a taker adjust realized maker fees without risking rejection
by makers that require exact payment.

## Motivation

Takers may want to give several makers the same realized fee to reduce the
on-chain fingerprint created by distinct advertised fees. Makers differ in how
they validate payment, so accepting overpayment cannot be assumed. An explicit
capability lets takers use flexible fees while preserving exact-payment
behavior for all other makers.

## Specification

### Advertisement

A maker supporting this feature MUST set `flex_fee` to `true` in the `features`
object of its HANDSHAKE messages:

```json
{"features": {"flex_fee": true}}
```

The feature is a unilateral maker promise and does not require the taker to
advertise it. A directory implementing JMP-0003 propagates it in the maker's
peerlist entry:

```text
nick;location;F:flex_fee
```

The promise applies to every current offer announced under that maker nick. A
taker has confirmed support after parsing `flex_fee: true` from the maker's
direct handshake or from its JMP-0003 peerlist entry. An absent, false,
malformed, or unavailable value means no support. A direct maker handshake
supersedes directory-propagated or cached information.

### Fee Calculation

For one maker, let:

- `C` be the CoinJoin amount from `!fill`.
- `I` be the sum of the maker's input values.
- `T` be the `txfee` contribution in the selected offer.
- `F` be the selected offer's fee at amount `C`.
- `R` be the realized fee assigned by the taker.

For an absolute offer, `F = int(cjfee)`. For a relative offer, `F` is
`Decimal(cjfee) * C`, rounded to the nearest satoshi with ties to even.

The maker's CoinJoin output MUST equal `C`. Its change output is:

```text
change = I - C - T + R
```

### Taker Behavior

For a maker without confirmed `flex_fee` support, the taker MUST use `R = F`.
For a maker with confirmed support, the taker MAY use any `R >= F`.

The taker MUST use each maker's `R` when funding the transaction, constructing
maker change outputs, enforcing its fee limits, and calculating ordinary and
sweep CoinJoin amounts. This permits mixed rounds in which some makers receive
their exact offered fee and others receive more.

### Maker Behavior

A maker advertising `flex_fee` MUST NOT reject an otherwise valid transaction
solely because its change output is greater than `I - C - T + F`. It MUST still
reject underpayment and perform all other transaction and policy checks.

## Backward Compatibility

Peers that do not understand `flex_fee` ignore it. Legacy takers continue to
pay exact offered fees. Takers using this extension also pay exact offered fees
to makers that do not advertise the capability, so those makers require no
changes.

## Security Considerations

Overpayment spends additional taker funds. Takers MUST apply their configured
fee limits to realized fees, including the excess above advertised fees.
Directory-propagated feature information can be stale or false; confirming the
capability in a direct maker handshake avoids relying on the directory.

## Reference Implementation

No complete implementation exists at publication. The existing maker
lower-bound checks in joinmarket-clientserver (`src/jmclient/maker.py`) and
joinmarket-ng (`maker/src/maker/tx_verification.py`) are compatible with the
maker behavior, but neither implementation advertises `flex_fee` and neither
taker assigns flexible realized fees.

joinmarket-clientserver first released its lower-bound checks in version
0.9.12. Version 0.9.11 and earlier require exact payment. Its wire protocol
does not reveal the software version, so a taker cannot distinguish these
unsignaled makers and MUST use `R = F` unless `flex_fee` is explicitly
advertised.
