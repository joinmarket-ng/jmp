## Abstract

This specification defines the `sp_ecdh` feature, which lets a taker pay a [BIP352](https://github.com/bitcoin/bips/blob/master/bip-0352.mediawiki) silent payment address as the payment output of a `tr0` CoinJoin (JMP-0005). A BIP352 receiver derives the output key from the sum of all of a transaction's eligible input public keys, so a taker acting alone cannot compute the output key in a multi-party CoinJoin. This document specifies the missing piece: a one-round collaborative ECDH in which each maker contributes a partial share for its own inputs, blinded with [Ruben Somsen's Blind Diffie-Hellman scheme](https://gist.github.com/RubenSomsen/be7a4760dd4596d06963d67baf140406) so makers learn nothing about the recipient, and proven correct with a discrete-log equality (DLEQ) proof, the same primitive JoinMarket already uses for PoDLE. Two new encrypted commands, `!spreq` and `!spshare`, are exchanged between Phase 3 and Phase 4 of the JMP-0001 flow. No change to BIP352 is required: a standard, unmodified BIP352 receiver detects and spends the payment.

## Motivation

Silent payment addresses are static: a recipient can publish one address (for donations, recurring payments, or invoicing without a server) and receive unlinkable payments with no interaction and no on-chain overhead. Paying such an address directly from a CoinJoin is attractive because the payment output is one of the equal-amount outputs and the receiver cannot tell which inputs belong to the sender.

JMP-0005 deliberately excludes BIP352 from the tr0 pit because the derivation is impossible unilaterally: the receiver scans with the sum of all eligible input public keys, and no single CoinJoin participant knows the private keys behind the others' inputs. BIP352 itself anticipates the collaborative solution. Its rationale notes that CoinJoin participants "need to coordinate to create the silent payment output and would need to use Blind Diffie-Hellman to prevent the other participants from learning who Alice is paying", and its taproot section sketches the share form `ECDH = a_1*B_scan + a_2*B_scan + ... + a_t*B_scan` together with DLEQ proofs "to ensure they are not acting maliciously". What BIP352 does not provide is an interactive wire protocol; that is an application-layer concern, and this document specifies it for JoinMarket.

JoinMarket is unusually well positioned to implement this: the DLEQ proof required to make maker shares trustless is exactly the Chaum-Pedersen construction already shipped for PoDLE, and the BIP352 even-Y scalar normalization for taproot inputs is the same normalization JMP-0005 already defines for the Taproot PoDLE.

## Specification

### Notation

`G` is the secp256k1 generator and `n` the curve order. `ser_P(P)` is the 33-byte SEC1 compressed encoding of point `P`. `x_only(P)` is the 32-byte X coordinate. `lift_x(x)` is the curve point with X coordinate `x` and even Y (BIP340). `hash_BIP0352/Inputs` and `hash_BIP0352/SharedSecret` are the BIP340-style tagged hashes defined in BIP352. A silent payment address decodes to a scan key `B_scan` and a (possibly labeled) spend key `B_m` per BIP352.

### Scope

`sp_ecdh` operates only inside a tr0 session (JMP-0005): every transaction input is a BIP86 key-path P2TR UTXO, which makes every input BIP352-eligible and its public key recoverable from the scriptPubKey. Only taker-created outputs may be silent payment outputs (the payment output, or in principle several outputs). Maker CoinJoin and change outputs are never silent payment outputs (see Rationale). The feature MUST NOT be used in sw0 sessions (see Rationale).

### Feature Negotiation

Makers that implement this specification advertise the feature in their handshake (JMP-0001 Feature Negotiation):

```json
{"features": {"sp_ecdh": true}}
```

The feature is discoverable before connecting via the JMP-0003 extended peerlist (`F:sp_ecdh`). A taker that intends to create silent payment outputs MUST select only makers that advertised `sp_ecdh`, and MUST NOT send `!spreq` to a maker that did not advertise it. A maker receiving `!spreq` without having advertised the feature SHOULD respond with `!error`.

### Eligible Scalars and Keys

For a P2TR input with output key program `q` (the 32-byte program of `OP_1 <q>`), its BIP352-eligible public key is `lift_x(q)` and its eligible scalar is the output-key scalar `d` (JMP-0005 Taproot PoDLE, including the internal-key normalization), negated to `n - d` if `d*G` has odd Y. This is the same parity normalization JMP-0005 applies for PoDLE, and it matches the BIP352 sender rule that taproot private keys are used in their even-Y form because the receiver lifts X-only keys assuming even Y.

For each participant, define:

- its **share scalar** `alpha` as the sum (mod n) of the eligible scalars of all inputs it contributes, and
- its **share key** `A_sum = alpha*G`, which equals the sum of `lift_x(q_j)` over those inputs and is therefore computable by anyone who knows the input set.

### Message Flow

The exchange happens after the taker has received and validated every `!ioauth` (Phase 3) and before it sends `!tx` (Phase 4):

```
Taker                                 Maker (each, in parallel)
  |  -------- !spreq (blinded scan points) -------->  |
  |  <------- !spshare (shares + DLEQ proofs) ------  |
  |  ---------------- !tx ------------------------->  |
```

Both commands are encrypted commands in the sense of JMP-0001 (NaCl box, base64-encoded), extending the encrypted set `auth, ioauth, tx, sig` with `spreq, spshare`.

#### Blinding

For each distinct scan key `B_scan_g` among the intended silent payment recipients, the taker:

1. Draws a fresh blinding scalar `r_g` uniformly from `[1, n-1]`. A fresh `r_g` MUST be used for every group and every session; `r_g` MUST never be reused.
2. Computes the blinded point `X_g = r_g*B_scan_g`.

The blinded points are uniformly distributed curve points and reveal nothing about `B_scan_g`.

#### !spreq (taker to maker)

```
!spreq <base64_payload>
```

Payload (binary, before base64):

| Offset | Size | Field |
|--------|------|-------|
| 0 | 1 | `count` (1 to 255), number of groups |
| 1 + 33*i | 33 | `ser_P(X_i)` for group i |

The taker sends the same `!spreq` (same points, same order) to every maker in the session. A maker MUST validate that each `X_i` is a valid, non-infinity curve point, that the `X_i` are pairwise distinct, and MUST respond at most once per session; a second `!spreq` in the same session is a protocol error. In the normal flow `count` is `1` (the taker's single payment output). Because each group is an additional static Diffie-Hellman evaluation against the same maker key (see Security Considerations, Static DH oracle exposure), a maker SHOULD reject a `!spreq` whose `count` exceeds a small implementation-defined bound (a value such as 4 covers every realistic payment-splitting case) rather than blindly answering all 255 possible groups.

#### !spshare (maker to taker)

```
!spshare <base64_payload>
```

Payload (binary, before base64):

| Offset | Size | Field |
|--------|------|-------|
| 0 | 1 | `count`, MUST equal the request count |
| 1 + 97*i | 33 | `ser_P(S_i)` where `S_i = alpha*X_i` |
| 34 + 97*i | 32 | `e_i`, DLEQ challenge |
| 66 + 97*i | 32 | `s_i`, DLEQ response |

`alpha` is the maker's share scalar over exactly the inputs it announced in `!ioauth`. Entries appear in request order.

#### DLEQ Proof

The proof shows that `S = alpha*X` was computed with the same secret `alpha` that links `G` to the maker's share key `A_sum`, without revealing `alpha`. It is the JMP-0001 PoDLE proof (Chaum-Pedersen) with the NUMS generator `J` replaced by the taker-supplied base `X`, with the taker-supplied base `X` additionally bound into the challenge hash. Binding `X` makes each proof valid only for the exact base it was issued against (a proof for `X_i` does not transfer to another group `X_j`) and, because the resulting preimage has five points rather than the four of the JMP-0001 PoDLE challenge, no `!spshare` proof can be replayed as a PoDLE proof or vice versa.

Prover (maker), for each group:

```
k  = random scalar in [1, n-1]      # fresh per proof
K1 = k*G
K2 = k*X
e  = int(SHA256(ser_P(K1) || ser_P(K2) || ser_P(A_sum) || ser_P(X) || ser_P(S))) mod n
s  = (k + e*alpha) mod n
```

Verifier (taker), recomputing `A_sum` from the maker's `!ioauth` input set:

```
K1' = s*G - e*A_sum
K2' = s*X - e*S
accept iff e == int(SHA256(ser_P(K1') || ser_P(K2') || ser_P(A_sum) || ser_P(X) || ser_P(S))) mod n
```

The taker MUST verify the DLEQ proof of every share and MUST validate that every `S` is a valid, non-infinity curve point. The taker MUST also reject a maker whose recomputed `A_sum` is the point at infinity (a degenerate input set whose eligible scalars sum to zero mod n, for which `ser_P(A_sum)` is undefined and the share carries no information). A maker whose share fails verification, or whose `A_sum` is infinity, MUST be treated like a nonresponsive maker (dropped from the session); its share MUST NOT be used.

### Output Derivation

Once the taker holds a verified share from every maker whose inputs will appear in the transaction, it derives the silent payment outputs following the BIP352 sender algorithm, with the private-key sum replaced by the unblinded share sum. For each group `g`:

```
a_T  = sum of the taker's own eligible scalars (mod n)
C_g  = a_T*B_scan_g + r_g^(-1) * sum_i(S_i_g)       # equals a*B_scan_g for the full input set
```

where the sum runs over all makers' shares for group `g`. If `C_g` is the point at infinity, the taker MUST abort. Then, with the final input set fixed:

```
A          = sum over all transaction inputs of lift_x(q)   # abort if infinity
input_hash = hash_BIP0352/Inputs(outpoint_L || ser_P(A))    # abort if 0 or >= n
ecdh_g     = input_hash * C_g
```

`outpoint_L` is the lexicographically smallest outpoint of the transaction, per BIP352. For each address `(B_scan_g, B_m)` the taker computes `t_k = hash_BIP0352/SharedSecret(ser_P(ecdh_g) || ser32(k))` with the BIP352 `k` counter rules. As in BIP352, if `t_k` is not a valid scalar (`t_k = 0` or `t_k >= n`) the taker MUST fail for that output. Otherwise it sets `P = B_m + t_k*G` and encodes `x_only(P)` as a P2TR output. In the normal JMP-0001 flow this is the taker's single equal-amount payment output with `k = 0`.

Correctness: `C_g = a_T*B_scan_g + r_g^(-1)*sum_i(alpha_i*r_g*B_scan_g) = (a_T + sum_i(alpha_i))*B_scan_g = a*B_scan_g`, where `a` is the BIP352 private-key sum over all eligible inputs, so an unmodified BIP352 receiver computing `input_hash*b_scan*A` derives the same shared secret and finds the output.

### Completeness and Input-Set Changes

- **All inputs covered.** The taker MUST obtain a verified share from every maker whose inputs appear in the final transaction and MUST NOT include any input whose eligible scalar is not covered by its own keys or a verified share. In the tr0 pit every input is P2TR key-path, so every input is eligible and is seen as such by the receiver.
- **Shares are input-set independent.** A share `S = alpha*X` depends only on the maker's own inputs and the blinded point, not on `input_hash` or on other participants. If a maker is dropped after shares were collected, the taker recomputes `A` and `input_hash` for the reduced input set and re-derives the outputs without re-querying the remaining makers. The same applies if the taker changes its own input selection.
- **Re-derivation before re-signing.** If the input set changes for any reason, the silent payment outputs MUST be re-derived before signatures are requested. JMP-0005's mandatory `SIGHASH_DEFAULT` enforces this naturally: any input change invalidates all collected signatures, and BIP352 forbids input changes after signing for the same reason (`ANYONECANPAY` is unsafe).

### Record Keeping and Recovery

The taker SHOULD persist, for each silent payment output, the tuple `(txid, B_scan, B_m, k, t_k)` at least until the output is confirmed. If derivation was performed incorrectly (an undetected bad share or implementation bug), a standard scanning receiver will not find the payment; the funds are not burned, because the receiver can compute the spending key `b_spend + t_k (+ label)` from an out-of-band disclosure of `t_k` (compare BIP352 Appendix A, out-of-band notifications). Mandatory DLEQ verification makes this a recovery path of last resort rather than an expected flow.

## Backward Compatibility

`!spreq` and `!spshare` are exchanged only between peers that both advertise `sp_ecdh`, inside an encrypted tr0 session. Legacy peers never observe them; unknown features in the handshake are ignored per JMP-0001. The resulting transaction is indistinguishable on-chain from any other tr0 CoinJoin: the silent payment output is an ordinary-looking P2TR output among the equal-amount outputs. Receivers need no JoinMarket awareness: any BIP352 v0 wallet detects the payment.

## Rationale

**No change to BIP352 is required.** The collaborative derivation produces exactly the shared secret a single-entity sender would produce, so the receiver side of BIP352 is untouched. BIP352 already names this construction: the all-inputs rule was chosen partly to protect a CoinJoin sender from the receiver (the receiver cannot tell which inputs are the sender's), the rationale points at Blind Diffie-Hellman for hiding the recipient from co-participants, and the taproot section sketches partial ECDH shares with DLEQ proofs for aggregate keys. The remaining gaps are an interactive protocol specification, which this document provides for JoinMarket, and a formal security proof for the collaborative setting, which BIP352 itself acknowledges is missing ("it is recommended that the keys of all inputs of a transaction belong to the same entity as there is no formal proof that the protocol is secure in a collaborative setting"). The only upstream contribution that would help is informational: an appendix to BIP352 specifying collaborative sending (share format, blinding, DLEQ) so that implementations interoperate; this document can serve as a concrete input to such a proposal.

**Alternatives considered and rejected.**

- *Derive from the taker's inputs only.* The receiver sums all eligible inputs; honoring a subset would require either scanning every input subset (combinatorial scanning cost, defeating BIP352's linear-scan design) or an explicit on-chain signal (an output fingerprint, defeating the goal that silent payments be indistinguishable). Both contradict BIP352's stated design and would require a backward-incompatible new silent payments version.
- *Make maker inputs ineligible.* BIP352 skips P2TR inputs spent via script path with the NUMS internal key `H`. Makers could theoretically use such spends so that only the taker's inputs count. This marks every maker input on-chain (script-path witnesses with a known-NUMS control block), destroys the tr0 pit's key-path uniformity, and inflates witness size. Rejected.
- *Unblinded shares.* Without blinding, every maker learns `B_scan`, can link the payment to a published silent payment address, and can compute the output key, identifying the taker's payment output among the equal outputs. Blinding is mandatory.
- *Sharing private keys.* Trivially correct and trivially unacceptable.

**Why tr0 only.** P2WPKH inputs are also BIP352-eligible, so the derivation would work in an sw0 pit. But the silent payment output must be P2TR, and a lone P2TR equal-amount output among P2WPKH outputs is self-identifying, which defeats the purpose of paying through a CoinJoin. In the tr0 pit the output is uniform with every other output.

**Why only taker outputs.** Makers are interactive participants that hand the taker a fresh address in `!ioauth`; they gain nothing from silent payments there. Deriving a maker output as a silent payment would also be circular: the address must be in `!ioauth`, but the derivation depends on the full input set, which is only known after every `!ioauth` arrives.

**Why one round and why between Phases 3 and 4.** After `!ioauth`, the taker knows every maker's input set, so share keys `A_sum` are verifiable; before `!tx`, the outputs are still undetermined, so the derived address can be placed in the transaction. Because shares are independent of `input_hash`, a single round suffices and partial failures do not invalidate other makers' shares.

**Provenance.** The blind DH construction is David Wagner's 1996 scheme as revived by Ruben Somsen (and deployed in Cashu and similar systems); the share-correctness DLEQ is Chaum-Pedersen, the same proof used by JoinMarket PoDLE and by Privacy Pass, whose security analysis (one-more-decryption hardness) is the closest studied analogue.

## Security Considerations

**No formal security proof.** BIP352 explicitly recommends single-entity inputs because the collaborative setting has no formal proof. This feature is opt-in for both sides, does not weaken sessions that do not use it, and its failure modes are loss of payment detectability (recoverable, see Record Keeping) and the oracle exposure below, not theft.

**Static DH oracle exposure.** A maker that returns `alpha*X` for a taker-chosen `X` acts as a static Diffie-Hellman oracle for `alpha`. Adaptive access to such an oracle degrades discrete-log security of that specific key (Brown-Gallant, [eprint 2004/306](https://eprint.iacr.org/2004/306); Cheon's attack): on secp256k1, on the order of 2^24 oracle queries against the same key would reduce its security to roughly 116 bits, and meaningful degradation needs far more queries than any realistic number of CoinJoin sessions. The relevant cost metric is the total number of distinct `(X, alpha*X)` evaluations a taker can extract for one `alpha`, which is the sum of the `count` fields across every `!spreq` that maker answers, not the number of sessions: a single `!spreq` with `count = 255` yields 255 evaluations from one response. Mitigations: a maker MUST respond to at most one `!spreq` per session; it SHOULD cap `count` at a small bound (see `!spreq`), so one session yields a handful of evaluations at most; it only responds after a PoDLE-verified `!auth`, so every session costs the taker a commitment; the queried key is the session's input-key sum, which is expected to be spent by the very transaction being built; and a maker SHOULD avoid offering the same UTXO set across a large number of aborted `sp_ecdh` sessions (rotating or remixing coins bounds per-key evaluations to a handful). A conservative maker MAY additionally track the cumulative number of evaluations served for a given UTXO set and stop offering `sp_ecdh` for that set well before any security-relevant threshold.

**Malicious or faulty shares.** A wrong share would make the taker derive an output the receiver never finds. The mandatory DLEQ verification reduces this to the binding of `A_sum`: since `A_sum` is recomputed by the taker from the maker's `!ioauth` inputs (the same inputs the maker must later sign with `SIGHASH_DEFAULT`), a maker cannot both pass verification and supply a wrong share. A maker that announces inputs it cannot sign can still abort the session (existing maker DoS, unchanged by this feature), but the transaction then never broadcasts, so no misdirected payment occurs.

**Recipient privacy against makers.** With fresh uniform blinding, `X_g` and `S_g` are uniformly random points; makers learn only that the taker creates some silent payment output, not to whom. Reuse of `r_g` across sessions or groups MUST NOT happen, as it would let a maker correlate requests. The on-chain transaction reveals nothing: the output is a generic P2TR output.

**Sender privacy against the receiver.** Unchanged from BIP352: because the shared secret commits to all inputs, the receiver cannot distinguish the taker's inputs from the makers'. This is the property BIP352 cites as the reason for the all-inputs rule.

**Point validation.** Makers MUST reject `X` values that are not valid non-infinity secp256k1 points and MUST reject a `!spreq` that repeats an `X_i` (distinct bases keep each group an independent blinding and prevent a taker from disguising repeated oracle queries as separate groups); takers MUST reject `S` values that are not valid non-infinity points and MUST reject a maker whose recomputed `A_sum` is infinity. secp256k1 has cofactor 1, so no small-subgroup checks are needed beyond curve membership.

**DoS.** A maker that withholds `!spshare` or fails verification is dropped exactly like a maker that withholds `!ioauth` or `!sig`. Because shares are input-set independent, recovery from a dropped maker requires no additional round trips to the remaining makers.
