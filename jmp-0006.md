## Abstract

This specification defines the `tx_extension_v2` feature flag, which
allows additional makers to join an in-flight JoinMarket CoinJoin
transaction *after* the initial round of signatures has been collected.
Extension increases the number of equal-amount CoinJoin outputs in a
single transaction without restarting the round, raising the cost of
subset-sum and intersection analysis on the resulting on-chain
transaction.

`v2` replaces the unshipped `tx_extension_v1` draft. The high-level
flow is unchanged but the CLSAG attestation primitive moved from a
sketch over the NWabiSabi-Rust crate to the cashu-kvac CLSAG module,
the transcript layout gained a `context_hash` slot, the minimum
attestation cardinality `K` was raised from `1` to `2`, and the
domain-separation tag advanced to `jmng/tx_extension_v2/attest`. The
two flags are not interoperable; `v1` has no implementation.

## Motivation

A CoinJoin's effective anonymity set against subset-sum analysis depends
on:

1. The number of equal-amount outputs.
2. The diversity of input/output groupings consistent with the on-chain
   transaction.

JoinMarket's base protocol fixes both at round-start: the taker selects N
makers, builds the transaction, collects signatures, and broadcasts. Any
maker that comes online during signing or any taker who would like to
piggyback their own CoinJoin onto the same transaction must wait for the
next round.

This specification allows the taker (still acting as coordinator) to
gather more participants -- either additional makers from the orderbook
or a separate "joiner" identity -- once the initial round is signed but
before broadcast. By using `SIGHASH_ALL | SIGHASH_ANYONECANPAY` for the
intermediate sigs, existing signatures remain valid as new inputs are
appended. A final "freeze" step re-collects `SIGHASH_ALL` signatures over
the now-complete transaction.

This feature builds on JMP-0005's `zkp_credentials_v2`: extension is only
useful when input/output mappings are hidden from the coordinator, since
each extension round otherwise leaks a fresh batch of mappings. Therefore
`tx_extension_v2` is only valid for runs that also negotiate
`zkp_credentials_v2`.

## Specification

### Feature Advertisement

Peers advertise `tx_extension_v2` support in the handshake `features`
dict and in their `Offer.features`:

```json
{"features": {"tx_extension_v2": true}}
```

`tx_extension_v2` MUST NOT be advertised by an implementation that does
not also advertise `zkp_credentials_v2`. A taker observing the
combination `{"tx_extension_v2": true, "zkp_credentials_v2": false}` MUST
treat the maker as not supporting extension and ignore the flag.

#### Sub-Flag: `tx_extension_v2.late_join`

A maker that is willing to join an *existing* in-flight transaction
(rather than just tolerate one) advertises:

```json
{"features": {"tx_extension_v2": true, "tx_extension_v2.late_join": true}}
```

This sub-flag tells the taker that the maker will respond to a `!cjext`
broadcast and follow the late-join handshake described below.

### Negotiation

Per-CoinJoin negotiation follows the same pattern as JMP-0005: the taker
includes `tx_extension_v2` in the `!fill` `features` field, the maker
acknowledges in `!pubkey` `features`, and the effective state is the
intersection.

If `tx_extension_v2` is active for a run, the maker MUST sign all of its
inputs in the initial round with `SIGHASH_ALL | SIGHASH_ANYONECANPAY`,
because the input/output set will change between rounds.

### Round Numbering

Within a CoinJoin run identified by `run_id` (a 32-byte random value
chosen by the taker at the start), each pass of input/output addition is
identified by `round_no`, a 16-bit unsigned integer starting at `1`.
Round `0` is reserved for the initial JMP-0001 / JMP-0005 round.

The taker MUST cap the number of *extension* rounds at `max_rounds`,
advertised in the `!cjext` broadcast (default 2). Round 0 is not
counted; `max_rounds = 2` means up to two extension rounds (rounds 1
and 2) may follow round 0. The taker MUST cap the wall-clock duration
of the extension phase at `extension_window_secs` (default 60).

### Wire Protocol

All commands described here are *new* relative to JMP-0001 and JMP-0005.
Encryption follows the same rule as the rest of the protocol:
participant-to-participant commands are encrypted under the NaCl
session; broadcast commands are sent as PUBMSG (687) and may include
encrypted content payloads addressed to specific recipients.

#### Phase EXT-1: Extension Beacon

After collecting all SIGHASH_ALL|ANYONECANPAY signatures from the
initial round AND the bond attestation from `K` participating makers
(see Phase EXT-1A below), the taker broadcasts:

```
!cjext <run_id_hex> <round_no> <epoch_id_hex> <issuer_pubkey_hex>
       <unsigned_tx_b64> <cj_amount> <deadline_ts> <max_rounds> <bond_attestation_b64>
```

| Field | Type | Description |
|-------|------|-------------|
| `run_id_hex` | string | 32-byte run identifier (hex) |
| `round_no` | integer | Round number (>= 1) |
| `epoch_id_hex` | string | KVAC epoch (same as JMP-0005 issuer setup) |
| `issuer_pubkey_hex` | string | KVAC issuer pubkey for this run |
| `unsigned_tx_b64` | string | Current unsigned transaction (will gain inputs/outputs) |
| `cj_amount` | integer | Equal-amount output value in satoshis |
| `deadline_ts` | integer | Unix timestamp; late-join requests after this MUST be rejected |
| `max_rounds` | integer | Maximum number of extension rounds (default 2). Round 0 is not counted. |
| `bond_attestation_b64` | string | See "Bond Attestation" below |

The beacon is sent as PUBMSG (687) so any maker connected to the
directory can observe it. Implementations SHOULD additionally direct-DM
the beacon to known late-join-capable makers from the orderbook to
reduce reliance on directory broadcast for routing.

#### Bond Attestation

To convince late joiners that the in-flight CoinJoin is real (not a
surveillance honeypot constructed by a malicious taker), the taker
collects a threshold attestation proving that at least `K` makers
holding fidelity bonds drawn from a quality-checked anonymity set `N`
are participating in the round. The attestation MUST hide *which* `K`
makers signed: revealing the round-0 participant set to outside
observers would defeat the privacy gain of the extension protocol.

The attestation is a vector of `K` independent CLSAG-style linkable
ring signatures over secp256k1, one per participating signer, each
ring drawn from the same taker-supplied anonymity set.

**Anonymity set selection.** The taker selects an ordered list of
`N` bond-pubkey/outpoint pairs from the orderbook and includes them
verbatim in the attestation payload. The taker is responsible for
choosing `N`; recommended construction is "all bonds at or above the
30th percentile by `bond_value` in the current orderbook snapshot,
capped at `N <= 200`". Each ring signature MUST verify against this
exact list, so the taker cannot vary the set per signer.

**Quality check (verifier-side).** Every late joiner independently
re-derives an acceptable anonymity set from its own orderbook view
and compares against the taker-supplied set. The verification
threshold is configurable; the default policy is:

- Every entry in the supplied set MUST appear in the verifier's
  orderbook with the published `utxo_pubkey` and `bond_outpoint`.
- `|N|` MUST be at least `min_anonymity_set_size` (default 25).
- The supplied set MUST cover at least
  `min_anonymity_set_quality_fraction` (default 0.5) of the verifier's
  own top-30th-percentile bonds. This catches a malicious taker who
  packs the set with many tiny bonds it controls.

**Per-signer ring signature.** A participating round-0 maker
contributes a CLSAG ring signature over secp256k1 with:

- Ring members: the `N` x-only bond pubkeys supplied by the taker.
- Signing key: the secret key controlling the maker's bond UTXO.
- Message: `DST || run_id || round_no_be16 || context_hash` where:
  - `DST` is the 27-byte ASCII tag `"jmng/tx_extension_v2/attest"`,
  - `run_id` is the 32-byte CoinJoin run identifier,
  - `round_no_be16` is `round_no` encoded as big-endian uint16,
  - `context_hash` is a 32-byte digest the taker MAY use to bind the
    attestation to additional run-specific context (the unsigned
    transaction skeleton, the verifier's anonymity-set quality
    requirements, etc.); takers that do not need this binding MUST
    pass the all-zero `context_hash` (`0x00 * 32`), which reproduces
    the simpler v1 transcript shape and is the default in the
    reference implementation.
- Linking key image: `I = H_p(P_signer) * x_signer + H_s(run_id) * G`,
  where `P_signer` is the signer's bond pubkey, `x_signer` is the
  corresponding secret key, `H_p` is the cashu-kvac try-and-increment
  hash-to-curve specialized to the CLSAG `H_p` domain, and
  `H_s(run_id)` is the Merlin-transcript key-image rotation scalar
  keyed on `run_id`. Adding `H_s(run_id) * G` rotates the key image
  per run so two attestations from different runs are unlinkable;
  within a single run the key image is deterministic so duplicate
  signers are trivially detected by checking key-image equality.

**Wire format** of `bond_attestation_b64` (decoded):

```
<set_size:2b BE>
  <pubkey_1:32b>...<pubkey_N:32b>
  <outpoint_1:36b>...<outpoint_N:36b>
<sig_count:1b>          (== K)
  <ring_sig_1>
  <ring_sig_2>
  ...
  <ring_sig_K>
```

Each `ring_sig_i` is a CLSAG signature object encoded as:

```
<key_image:33b><c0:32b><s_1:32b>...<s_N:32b>
```

Total per-ring size: `33 + 32 + 32 * N` bytes; for `N = 100` this
is approximately 3.3 KB per ring, so a `K = 3` attestation runs to
about 10 KB plus the 6.8 KB ring-member list, ~17 KB total.

**Recommended parameters.** `K = 3`, `N` chosen by the taker as
described, threshold `min_anonymity_set_size = 25`,
`min_anonymity_set_quality_fraction = 0.5`. `K` MAY be raised by
takers willing to coordinate larger attestation rounds; verifiers
MUST accept any `K` in the closed range
`[attestation_threshold_K_min, attestation_threshold_K_max]`
(defaults `2` and `16` respectively). `K = 1` is rejected because
a single ring signature does not give meaningful threshold
assurance: an isolated malicious taker can produce it whenever it
controls any one bond in the ring, including bonds the verifier
itself reports as healthy. Requiring at least two independent
signers forces a colluding taker to corrupt at least two bonded
identities, which is the minimal non-trivial Sybil cost.

**Verification procedure** for late joiners:

1. Decode the attestation, parse `N` ring members and `K` ring
   signatures. Reject if `K < attestation_threshold_K_min` (default
   `2`) or `K > attestation_threshold_K_max` (default `16`).
2. Apply the quality check above; reject the attestation if it fails.
3. For each ring signature: verify the CLSAG signature against the
   shared ring, the transcript
   `DST || run_id || round_no_be16 || context_hash` (with `DST =
   "jmng/tx_extension_v2/attest"`), and the supplied key image. The
   verifier MUST use the same `context_hash` the taker supplied; the
   default is the all-zero 32-byte digest.
4. Reject the attestation if any two key images are equal (would
   indicate a single signer claiming `K` distinct identities within
   one run).
5. Record the set of seen key images keyed by `run_id` for
   monitoring; reject any subsequent `!cjext` for the same `run_id`
   that reuses any already-seen key image (replay protection).

CLSAG was chosen over alternatives (concat Schnorr revealing
signers, Triptych, AOS/Borromean) because it gives `O(N)` signature
size with a small constant, supports per-run key-image rotation
cleanly, and can be implemented over secp256k1 reusing primitives
the cashu-kvac crate already ships. The trade-off is a signature
size linear in `N` rather than logarithmic; with `N ~ 100` this is
acceptable for a once-per-extension PUBMSG broadcast that uses
JMP-0001 fragmentation if needed. The reference implementation is
`cashu-kvac/src/clsag.rs` (Rust) exposed to Python via the
`cashu_kvac.CLSAG` class and wrapped in
`jmcore.clsag_attestation`.

#### Phase EXT-1A: Attestation Collection

The taker assembles `bond_attestation_b64` by collecting `K` CLSAG
signatures from a chosen subset of round-0 makers BEFORE broadcasting
`!cjext`. Selection and collection use a new PRIVMSG pair:

```
taker -> !attestreq <run_id_hex> <round_no> <ring_b64>
maker -> !attest    <run_id_hex> <round_no> <clsag_sig_b64>
```

| Field | Type | Description |
|-------|------|-------------|
| `run_id_hex` | string | 32-byte run identifier (hex) |
| `round_no` | integer | The extension round about to be announced (>= 1) |
| `ring_b64` | string | Base64-encoded `<set_size:2b BE><pubkey_1:32b>...<pubkey_N:32b><outpoint_1:36b>...<outpoint_N:36b>` |
| `clsag_sig_b64` | string | Base64-encoded `<key_image:33b><c0:32b><s_1:32b>...<s_N:32b>` |

Both messages are encrypted under the existing per-session NaCl
channel established during round 0. The taker MAY send `!attestreq`
to more than `K` round-0 makers in parallel and use the first `K`
valid `!attest` replies received within
`attestation_request_timeout_secs`. If fewer than `K` makers reply
in time, the taker selects additional candidates and retries; if
the taker still cannot collect `K` signatures, it MUST abort the
extension phase and proceed to Phase EXT-4 (freeze) over the round-0
participant set only.

**Maker-side checks** before signing an `!attestreq`:

1. The `run_id` MUST match the round the maker is currently
   participating in.
2. The `round_no` MUST be at most `max_rounds` (per the round-0
   `!fill` features negotiation, the taker advertised this value).
3. The supplied ring MUST include the maker's own bond pubkey and
   bond outpoint (otherwise the maker cannot produce a valid CLSAG
   over this ring).
4. The maker MAY apply the same quality check that verifiers run
   (size, percentile overlap with its local orderbook view) before
   signing; rejection is a routine response and MUST emit `!error`.

A maker that has already produced an `!attest` for a given
`(run_id, round_no)` MUST refuse to sign a second one for the same
`(run_id, round_no)` even if the ring differs, to keep its key image
unique within the run.

#### Phase EXT-2: Late Join Handshake

A maker that wishes to join an extension round responds to `!cjext` by
opening a fresh session with the taker (using the location-string
extracted from the directory's peer list, exactly as in JMP-0001) and
sending a normal `!fill` message annotated with extension parameters:

```
!fill <oid> <amount> <taker_nacl_pk> <commitment> features={"tx_extension_v2":true,"zkp_credentials_v2":true,"join_run":"<run_id_hex>","join_round":<round_no>}
```

The taker:

1. Verifies the maker advertised `tx_extension_v2.late_join` and is in
   the orderbook with sufficient `bond_value`.
2. Treats the rest of the handshake exactly as JMP-0001 / JMP-0005
   (`!auth`, `!ioauth`, `!zkpparams`, `!zkpreq`, `!zkpcred`,
   `!zkpreg`).

If the maker is already a round-0 participant, it MUST NOT submit a
late-join `!fill`; the taker will direct-DM existing participants the
extended-tx message at Phase EXT-3.

#### Phase EXT-3: Extended Transaction

After all late joiners have completed the credential and registration
phases, the taker constructs the updated unsigned transaction (with the
new inputs and outputs appended and the output set re-shuffled) and
sends it to *every* participant (round-0 and late joiners alike):

```
!txext <run_id_hex> <round_no> <unsigned_tx_b64> <input_index_map_b64>
```

`input_index_map_b64` is a base64-encoded JSON object mapping each
participant's previous input indices (round_no - 1) to their new indices
(round_no). This allows participants who already signed to detect that
their original inputs have been preserved with the same outpoints, only
their position changed:

```json
{"prev_to_new": [0, 3, 1, 5], "new_inputs_count": 2}
```

Each participant verifies:

1. Its previous inputs are still present at the indices specified.
2. Its registered outputs are still present in the new output set.
3. The new inputs and outputs respect the announced cj_amount.

The participant then re-signs *only* its inputs with `SIGHASH_ALL |
SIGHASH_ANYONECANPAY` over the new transaction:

```
!sigext <run_id_hex> <round_no> <input_index> <signature_b64>
```

One `!sigext` per input. The previous round's signatures remain valid
on the now-larger transaction because of the SIGHASH_ANYONECANPAY flag,
but each participant resigns to attest that they observe the new
transaction shape. A participant MAY choose to abort here (sending
`!error`) if the new transaction is not acceptable; the taker then
either continues without that participant (dropping their inputs and
outputs and re-broadcasting an updated `!txext`) or aborts the run.

Phase EXT-3 MAY repeat up to `max_rounds` times.

#### Phase EXT-4: Freeze

When the taker decides to stop accepting joiners (deadline reached, or
maximum rounds hit, or no more candidates), it broadcasts a "freeze"
message:

```
!txfreeze <run_id_hex> <final_unsigned_tx_b64>
```

This is sent to every participant via PRIVMSG (encrypted under each
participant's session). Each participant verifies the final transaction
and re-signs all of its inputs with `SIGHASH_ALL` (note: not
ANYONECANPAY) to fully bind to the now-immutable input set:

```
!sigfinal <run_id_hex> <input_index> <signature_b64>
```

These `SIGHASH_ALL` signatures REPLACE the participant's earlier
signatures in the final transaction. The taker collects all
`!sigfinal` messages, replaces the placeholder signatures, and
broadcasts the transaction to the Bitcoin network as in JMP-0001
Phase 5.

If any participant fails to send `!sigfinal` by a short hard deadline
(recommended: 30 seconds), the taker MAY broadcast a "fallback"
transaction containing only round-0 participants and the original
SIGHASH_ALL|ANYONECANPAY signatures (which remain valid because the
SIGHASH form is permissive). Late joiners are dropped.

### State Machine Summary

```
Round 0 (legacy or ZKP):
    fill -> pubkey -> auth -> ioauth (or zkpreq/zkpcred) -> tx -> sig

After round 0 SIG collection (sigs are SIGHASH_ALL|ANYONECANPAY when tx_extension is active):
    [optional] cjext broadcast
    [optional] late-join fill/pubkey/auth/ioauth/zkpreq/zkpcred/zkpreg
    [optional] txext -> sigext (loop, up to max_rounds)
    txfreeze -> sigfinal -> broadcast
```

### Maker State Machine Additions

In addition to the JMP-0001 states, makers participating in a
`tx_extension_v2` run track:

- `EXTENDED_TX_RECEIVED`: after `!txext`, before resigning
- `EXTENDED_SIG_SENT`: after sending `!sigext`
- `FROZEN_TX_RECEIVED`: after `!txfreeze`
- `FROZEN_SIG_SENT`: after sending `!sigfinal`

A maker MAY accept up to `max_rounds` cycles of `EXTENDED_TX_RECEIVED ->
EXTENDED_SIG_SENT` before transitioning to `FROZEN_TX_RECEIVED`.

### Configuration Parameters

| Parameter | Default | Description |
|-----------|---------|-------------|
| `max_rounds` | 2 | Maximum number of extension rounds (round 0 not counted) |
| `extension_window_secs` | 60 | Wall-clock budget for the entire extension phase |
| `freeze_grace_secs` | 30 | Window for receiving `!sigfinal` after `!txfreeze` |
| `min_anonymity_set_size` | 25 | Minimum `N` ring members the verifier accepts in a bond attestation |
| `min_anonymity_set_quality_fraction` | 0.5 | Minimum overlap (fraction) between the supplied ring set and the verifier's locally-derived top-percentile bond set |
| `late_join_bond_threshold` | median_bond | Minimum bond a late joiner must have to participate |
| `attestation_threshold_K` | 3 | Number of CLSAG ring signatures the taker collects from round-0 makers (see "Bond Attestation") |
| `attestation_threshold_K_min` | 2 | Minimum `K` a verifier accepts in a bond attestation; raised from 1 in v2 to force at least two independent signers |
| `attestation_threshold_K_max` | 16 | Hard upper bound on `K` to defeat amplification attacks |
| `attestation_request_timeout_secs` | 10 | How long the taker waits for an `!attest` reply before re-selecting signers |

## Rationale

### Why `SIGHASH_ALL | SIGHASH_ANYONECANPAY` for intermediate rounds?

Because each round changes the input set. `SIGHASH_ANYONECANPAY` allows
appending inputs without invalidating prior signatures.
`SIGHASH_SINGLE` (which would also allow output mutation) is rejected
because it permits output reordering, which we explicitly want to
prevent within a round (the maker has registered specific outputs and
must be able to verify them in the next round).

### Why a second SIGHASH_ALL pass at freeze?

Once the input set is final, plain `SIGHASH_ALL` is the standard form
and avoids any ambiguity for downstream observers. It also commits each
maker to the *output set* in addition to its own inputs, which is a
stronger guarantee than ANYONECANPAY alone.

### Why a bond attestation rather than just trusting the directory?

A taker can fabricate `!cjext` beacons cheaply if the only check is
"directory broadcast it". Late joiners would then leak inputs/outputs
into a non-existent CoinJoin, effectively letting the taker run a
surveillance trap. The bond attestation forces the taker to coordinate
with at least K real bonded makers, each of whom loses nothing
financially by signing but compromises its own privacy in front of
the other round-0 participants if it signs for a fake round; the
remaining round-0 participants would notice their inputs never make
it on chain.

### Why CLSAG ring signatures rather than plain Schnorr or MuSig2?

The earliest sketch of this design used K plain BIP340 Schnorr
signatures, one per signing maker, with the signers' bond UTXOs
included verbatim in the attestation. That construction directly
publishes K of the round-0 participants' identities, which defeats
the privacy guarantee that motivates the extension protocol in the
first place: an outside observer learning who is in round 0 can
correlate them with their orderbook offers and inputs.

CLSAG over secp256k1 hides the signer inside an N-element ring
drawn from the orderbook's top-percentile bonds while keeping
verification cheap (linear scan, no pairings). The per-run
key-image construction (`H_p(P) * x + H_s(run_id)`) gives within-run
duplicate detection without cross-run linkability.

MuSig2 was rejected for two reasons: it would aggregate the K
signers into a single signature whose public key still has to come
from somewhere (forcing a published "attestation key" set, which is
just plain Schnorr again); and it would add an interactive signing
round across the K signers, which is a new failure mode in the
critical path of the extension flow.

Triptych and similar logarithmic-size ring constructions were
considered but rejected for now because there is no production
secp256k1 implementation we can take as a dependency, and porting
research code into the protocol critical path is too much risk for
the size win at our chosen `N`.

### Why limit late joiners to bonded makers?

A late joiner who is not in the orderbook is a black box to the taker
and to other participants. Forcing them to be a bonded maker means we
reuse the existing fidelity-bond anti-Sybil layer rather than inventing
a parallel one.

### Why broadcast `!cjext` at all?

Late joiners that are *already in the orderbook* could be reached by
direct DM, but the orderbook entry advertises a maker's ability to
join, not its real-time availability. Broadcasting via PUBMSG lets any
listening maker who has just come online opportunistically respond,
maximizing the late-join pool. The bond attestation prevents this
broadcast from being a surveillance vector.

### Could the taker impersonate joiners to inflate density?

Yes, if the taker controls extra UTXOs. This is no different from the
base protocol's "taker may add their own coins". The defense is the
same: the maker fee structure means the taker pays per output, so
self-stuffing has a real cost. The privacy benefit (subset-sum
hardening) accrues to all real participants regardless.

## Backward Compatibility

- Reference makers (joinmarket-clientserver) do not advertise
  `tx_extension_v2` and use single-round `SIGHASH_ALL` signing. They
  cannot participate in extension rounds.
- The unshipped `tx_extension_v1` draft and the present `v2` flag are
  NOT interoperable: the DST, transcript layout, and `K_min` default
  all changed. Implementations MUST NOT advertise `v1` and MUST
  treat a peer advertising `v1` as not supporting extension.
- A taker that includes a non-extension maker in round 0 of a run that
  it later wants to extend MUST either (a) abort the extension (round-0
  signatures are SIGHASH_ALL and cannot tolerate appended inputs), or
  (b) request the non-extension maker to abandon its slot, allowing the
  taker to drop its inputs/outputs before extending.
- Directories require no changes; `!cjext` is a PUBMSG and the rest of
  the new commands are PRIVMSG, both already supported.

## Security Considerations

- **Fake-beacon attack**: a malicious taker broadcasts `!cjext` for a
  CoinJoin that does not exist, hoping to harvest joiner inputs/outputs
  for surveillance. Defended by the bond attestation requirement.
- **Bond-attestation collusion**: if `K` bonded makers collude with the
  taker, they can produce a valid attestation for a fake round. Because
  CLSAG ring signatures hide which `K` makers signed, this attack does
  not unmask the colluders, but it also does not let them deny their
  participation: the per-run key images bind each colluder to one
  attestation in this `run_id`. Late joiners detect repeat-attacker
  patterns by accumulating key images per attacker class. The
  primary defense is therefore quality of the anonymity set
  (`min_anonymity_set_size`, `min_anonymity_set_quality_fraction`):
  the larger and more honest `N` is, the more honest signers must be
  co-opted to reach `K` valid signatures.
- **Anonymity-set poisoning**: a malicious taker could include `N`
  bond UTXOs that it controls so any `K` of those produce a valid
  attestation. Defended by the verifier-side quality check that
  requires the supplied set to overlap with the verifier's locally
  derived top-percentile bond set; a packed set of attacker-controlled
  bonds will not match a healthy orderbook view.
- **Late-joiner front-running**: a late joiner could submit valid
  registrations and then refuse to sign at freeze, forcing the taker
  to abort or fall back. Defended by the freeze grace window and the
  taker's option to broadcast the fallback transaction.
- **Replay across rounds**: `run_id` and `round_no` are bound into
  every signed message; replaying a `!sigext` from round 1 into round
  2 fails verification.
- **Tor circuit reuse**: late joiners that share Tor circuits with
  other identities can be correlated by the directory. Implementations
  MUST use stream isolation per JMP-0005.

## Reference Implementation

- [joinmarket-ng](https://github.com/joinmarket-ng/joinmarket-ng):
  - `jmcore/src/jmcore/clsag_attestation.py` (Python wrapper around
    cashu-kvac's CLSAG module: transcript construction, ring hashing,
    `pack_attestation` / `unpack_attestation`, and the
    `sign_ring` / `verify_attestation` entry points)
  - `jmcore/src/jmcore/attestation_wire.py` (JMP-0006 framing helpers)
  - `taker/src/taker/coinjoin_session.py` (taker-side extension phases)
  - `maker/src/maker/protocol_handlers.py` (maker-side `!attestreq` /
    `!cjext` / `!txext` / `!txfreeze` handlers)
- [cashu-kvac](https://github.com/lollerfirst/cashu-kvac): upstream
  KVAC primitives. JoinMarket NG uses the in-tree fork at
  `cashu-kvac/` which adds the secp256k1 CLSAG module
  (`cashu-kvac/src/clsag.rs`) exposed to Python as
  `cashu_kvac.CLSAG` with `sign`, `verify`, `key_image`, and
  `encoded_len` methods.
