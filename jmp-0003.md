## Abstract

This specification defines the `peerlist_features` feature flag, which extends
the PEERLIST message format to include each peer's advertised features. This
allows takers to discover peer capabilities before establishing direct
connections, enabling more efficient maker selection.

## Motivation

In the base protocol (JMP-0001), the PEERLIST message contains only nick and
location for each peer. A taker that needs makers with specific capabilities
(e.g., `neutrino_compat`) must either:

1. Connect to every maker and perform a handshake to discover features, or
2. Wait for the maker to announce offers and infer capabilities from the
   announcement format.

Both approaches are inefficient. Option 1 wastes Tor circuit establishment
time and connection resources. Option 2 requires waiting for announcements and
does not reliably indicate all capabilities.

By including feature information in the PEERLIST, takers can filter makers by
capability before attempting connections, reducing unnecessary Tor circuits
and improving CoinJoin startup latency.

## Specification

### Feature Advertisement

Directory servers that support the extended peerlist format advertise
`peerlist_features` in their DN_HANDSHAKE response:

```json
{"features": {"peerlist_features": true}}
```

Clients that can parse extended peerlist entries advertise the same feature in
their HANDSHAKE:

```json
{"features": {"peerlist_features": true}}
```

### Extended Peerlist Entry Format

When a directory supports `peerlist_features`, it MAY include a feature suffix
in peerlist entries for peers that advertised features during their handshake.

Standard entry format (JMP-0001):

```
nick;location
nick;location;D
```

Extended entry format:

```
nick;location;F:feature1+feature2
nick;location;D;F:feature1+feature2
```

The `F:` prefix identifies the features field. Features are listed as a
plus-separated (`+`) list of feature name strings. The `+` separator is used
instead of `,` because the PEERLIST message uses commas to separate entries.

The `F:` field, if present, MUST be the last field in the entry (after the
optional `D` disconnect flag).

### Feature Field Rules

- The `F:` field is OPTIONAL. Entries without it indicate the peer advertised
  no features (or the directory does not track features).
- Only features explicitly set to `true` in the peer's handshake are included.
- Unknown feature names MUST be preserved (not filtered) by the directory.
- The order of features within the `+`-separated list is not significant but
  implementations SHOULD sort alphabetically for deterministic output.
- An empty feature list (`F:`) SHOULD be omitted entirely rather than sent as
  `F:` with no value.

### Parsing

Implementations parse peerlist entries by splitting on `;` (semicolon):

1. First field: nick
2. Second field: location (`host:port`)
3. Remaining fields: iterate and check:
   - `D` indicates a disconnect notification
   - Anything starting with `F:` contains the feature list (split on `+`)
   - Unknown fields SHOULD be silently ignored

This parsing approach is forward-compatible -- additional fields can be added
in future specifications without breaking existing parsers.

### Example

A PEERLIST message with extended entries:

```
J5maker1OOOOOOO;abc123.onion:5222;F:neutrino_compat+ping,J5maker2OOOOOOO;def456.onion:5222,J5dirOOOOOOOOOO;dir789.onion:5222;F:ping+peerlist_features
```

Parsed:

| Nick | Location | Disconnect | Features |
|------|----------|------------|----------|
| J5maker1OOOOOOO | abc123.onion:5222 | No | neutrino_compat, ping |
| J5maker2OOOOOOO | def456.onion:5222 | No | (none) |
| J5dirOOOOOOOOOO | dir789.onion:5222 | No | ping, peerlist_features |

## Rationale

### Why use `+` instead of `,` as the feature separator?

The PEERLIST message uses commas to separate entries. Using commas within
entries would create parsing ambiguity. The `+` character does not appear in
nicks, locations, or existing field values, making it unambiguous.

### Why use the `F:` prefix?

The `F:` prefix distinguishes the feature field from other potential future
extensions and from the existing `D` disconnect flag. Without a prefix,
parsers would need to use positional logic that could break with future
additions.

### Why not send features in a separate message?

A separate message would require coordinating its delivery with the PEERLIST,
adding protocol complexity. Embedding features in the existing format is
simpler and atomic.

## Backward Compatibility

- The reference implementation (joinmarket-clientserver) does not parse the
  `F:` suffix and silently ignores it when splitting peerlist entries, because
  its parser only looks at the first two `;`-separated fields and the optional
  `D` flag.
- [joinmarket-rs](https://github.com/joinmarket-rs/joinmarket-rs) does not implement this feature. Its peerlist format is
  strictly `nick;location` with optional `;D`.
- Directories that do not support `peerlist_features` send standard entries.
  Clients MUST handle both formats.
