# JMP-0012: Credential Market

## Abstract

This opt-in market exchanges externally generated PoDLE openings and delegated
fidelity-bond certificates. Discovery uses existing JoinMarket directories.
Trades prefer direct onion connections and fall back to end-to-end encrypted
directory relay. New operations settle only through externally managed BOLT11
invoices; no Lightning node integration, escrow, spending authority, or atomic
fair exchange is assumed. A separately authorized fidelity bond makes
specific seller-signed contradictions accountable under [JMP-0013](jmp-0013.md).

## Motivation

An external PoDLE opening lets a taker authenticate without disclosing one of
its actual CoinJoin inputs to participating makers. Delegation lets a maker use
a fidelity bond without custody of its spending key. Neither primitive requires
a change to legacy CoinJoin authentication or fidelity-bond proof messages.

Privacy takes precedence over market efficiency. The market MUST NOT publish
buyer histories, payment receipts, invoice hashes, PoDLE openings, or renter
certificate private keys as listings. Users SHOULD acquire credentials separately
from their CoinJoin sessions, use fresh buyer keys and Tor identities per trade,
and avoid paying from coins belonging to the forthcoming CoinJoin.

## Specification

### Roles and Trust

* The bond owner authorizes a distinct market signing key for a specified period.
* The seller holds this market key, inventory, and payment requests, but need not
  hold the bond spending key. Its market encryption key is a separate X25519 key.
* The buyer generates its delivery encryption key locally. A bond renter also
  generates its own secp256k1 certificate key, never sending the private key.
* Payment wallets remain external. An explicit local seller acknowledgment, not
  an untrusted remote payment claim, initiates finalization.

A valid authorization establishes responsibility, not the existence or value of
collateral. Before paying, the buyer MUST independently verify the bond outpoint,
its positive confirmed unspent value, and its reconstructed CLTV P2WSH script
against its configured Bitcoin backend. The locktime MUST still be in the future.
The messaging network and Bitcoin network MUST be treated separately; for
example, an existing testnet messaging directory may serve regtest clients.

The buyer MUST set a maximum price and explicitly accept seller risk. The seller
can withhold delivery after payment. A signed quote or Lightning preimage does
not eliminate this risk. Timeouts MUST NOT be classified as
cheating evidence. A provider can also spend a PoDLE backing output before use.

### Encoding and Signatures

Market JSON uses ASCII strings, exact integers with absolute value at most
`2^53-1`, booleans, null, objects, and arrays. Duplicate object keys, floating
point values, unknown schema fields, unsupported versions, and nesting beyond
12 levels MUST be rejected. Documents are at most 16,384 bytes before transport
encoding. Canonical encoding sorts object keys, has no insignificant whitespace,
and uses JSON string escaping. Hex fields are lowercase with fixed byte lengths.

A signed document is `{"body": <object>, "signature": <DER-hex>}`. The signature
is strict low-S secp256k1 ECDSA over the Bitcoin Signed Message hash of:

```text
JMP-MARKET-V1|<canonical JSON body bytes>
```

Each body includes integer `version: 1` and a domain-specific `kind`. A document
identifier is SHA256 of canonical JSON bytes. References to authorizations and
allocations hash their **body**, excluding the signature, to avoid treating a
different valid ECDSA signature as a different contract.

`bond` is an object containing `network`, `outpoint: {txid,vout}`, `pubkey`
(compressed, 33 bytes), and `locktime` (uint32 Unix timestamp). Network values are
`mainnet`, `testnet`, `signet`, and `regtest`.

### Periods and Owner Authorization

To match inclusive legacy certificate expiry, period `p` covers heights
`2016*p+1` through `2016*(p+1)`, inclusive. At a positive chain height `h`, use
`floor((h-1)/2016)`. This differs from floor(h/2016) at the boundary block.

The bond owner signs this authorization body:

```json
{
  "kind": "authorization",
  "version": 1,
  "policy": "signed-faults-v1",
  "bond": {"network": "regtest", "outpoint": {"txid": "<32-byte hex>", "vout": 0}, "pubkey": "<33-byte hex>", "locktime": 2000000000},
  "period": 1,
  "seller_pubkey": "<33-byte hex>"
}
```

Placeholders in examples are explanatory and are not valid wire records.
Signing this domain explicitly accepts JMP-0013 sanctions. A legacy bond
certificate, nick signature, or rental certificate MUST NOT authorize a market
key or sanctions. An owner SHOULD use a different market key for each period.
Changing market keys does not permit duplicate allocations of the same resource.

### Native Transport

The following commands use existing JMP-0001 routing and authenticated private
message envelopes. Commands MUST be matched by complete token, not prefix.

| Command | Channel | Payload |
|---------|---------|---------|
| `mbook` | Public | Empty discovery request |
| `moffer` | Public | Signed JM envelope containing base64 of a signed listing |
| `mrequest` | Private | Signed JM envelope containing base64 sealed ciphertext |
| `mresponse` | Private | Signed JM envelope containing base64 sealed ciphertext |
| `mproof` | Public | Base64 canonical JMP-0013 proof |

The ordinary JM envelope signature uses `onion-network` on both direct and relay
paths. Listing bodies contain `kind: listing`, `version`, Bitcoin `network`,
`period`, `seller_pubkey`, `encryption_pubkey`, `products` (one or both of
`podle`, `bond`), indicative `price_sats`, and Unix `expires_at`. Listings contain
neither bond outpoints nor buyer information. Listings are at most 2,048 bytes.
Listing signatures prove key continuity, not stake ownership. Stake is disclosed
only in the private quote.

A seller publishes `moffer` to every connected directory when it starts and
re-announces before the listing expires, like CoinJoin offers. The reference
implementation sets `expires_at` one hour ahead and re-announces every 30
minutes; clients reject lifetimes exceeding two hours. A seller answers a public
`mbook` with a public `moffer` through the directory that relayed the request,
so a client that connects later need not wait for the next announcement. Clients
SHOULD send `mbook` once per directory connection rather than periodically, and
SHOULD drop listings from sellers that leave the directory peer list.

An orderbook observer MAY send `mbook` and validate public `moffer` messages
without becoming a credential buyer or seller. It MUST authenticate the outer
nick signature and inner listing signature and validate the encoding, network,
size, and expiry before presenting an advertisement as valid. A valid listing
does not prove available inventory, bond ownership, collateral value, exclusive
rental rights, or payment safety. A listing is not a CoinJoin liquidity offer.
Observers SHOULD keep listing state bounded and ephemeral, merge duplicate
observations across directories, and remove expired advertisements locally.

Before a request, the buyer obtains the seller location from existing peer
discovery, tries its direct onion connection, and falls back to one connected
directory. Production clearnet fallback is forbidden unless an explicit
development setting enables it. No HTTP seller endpoint or public invoice
directory is introduced.

Requests use libsodium SealedBox to the advertised seller X25519 key. Their
plaintext contains `request_id` (random 16-byte hex), `reply_pubkey` (base64
ephemeral X25519 key), and `body`. Replies use SealedBox to this reply key and
contain the same `request_id` and a response `body`. All underlying private
envelopes remain JM-signed. The same ciphertext and transport request ID are
reused on direct-to-relay retry. Decryption alone does not authenticate a sender.

The inner quote request contains `action: quote`, its own durable random
`request_id` (16-byte hex), `buyer_pubkey` (32-byte hex), `product`,
`certificate_pubkey` (null for PoDLE), `rail`, and `max_price_sats`.
The buyer key in this request is the persistent **trade-local** delivery key,
not the per-call transport reply key. A delivery request contains only
`action: delivery` and `quote_id`; its reply contains a sealed delivery or null.
There is no remotely accessible settlement command.

Each persisted buyer request owns a distinct trade-local key bundle by default.
The reference implementation generates it when the request file is first created,
stores it beside that file, and never regenerates it, so two purchases never
share a buyer public key and therefore never share an allocation buyer tag. A
retry reuses the existing bundle, and a persisted request whose bundle is missing
or unreadable MUST fail rather than rotate to a key the seller never quoted.
The reference CLI requires the request file for polling and retrieves the same
adjacent key bundle. It does not expose a shared buyer-key override.

### Quotes and Payment

A seller-signed quote body contains `kind: quote`, `version`, the complete signed
`authorization`, random 32-byte `quote_id`, `buyer_pubkey`, `product`, `resource`,
`certificate_pubkey`, `payment`, `created_at`, and `expires_at`.

`resource` is the PoDLE commitment hash, or, for a bond rental, SHA256 of canonical
`{"bond": <bond reference>, "period": p}`. A rental quote MUST name the renter's
certificate public key. A buyer MUST verify every request binding, the seller
signature, owner authorization, current chain period, amount cap, payment rail,
and payment request before displaying an actionable payment URI.

`payment` contains only `rail`, `request`, and `amount_sats`. The only valid rail
is `lightning`; other rails and unknown fields are invalid. Sellers MUST reject
unsupported rails before reservation or ledger changes. Buyers MUST validate
payment terms before displaying a payable URI. There is no older payment format
or migration path for this unpublished protocol.

* `lightning`: `request` is a valid signed BOLT11 invoice with an exact amount of
  `amount_sats*1000` millisatoshis, the appropriate network prefix, and expiration
  no earlier than the quote. Amountless invoices and ambiguous singleton tags
  are rejected. BOLT11 defines a distinct currency prefix per network: `lnbc`
  for mainnet, `lntb` for testnet, `lntbs` for signet, and `lnbcrt` for
  regtest. The invoice prefix MUST match the trade's Bitcoin network exactly.
  Unknown mandatory features are rejected.

Quote lifetimes are at most 900 seconds. A quote is valid only when
`created_at <= now < expires_at`. The seller MUST NOT reassign its invoice to
another quote after expiration. Late payments require operator reconciliation.

A Lightning preimage MUST be exactly 32 bytes and hash to the invoice payment
hash. It is not proof of payer identity or of actual settlement, since the payee
already knows it. The reference seller requires explicit local confirmation of
wallet settlement before finalizing. Future wallet adapters must preserve this
trust boundary and invoice uniqueness; none are specified here.

### Final Allocation and Delivery

Quotes are revocable reservations, not finalized allocations. On accepted local
settlement, the seller atomically commits inventory consumption, unique payment
reference consumption, an allocation receipt, and the sealed delivery. The
transaction MUST be durable before returning any finalized receipt. Repeated
requests for the same trade return the original records. A different request
cannot receive the same inventory, including after restart or concurrent access.

An allocation body contains `kind: allocation`, `version`, `authorization`
(authorization body hash), `allocation_id` (quote ID), `buyer_tag` (SHA256 of the
buyer's X25519 public key bytes), `product`, `resource`, and
`certificate_pubkey`. It has no invoice, payment amount, or settlement reference.

A delivery body contains `kind: delivery`, `version`, `allocation` (allocation
body hash), and `credential` (object). Both bodies are seller-signed. The package
is `{"authorization": <signed>, "allocation": <signed>, "delivery": <signed>}`,
sealed to the quote's buyer key. Even a caller knowing the quote ID or payment
outpoint receives only this buyer-sealed package. The buyer retains original
signed bytes before rejecting an invalid delivered credential, so evidence is
not discarded by an import validator.

Bond credentials contain `version`, `bond`, `cert_pubkey`, `cert_expiry=p+1`,
`cert_signature`, and `lease`. The certificate uses the existing Bitcoin Signed Message
signature over `fidelity-bond-cert|<raw cert pubkey>|<expiry>`; the legacy
ASCII-public-key variant remains accepted. The owner signs each renter request
offline, while the online seller retains only market and encryption keys.
The renter imports the public metadata and signature alongside its own local
certificate key into the existing external-bond registry.

Legacy certificates have no enforceable activation time, exclusivity, or
revocation. Sellers MUST NOT offer future-period certificates as though they
were unusable now. A contractual one-period rental does not change this fact.
The required `lease` is an owner-signed document with `kind: exclusive-bond-lease`,
`version: 1`, `policy: exclusive-period-v1`, `bond`, `period`, and `cert_pubkey`.
Its bond and hot key MUST match the credential, and its period MUST equal both
the authorization period and `cert_expiry-1`. The policy promises that no other
hot key will represent the bond during that period, including previously issued
certificates still valid then. JMP-0013 defines owner-equivocation evidence and
requires local timely observation before exclusion through the following period.
Ordinary maker proofs carry no lease, market metadata, or rental indicator.
Renter key sharing is not prevented or sanctioned by this policy.
Clients retain outpoint-based maker deduplication and do not count several
renters of one bond as independent maker slots.

### External PoDLE Credentials

The version-1 credential contains `network`, `outpoint: {txid,vout}`, `P`, `P2`,
`sig`, `e`, `commitment`, `index`, `scriptpubkey`, `blockheight`, and `version`.
Points are compressed 33-byte hex, scalars and commitment are 32-byte hex,
`index` is 0 through 255, and confirmation height is positive.
JMP-0012 sales further restrict the index to 0, 1, or 2 for standard maker
compatibility. A signed market delivery outside that range is invalid even when
the underlying portable PoDLE proof is mathematically valid. Nonstandard retry
policies require a different negotiated market version, not an implicit fallback.

Before import, clients verify the proof against precisely its declared NUMS
index and bind `P` to the supplied script. Before use, they independently verify
the backing output's unspent status, authoritative script, height metadata,
confirmations, value threshold, maker-compatible retry index, network, and local
blacklists. Supplied metadata is not chain authority. Neutrino clients use the
existing metadata verification interface and fail closed when unavailable.
Cached address UTXO lists or history are discovery views, not sufficient evidence
for settlement or credential use. A verification result must be consistent with
one active-chain view and bind the exact outpoint to the expected output script;
unavailable verification, stale chain anchors, or a reorganization during the
check must not be interpreted as proof that an output is unspent.

The backing output MUST NOT be added to the CoinJoin funding inputs merely to
authenticate. It is neither imported as a spending key nor reserved as a wallet
input. Consumption is durable before `!fill`, including unsuccessful rounds and
replacement waves. A new replacement authentication wave consumes a new opening.
The reference implementation offers explicit `disabled` and `only` policies;
`only` MUST stop on exhaustion rather than disclose a local wallet-input proof.

NG's local storage keeps `used` and legacy `external` intact and stores these
strict records separately under `external_v1`, keyed by commitment. It does not
claim compatibility with the legacy nested external JSON format. All concurrent
writers to this file must use the new locking protocol; old binaries must not
share this mutable pool concurrently.

### Seller Separation for Purchased Openings

A seller knows the commitment it sold and can recognize it in public `!hp2`
traffic. If that same seller is also a maker in the round that reveals the
opening, it learns directly which CoinJoin its credential authenticated. An
importing client that verified the seller's owner authorization therefore records
that seller's complete bond reference as the record's provenance, beside the
credential in the pool.

A round that may reveal such a record hard-excludes every maker offer that proved
exactly that bond. Matching requires the complete independently verified tuple of
network, outpoint, public key, and locktime; an offer whose bond was not verified,
a different key on the same outpoint, and an outpoint-only match are never
matched, for JMP-0013's reason. The exclusion applies to all selection passes of
the round, including sweep selection and every replacement wave, and it MUST NOT
be a preference that thin liquidity relaxes. Selection happens before any maker
is contacted, and the round then either consumes exactly the previewed record or
none: substituting a different seller's credential after makers were chosen would
silently break the separation the exclusion was based on.

Provenance is a claim, not a clean bill. A record without it is **unknown**, which
is the normal state for credentials imported from a file or stored before this
field existed. Those records keep working exactly as before and are simply not
seller-separated; an absent provenance MUST NOT block use or imply a seller. The
exclusion also cannot reach a seller's other identities: an unbonded nick, a
second bond, or an offer that never proved a bond is indistinguishable from an
unrelated maker, so a seller determined to observe the round can still do so.

A sweep does not know its CoinJoin amount until makers are chosen, so its
eligibility check uses the total input value, a conservative upper bound. This can
reject a credential whose backing output would have satisfied the eventual,
smaller amount; it never admits one that would not.

### Optional Wallet-Native Key Profile

This profile describes the experimental NG wallet capability. It is a local
recovery convention, not a new wire field or a requirement that other market
implementations derive their keys identically. Existing randomly generated
market keys remain interoperable.

Start from the 64-byte binary BIP39 seed, including its passphrase, at the
unlocked wallet boundary. Apply [SLIP-0021](https://github.com/satoshilabs/slips/blob/master/slip-0021.md):
the master node is HMAC-SHA512 with key `Symmetric key seed` and seed as message;
each child is HMAC-SHA512 with the parent's first 32 bytes as key and
`0x00 || label` as message. The first label is the ASCII string
`JoinMarket NG credential market`. It is not a BIP32 child or a hash of a
spending private key.

Each item separated by `/` below is a separate child label, not a slash-delimited
string passed to HMAC:

```text
v1 / network / NETWORK / chain / GENESIS_HASH / role / ROLE / period / PERIOD
   / bond / BOND_LABELS / trade / TRADE_LABELS / purpose / PURPOSE / algorithm / ALGORITHM
```

All labels are ASCII. `NETWORK` is a supported Bitcoin network, `ROLE` is `buyer`
or `seller`, and `PERIOD` is a minimal decimal integer from 0 through 65534.
`GENESIS_HASH` is lowercase 32-byte hexadecimal, never a moving tip hash.
`BOND_LABELS` is `none`, or the three labels `outpoint / TXID / VOUT`, using a
lowercase 32-byte transaction hash and minimal decimal uint32 output index.
`TRADE_LABELS` is `none`, or `id / TRADE_ID`, where the latter is a durable local
32-byte identifier in lowercase hexadecimal. It is not the 16-byte transport
request ID. Period identities can omit the trade; trade-local keys require a
distinct retained trade identifier. Derivation inputs do not themselves verify
chain identity, bond ownership, or eligibility.

Document signing uses purpose `document-signing` and algorithm
`secp256k1-ecdsa-bitcoin-message`, then one additional decimal counter label.
Try counters 0 through 255, taking the last 32 bytes of each child as an unsigned
big-endian scalar. Accept only `0 < scalar < n`, where `n` is the secp256k1 group
order; never reduce modulo `n`. Exhaustion is an error. Public keys are compressed.

Message encryption uses purpose `message-encryption` and algorithm
`x25519-xsalsa20-poly1305-sealedbox`. Use the final node's last 32 bytes as the
NaCl private key input; the library applies X25519 clamping. Decrypted plaintext
remains untrusted and requires the existing market validation.

The wallet retains only the application-specific node for this capability and
exposes public keys, document signing, and bounded sealed-box decryption, not raw
private keys. Wallet close or daemon lock revokes further operations through
retained references. This is an in-process API boundary, not a sandbox or a
guarantee of memory erasure. Buyer acquisition and renter key management remain
file-oriented CLI workflows.

The local ledger identity is SHA256 of the key bytes of the
`wallet-ledger-identity-v1` child of the application node. It is wallet-wide
across roles and networks, distinct from the short wallet fingerprint, and MUST
NOT be published as a market identity. It is not a replacement for trade-local
keys or buyer tags.

For a public derivation vector, use the SLIP-0021 example mnemonic `all` twelve
times with an empty passphrase, network `regtest`, fictitious genesis hash
`11` repeated 32 times, role `buyer`, period `4`, and absent bond and trade:

```text
signing public key:    03a9cbd24b5cf7d1eba3e9b82cb2af5a6a7bda25b49f238475b6ad859ad481bbfd
encryption public key: 4827536a26038dea66e51f7f988b33b4dc3cacf1a275eb60477283617a2f5a18
```

This vector demonstrates derivation only, not a real chain or a safe trade scope.

### Wallet Ledger Activation

The NG store uses schema version 1 with explicit `standalone` or `wallet` ledger
mode. Opening a wallet does not activate the store.
`WalletService.activate_market_ledger(history_confirmed=True)` is a local API,
not a P2P operation; the confirmation is the operator's affirmation of complete
history, not a conclusion drawn from missing files or successful key recovery.

Activation records durable intent beside the SQLite database, selects wallet
mode, binds an exact canonical commitments JSON path, and records
wallet-specific `activating` state before importing history. A successful import
records `ready`; failure leaves `activating` or `recovery_required`. Repeating
activation MUST NOT implicitly resume or reset an interrupted/recovery state.

An absent store or a standalone store remains market-disabled for the
native wallet workflow, preserving existing CoinJoin behavior. A standalone store
with activation intent indicates interrupted activation and MUST fail closed.
Missing or inconsistent wallet intent, metadata, schema, foreign keys, or
inventory/ownership correspondence MUST fail closed rather than rebuild state.

The ledger has one globally unique ownership row per PoDLE commitment hash,
independent of period or role. Market inventory insertion and local claims use
that same SQLite authority. Imported credentials transition from `held_local`
to `used` at attempted use; a held credential is not already spent merely because
it was purchased. Existing ownership survives wallet switches and cannot be
reassigned by importing the shared JSON projection for a different wallet.

Before returning a local proof, the taker commits consumption in SQLite and
then updates its legacy JSON projection. Projection failure may burn a credential,
but MUST NOT release its ledger claim. Selection snapshots are advisory; the final
claim rechecks ownership and readiness. Cross-store operations acquire the JSON
sidecar lock before SQLite and do not hold either lock across chain I/O.

Readiness is wallet-specific. A disabled wallet may continue ordinary CoinJoin
credential use, with its tombstones recorded in the shared ledger, but cannot
sell. An activating or recovery-required wallet cannot issue market credentials
or use local PoDLE. This compatibility rule does not automatically activate a
market role. Only one wallet session is active; concurrent unlocked wallets are
not the runtime model.

When the wallet has an explicit data directory, the NG taker requires its own
data directory to resolve to the same canonical location, including before
activation. This prevents a running taker from missing a subsequently activated
wallet ledger. Existing callers using different directories must align their
configuration; the implementation does not move history or rescan automatically.

The unbound file-oriented seller CLI intentionally refuses writes and serving
against an activated ledger. Inspection and finalized-package export remain
available. Activation does not start a native seller or initiate payments.

### Current NG Wallet-Native Operations

This subsection records experimental NG implementation status. Its local wallet
and daemon interfaces do not define additional P2P messages, wire fields, or
signature formats beyond this draft.

The wallet-native seller derives a revocable market-key capability from the
unlocked wallet, bound to its chain, role, period, and bond context. It signs
canonical market documents and decrypts market messages without exporting a
spending key. At startup, it accepts only a bond already in the wallet's cached
mixdepth-0 state whose canonical key, address, and script match the requested
outpoint. It also verifies the backend genesis, height, median time, confirmation
state, unspent value, and locktime. The wallet signs a delegated renter bond
certificate internally before finalization; the bond spending key remains in the
wallet.

The unlocked wallet's authenticated daemon API can inspect ledger state; start,
inspect, and stop the seller; add inventory and externally generated payment
terms; inspect pending quotes; and locally settle a quote. It rechecks
authentication after acquiring the wallet lifecycle lock. Settlement requires an
explicit local Lightning settlement acknowledgment and does
not send or automatically confirm payments. A native seller may run alongside
ordinary CoinJoin activity in the single unlocked wallet session.

Ledger activation is explicit. The daemon can diagnose state without creating or
repairing artifacts, recover confirmed history only into an intact wallet-mode
ledger, and rebind an intact moved ledger only with explicit history and
writer-stopped confirmations. Rebinding records a durable transition before it
changes bindings or merges history. Unknown, missing, inconsistent, or
recovery-required state is never automatically reset into a usable ledger. The
market capability added during wallet-service construction and read-only ledger-path
resolution do not activate a market ledger, migrate market state, or trigger wallet
sync or rescans. Recovery cannot reconstruct missing authoritative allocation
or consumption history, and a complete valid offline rollback of both the
database and its intent remains inherently undetectable from local artifacts.

Native direct onion-service hosting and automatic seller restart for a new period
are not implemented. Buyer acquisition and renter key management remain CLI-only.

## Rationale and Incentives

Rental income compensates the owner for foregoing maker income and taking
market-key and renter conduct risk. Renters compare rental price with expected
maker income and the benefit of rotating bond associations. Opportunity cost is
not a protocol-enforced price floor. Rental can reduce an attacker's custody and
coordination costs even though distinct bonded slots still require distinct
outpoints. The market is therefore experimental, not a claim of stronger Sybil
resistance than custody-based participation.

PoDLE prices compensate for inventory, monitoring, invalidation risk, payment
cost, and privacy leakage. One backing key/output can support only the configured
NUMS retries, but a market can make access cheaper. One opening can still probe
many makers concurrently. Neither pricing, receipt accountability, nor `!hp2`
gossip solves issue #47. Maker-specific upfront fees or a different coordination
protocol would be separate changes.

Onchain micropayments can cost more than the goods, which is why new operations
are Lightning-only. Users can pay for credentials
ahead of need, but buying correlated openings from one backing key/output can
let colluding makers cluster them. This version does not encourage automatic
large bundles or silently choose the cheapest provider. A provider knows its
sold commitment and can correlate it with public `!hp2` timing; LN does not erase
this information or conceal every routing/endpoint relationship.

## Security Considerations

Services bound message sizes, pending requests, discovery results, caches, work
queues, and quote reservations. The reference uses at most 64 concurrent work
items, 256 listings, 256 cached transport responses, and 64 live seller quotes.
It admits at most one new quote per second globally. These are resource bounds,
not Sybil resistance. Anonymous clients can still repeatedly reserve scarce
inventory or exhaust a manually populated invoice queue. Operators must price
and limit exposure, choose reservation lifetimes, and replenish stock. Expired
reservation metadata and
payment tombstones require protected storage and operational capacity planning.

No public seller endpoint is fetched for UTXO or payment verification. There is
no automatic refund, automatic payment, arbitrary webhook execution, or payment
node credential in the protocol. Secret state files are owner-only and writes
are atomic. Restoring an old database backup can defeat local one-time sale
protection, so operators must not resume issuance from stale inventory state.

Seed recovery restores deterministic keys, not allocation or consumption history.
Missing, partial, unsupported-version, corrupt, or known-restored ledger state
MUST NOT automatically enable wallet-native issuance. A schema/version marker or
valid backup signature alone does not prove that a backup contains all subsequent
consumption tombstones. A running manager refuses known database replacement
or missing artifacts persistently. Complete consistent rollback of both database
and intent while no manager is running cannot be detected from these local
artifacts alone. Known-restored ledgers must require recovery; no automatic
reconciliation is implemented. Older binaries must not write an activated ledger
or its JSON projection concurrently. Key derivation alone does not prevent reuse.

## Backward Compatibility

Legacy directories can relay these commands without understanding the market.
Legacy peers ignore them and do not enforce JMP-0013 sanctions. CoinJoin proof
messages and their cryptographic validation remain unchanged. Upgraded clients
must not interpret market support as global agreement or guaranteed delivery of
fault gossip. The market is disabled unless explicitly invoked; external-only
taker policy is separately opt-in.

## Reference Implementation

The experimental ring market branch of
[joinmarket-ng](https://github.com/joinmarket-ng/joinmarket-ng) implements
`jm-market`, the external PoDLE pool, and fault filtering. The market does not
depend on channel rings or buyouts.

The branch also includes read-only watcher views separating CoinJoin, PoDLE,
and bond-rental advertisements. Its additive `credential_market` orderbook JSON
field is a local watcher API, not a new P2P command. The watcher sends one
`mbook` per directory connection and maintains bounded, expiring listing
state without activating a buyer or seller. Wallet-native key operations are
implemented in `jmcore.market_keys`, constructed by `WalletService` from the
BIP39 seed and revoked by wallet close or daemon lock. These additions do not
by themselves start market services, create or migrate a ledger, alter spending
derivation, or trigger rescans when an existing installation upgrades. The same
worktree implements the explicit authenticated wallet-native seller operations
described above; they are a local daemon interface, not additional wire
implementation.

The durable seller store is shared through `jmcore.market_store`. Wallet-mode
ownership and readiness are enforced by the shared store and taker's
`PoDLEManager`; its wallet identity is derived inside `WalletService`. The taker
closes its cached ledger handle on shutdown. No migration or compatibility alias
for earlier unpublished market formats is provided. Ordinary wallet and PoDLE
history protections remain in force.

The worktree accepts only Lightning payment documents, writes a per-request
buyer key bundle beside each persisted request, and applies seller separation
from recorded pool provenance across initial, sweep, and replacement selection.
Bond credentials require owner-signed exclusive leases. Renter-signed conflict
reports require the local corroboration described in JMP-0013.
