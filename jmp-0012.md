# JMP-0012: Credential Market

## Abstract

This opt-in market exchanges externally generated PoDLE openings and delegated
fidelity-bond certificates. Discovery uses existing JoinMarket directories.
Trades prefer direct onion connections and fall back to end-to-end encrypted
directory relay. Payments use externally managed BOLT11 invoices or confirmed
Bitcoin outputs; no Lightning node integration, escrow, spending authority, or
atomic fair exchange is assumed. A separately authorized fidelity bond makes
specific seller-signed contradictions accountable under [JMP-0013](jmp-0013.md).

## Motivation

An external PoDLE opening lets a taker authenticate without disclosing one of
its actual CoinJoin inputs to participating makers. Delegation lets a maker use
a fidelity bond without custody of its spending key. Neither primitive requires
a change to legacy CoinJoin authentication or fidelity-bond proof messages.

Privacy takes precedence over market efficiency. The market MUST NOT publish
buyer histories, payment receipts, invoice hashes, PoDLE openings, or renter
certificate private keys as listings. Users SHOULD acquire credentials separately
from their CoinJoin sessions, use fresh buyer keys and Tor identities per trade,
and avoid paying from coins belonging to the forthcoming CoinJoin.

## Specification

### Roles and Trust

* The bond owner authorizes a distinct market signing key for a specified period.
* The seller holds this market key, inventory, and payment requests, but need not
  hold the bond spending key. Its market encryption key is a separate X25519 key.
* The buyer generates its delivery encryption key locally. A bond renter also
  generates its own secp256k1 certificate key, never sending the private key.
* Payment wallets remain external. An explicit local seller acknowledgment, not
  an untrusted remote payment claim, initiates finalization.

A valid authorization establishes responsibility, not the existence or value of
collateral. Before paying, the buyer MUST independently verify the bond outpoint,
its positive confirmed unspent value, and its reconstructed CLTV P2WSH script
against its configured Bitcoin backend. The locktime MUST still be in the future.
The messaging network and Bitcoin network MUST be treated separately; for
example, an existing testnet messaging directory may serve regtest clients.

The buyer MUST set a maximum price and explicitly accept seller risk. The seller
can withhold delivery after payment. A signed quote, Lightning preimage, or
onchain payment does not eliminate this risk. Timeouts MUST NOT be classified as
cheating evidence. A provider can also spend a PoDLE backing output before use.

### Encoding and Signatures

Market JSON uses ASCII strings, exact integers with absolute value at most
`2^53-1`, booleans, null, objects, and arrays. Duplicate object keys, floating
point values, unknown schema fields, unsupported versions, and nesting beyond
12 levels MUST be rejected. Documents are at most 16,384 bytes before transport
encoding. Canonical encoding sorts object keys, has no insignificant whitespace,
and uses JSON string escaping. Hex fields are lowercase with fixed byte lengths.

A signed document is `{"body": <object>, "signature": <DER-hex>}`. The signature
is strict low-S secp256k1 ECDSA over the Bitcoin Signed Message hash of:

```text
JMP-MARKET-V1|<canonical JSON body bytes>
```

Each body includes integer `version: 1` and a domain-specific `kind`. A document
identifier is SHA256 of canonical JSON bytes. References to authorizations and
allocations hash their **body**, excluding the signature, to avoid treating a
different valid ECDSA signature as a different contract.

`bond` is an object containing `network`, `outpoint: {txid,vout}`, `pubkey`
(compressed, 33 bytes), and `locktime` (uint32 Unix timestamp). Network values are
`mainnet`, `testnet`, `signet`, and `regtest`.

### Periods and Owner Authorization

To match inclusive legacy certificate expiry, period `p` covers heights
`2016*p+1` through `2016*(p+1)`, inclusive. At a positive chain height `h`, use
`floor((h-1)/2016)`. This differs from floor(h/2016) at the boundary block.

The bond owner signs this authorization body:

```json
{
  "kind": "authorization",
  "version": 1,
  "policy": "signed-faults-v1",
  "bond": {"network": "regtest", "outpoint": {"txid": "<32-byte hex>", "vout": 0}, "pubkey": "<33-byte hex>", "locktime": 2000000000},
  "period": 1,
  "seller_pubkey": "<33-byte hex>"
}
```

Placeholders in examples are explanatory and are not valid wire records.
Signing this domain explicitly accepts JMP-0013 sanctions. A legacy bond
certificate, nick signature, or rental certificate MUST NOT authorize a market
key or sanctions. An owner SHOULD use a different market key for each period.
Changing market keys does not permit duplicate allocations of the same resource.

### Native Transport

The following commands use existing JMP-0001 routing and authenticated private
message envelopes. Commands MUST be matched by complete token, not prefix.

| Command | Channel | Payload |
|---------|---------|---------|
| `mbook` | Public | Empty discovery request |
| `moffer` | Public | Signed JM envelope containing base64 of a signed listing |
| `mrequest` | Private | Signed JM envelope containing base64 sealed ciphertext |
| `mresponse` | Private | Signed JM envelope containing base64 sealed ciphertext |
| `mproof` | Public | Base64 canonical JMP-0013 proof |

The ordinary JM envelope signature uses `onion-network` on both direct and relay
paths. Listing bodies contain `kind: listing`, `version`, Bitcoin `network`,
`period`, `seller_pubkey`, `encryption_pubkey`, `products` (one or both of
`podle`, `bond`), indicative `price_sats`, and Unix `expires_at`. Listings contain
neither bond outpoints nor buyer information. They expire after 60 seconds in the
reference implementation; clients reject lifetimes exceeding 120 seconds.
Listings are at most 2,048 bytes. Listing signatures prove key continuity, not
stake ownership. Stake is disclosed only in the private quote.

Before a request, the buyer obtains the seller location from existing peer
discovery, tries its direct onion connection, and falls back to one connected
directory. Production clearnet fallback is forbidden unless an explicit
development setting enables it. No HTTP seller endpoint or public invoice
directory is introduced.

Requests use libsodium SealedBox to the advertised seller X25519 key. Their
plaintext contains `request_id` (random 16-byte hex), `reply_pubkey` (base64
ephemeral X25519 key), and `body`. Replies use SealedBox to this reply key and
contain the same `request_id` and a response `body`. All underlying private
envelopes remain JM-signed. The same ciphertext and transport request ID are
reused on direct-to-relay retry. Decryption alone does not authenticate a sender.

The inner quote request contains `action: quote`, its own durable random
`request_id` (16-byte hex), `buyer_pubkey` (32-byte hex), `product`,
`certificate_pubkey` (null for PoDLE), `rail`, and `max_price_sats`.
The buyer key in this request is the persistent **trade-local** delivery key,
not the per-call transport reply key. A delivery request contains only
`action: delivery` and `quote_id`; its reply contains a sealed delivery or null.
There is no remotely accessible settlement command.

### Quotes and Payment

A seller-signed quote body contains `kind: quote`, `version`, the complete signed
`authorization`, random 32-byte `quote_id`, `buyer_pubkey`, `product`, `resource`,
`certificate_pubkey`, `payment`, `created_at`, and `expires_at`.

`resource` is the PoDLE commitment hash, or, for a bond rental, SHA256 of canonical
`{"bond": <bond reference>, "period": p}`. A rental quote MUST name the renter's
certificate public key. A buyer MUST verify every request binding, the seller
signature, owner authorization, current chain period, amount cap, payment rail,
and payment request before displaying an actionable payment URI.

`payment` contains `rail`, `request`, `amount_sats`, and `min_confirmations`:

* `onchain`: `request` is a network-checked Bitcoin address. Settlement identifies
  an exact `txid:vout` with the specified script and exact satoshi amount, unspent
  and at least `min_confirmations` deep according to the seller backend. A txid
  alone is insufficient. At least one confirmation is required.
* `lightning`: `request` is a valid signed BOLT11 invoice with an exact amount of
  `amount_sats*1000` millisatoshis, the appropriate network prefix, and expiration
  no earlier than the quote. Amountless invoices and ambiguous singleton tags
  are rejected. BOLT11 uses `lntb` for both testnet and signet, so it cannot by
  itself distinguish those two networks. Unknown mandatory features are rejected.

Lightning quote lifetimes are at most 900 seconds. Onchain lifetimes may be up
to 86,400 seconds; the seller chooses a window suitable for its required
confirmations and availability. A quote is valid only when
`created_at <= now < expires_at`. The seller MUST NOT reassign its invoice or
payment address to another quote after expiration. Late, replaced, reorganized,
underpaid, or spent settlement outputs require manual reconciliation, not
automatic delivery to whichever buyer first submits a public transaction ID.

A Lightning preimage MUST be exactly 32 bytes and hash to the invoice payment
hash. It is not proof of payer identity or of actual settlement, since the payee
already knows it. The reference seller requires explicit local confirmation of
wallet settlement before finalizing. Future wallet adapters must preserve this
trust boundary and invoice uniqueness; none are specified here.

### Final Allocation and Delivery

Quotes are revocable reservations, not finalized allocations. On accepted local
settlement, the seller atomically commits inventory consumption, unique payment
reference consumption, an allocation receipt, and the sealed delivery. The
transaction MUST be durable before returning any finalized receipt. Repeated
requests for the same trade return the original records. A different request
cannot receive the same inventory, including after restart or concurrent access.

An allocation body contains `kind: allocation`, `version`, `authorization`
(authorization body hash), `allocation_id` (quote ID), `buyer_tag` (SHA256 of the
buyer's X25519 public key bytes), `product`, `resource`, and
`certificate_pubkey`. It has no invoice, payment amount, or settlement reference.

A delivery body contains `kind: delivery`, `version`, `allocation` (allocation
body hash), and `credential` (object). Both bodies are seller-signed. The package
is `{"authorization": <signed>, "allocation": <signed>, "delivery": <signed>}`,
sealed to the quote's buyer key. Even a caller knowing the quote ID or payment
outpoint receives only this buyer-sealed package. The buyer retains original
signed bytes before rejecting an invalid delivered credential, so evidence is
not discarded by an import validator.

Bond credentials contain `version`, `bond`, `cert_pubkey`, `cert_expiry=p+1`, and
`cert_signature`. The certificate uses the existing Bitcoin Signed Message
signature over `fidelity-bond-cert|<raw cert pubkey>|<expiry>`; the legacy
ASCII-public-key variant remains accepted. The owner signs each renter request
offline, while the online seller retains only market and encryption keys.
The renter imports the public metadata and signature alongside its own local
certificate key into the existing external-bond registry.

Legacy certificates have no enforceable activation time, exclusivity, or
revocation. Sellers MUST NOT offer future-period certificates as though they
were unusable now. A contractual one-period rental does not change this fact.
Clients retain outpoint-based maker deduplication and do not count several
renters of one bond as independent maker slots.

### External PoDLE Credentials

The version-1 credential contains `network`, `outpoint: {txid,vout}`, `P`, `P2`,
`sig`, `e`, `commitment`, `index`, `scriptpubkey`, `blockheight`, and `version`.
Points are compressed 33-byte hex, scalars and commitment are 32-byte hex,
`index` is 0 through 255, and confirmation height is positive.
JMP-0012 sales further restrict the index to 0, 1, or 2 for standard maker
compatibility. A signed market delivery outside that range is invalid even when
the underlying portable PoDLE proof is mathematically valid. Nonstandard retry
policies require a different negotiated market version, not an implicit fallback.

Before import, clients verify the proof against precisely its declared NUMS
index and bind `P` to the supplied script. Before use, they independently verify
the backing output's unspent status, authoritative script, height metadata,
confirmations, value threshold, maker-compatible retry index, network, and local
blacklists. Supplied metadata is not chain authority. Neutrino clients use the
existing metadata verification interface and fail closed when unavailable.

The backing output MUST NOT be added to the CoinJoin funding inputs merely to
authenticate. It is neither imported as a spending key nor reserved as a wallet
input. Consumption is durable before `!fill`, including unsuccessful rounds and
replacement waves. A new replacement authentication wave consumes a new opening.
The reference implementation offers explicit `disabled` and `only` policies;
`only` MUST stop on exhaustion rather than disclose a local wallet-input proof.

NG's local storage keeps `used` and legacy `external` intact and stores these
strict records separately under `external_v1`, keyed by commitment. It does not
claim compatibility with the legacy nested external JSON format. All concurrent
writers to this file must use the new locking protocol; old binaries must not
share this mutable pool concurrently.

## Rationale and Incentives

Rental income compensates the owner for foregoing maker income and taking
market-key and renter conduct risk. Renters compare rental price with expected
maker income and the benefit of rotating bond associations. Opportunity cost is
not a protocol-enforced price floor. Rental can reduce an attacker's custody and
coordination costs even though distinct bonded slots still require distinct
outpoints. The market is therefore experimental, not a claim of stronger Sybil
resistance than custody-based participation.

PoDLE prices compensate for inventory, monitoring, invalidation risk, payment
cost, and privacy leakage. One backing key/output can support only the configured
NUMS retries, but a market can make access cheaper. One opening can still probe
many makers concurrently. Neither pricing, receipt accountability, nor `!hp2`
gossip solves issue #47. Maker-specific upfront fees or a different coordination
protocol would be separate changes.

Onchain micropayments may cost more than the goods. Users can pay for credentials
ahead of need, but buying correlated openings from one backing key/output can
let colluding makers cluster them. This version does not encourage automatic
large bundles or silently choose the cheapest provider. A provider knows its
sold commitment and can correlate it with public `!hp2` timing; LN does not erase
this information or conceal every routing/endpoint relationship.

## Security Considerations

Services bound message sizes, pending requests, discovery results, caches, work
queues, and quote reservations. The reference uses at most 64 concurrent work
items, 256 listings, 256 cached transport responses, and 64 live seller quotes.
It admits at most one new quote per second globally. These are resource bounds,
not Sybil resistance. Anonymous clients can still repeatedly reserve scarce
inventory or exhaust a manually populated invoice queue. Operators must price
and limit exposure, choose reservation lifetimes, and replenish stock; longer
onchain holds worsen this griefing tradeoff. Expired reservation metadata and
payment tombstones require protected storage and operational capacity planning.

No public seller endpoint is fetched for UTXO or payment verification. There is
no automatic refund, automatic payment, arbitrary webhook execution, or payment
node credential in the protocol. Secret state files are owner-only and writes
are atomic. Restoring an old database backup can defeat local one-time sale
protection, so operators must not resume issuance from stale inventory state.

## Backward Compatibility

Legacy directories can relay these commands without understanding the market.
Legacy peers ignore them and do not enforce JMP-0013 sanctions. CoinJoin proof
messages and their cryptographic validation remain unchanged. Upgraded clients
must not interpret market support as global agreement or guaranteed delivery of
fault gossip. The market is disabled unless explicitly invoked; external-only
taker policy is separately opt-in.
