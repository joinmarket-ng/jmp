## Abstract

This specification defines the `ping` feature flag and the application-level
PING/PONG heartbeat mechanism for detecting stale connections between directory
servers and their peers. It enables directory servers to identify and evict
unresponsive peers that hold TCP connections open through Tor without actually
being reachable.

## Motivation

JoinMarket peers communicate over Tor onion services. Tor's TCP proxy model
can keep connections open indefinitely even when the remote peer has crashed,
lost network connectivity, or become unresponsive. The TCP keepalive mechanism
is insufficient because:

1. Tor relays buffer data and may acknowledge TCP segments even when the
   circuit is broken
2. Default TCP keepalive timers are too long (typically 2 hours) for a
   real-time trading protocol
3. Tor circuit failures may not propagate TCP RST to the local endpoint

Without application-level liveness detection, the directory server's peerlist
accumulates stale entries. Takers waste time attempting to connect to
unreachable makers and may fail to complete CoinJoin transactions.

## Specification

### Feature Advertisement

Peers that support the PING/PONG heartbeat advertise `ping` in their handshake
`features` dict:

```json
{"features": {"ping": true}}
```

A directory server SHOULD advertise `ping` in its DN_HANDSHAKE response. A
client (maker or taker) SHOULD advertise `ping` in its HANDSHAKE request if it
can respond to PING messages.

### Message Format

**PING (type 797)**

Sent by the directory server to probe a peer. The `line` field is empty:

```json
{"type": 797, "line": ""}
```

**PONG (type 799)**

Sent by the peer in response to a PING. The `line` field is empty:

```json
{"type": 799, "line": ""}
```

A peer MUST respond to a PING with a PONG as quickly as possible. No
additional processing or delay should occur between receiving a PING and
sending a PONG.

### Heartbeat Algorithm

The directory server runs a periodic heartbeat sweep. The algorithm has three
steps:

#### Step 1: Hard Eviction

Peers that have been idle (no messages sent or received) for longer than
`hard_evict_threshold` are disconnected immediately without a probe. This
catches peers that have been silent for an extended period regardless of
whether they support PING.

#### Step 2: Idle Probing

Peers that have been idle for longer than `idle_probe_threshold` but less than
`hard_evict_threshold` are probed based on their capabilities:

- **Ping-capable peers**: The directory sends a PING (797) message and marks
  the peer as having a pending PONG.
- **Non-ping makers**: The directory sends a unicast `!orderbook` request
  (as a PUBMSG, type 687) to elicit an offer re-announcement. When the maker
  responds with its offers, the directory updates the peer's `last_seen`
  timestamp, keeping it alive. The offer content itself is discarded by the
  directory.
- **Non-ping takers**: No probe is sent. These peers will be hard-evicted
  after `hard_evict_threshold` if they remain silent.

#### Step 3: PONG Collection

After sending PINGs, the directory waits for `pong_wait` seconds. Peers that
were sent a PING but did not respond with a PONG within this window are
evicted.

### Activity Tracking

Every message received from a peer (of any type) updates that peer's
`last_seen` timestamp. This means that active peers -- those sending offers,
processing CoinJoins, or otherwise communicating -- are never probed.

### Timing Parameters

The following timing parameters are used. Implementations SHOULD use these
defaults for interoperability with [joinmarket-rs](https://github.com/joinmarket-rs/joinmarket-rs):

| Parameter | Default | Description |
|-----------|---------|-------------|
| `sweep_interval` | 60s | How often the heartbeat sweep runs |
| `idle_probe_threshold` | 600s (10 min) | Idle duration before probing |
| `hard_evict_threshold` | 1500s (25 min) | Idle duration before unconditional eviction |
| `pong_wait` | 30s | Time to wait for PONG after sending PING |

These values are chosen to balance responsiveness with tolerance for Tor
latency:

- A maker that disconnects cleanly and reconnects within 10 minutes is never
  probed.
- A Tor circuit disruption is detected within ~11 minutes (10 min idle + up
  to 60s until next sweep + 30s pong wait).
- The 25-minute hard eviction catches peers that never responded to any probe
  type.

### Rate Limiting

Directory servers SHOULD rate-limit GETPEERLIST requests. [joinmarket-rs](https://github.com/joinmarket-rs/joinmarket-rs)
enforces a maximum of 3 GETPEERLIST requests per minute per peer, disconnecting
peers that exceed this limit.

## Rationale

### Why not rely on TCP keepalive?

TCP keepalive operates at the transport layer and is proxied by Tor. A Tor
relay may acknowledge TCP keepalive probes on behalf of a disconnected peer,
masking the failure. Application-level probing sends data through the full Tor
circuit, providing true end-to-end liveness verification.

### Why the `!orderbook` fallback for non-ping peers?

The reference implementation (joinmarket-clientserver) defines PING/PONG
message types but does not process them. Sending a PING to a legacy client
would produce no response, making it impossible to distinguish "alive but not
ping-capable" from "dead." The `!orderbook` probe leverages existing behavior
-- makers always respond to `!orderbook` with their offers. If the offers
arrive, the peer is alive. This probe only works for makers (takers do not
respond to `!orderbook`).

### Why separate idle and hard-evict thresholds?

The two-tier approach handles different failure modes:

- **Idle probe threshold** (10 min): Catches peers that are connected but have
  stopped communicating (e.g., process hang, Tor circuit degradation).
- **Hard evict threshold** (25 min): Catches peers where the probe itself
  failed to deliver (e.g., fully broken Tor circuit where neither the probe
  nor any response can traverse).

### Why is PING unidirectional (DN -> peer)?

Only directory servers need to manage a peerlist and detect stale connections.
Clients detect directory failures through the absence of expected responses
(e.g., no DN_HANDSHAKE, no PEERLIST) and reconnect. Adding client-initiated
PING would increase protocol complexity without meaningful benefit.

## Backward Compatibility

- The reference implementation (joinmarket-clientserver) defines PING (797) and
  PONG (799) in its message type constants but does not send or handle them.
  Receiving a PING will cause the message to be silently dropped (unrecognized
  control message). The directory falls back to `!orderbook` probing for these
  peers.
- [joinmarket-rs](https://github.com/joinmarket-rs/joinmarket-rs) fully implements this specification as the origin of the
  heartbeat design.
- [joinmarket-ng](https://github.com/joinmarket-ng/joinmarket-ng) implements both the directory-side heartbeat sweep and the
  client-side PONG response.
- Note: Message type code 797 collides with the local-only CONNECT_IN code in
  joinmarket-clientserver. This is safe because CONNECT_IN is never sent over
  the wire and PING is only sent over the wire.

## Security Considerations

- **PING flooding**: A malicious peer could send many PONG messages. Since PONG
  only clears a boolean flag, this has minimal cost. Directory servers SHOULD
  ignore unsolicited PONG messages (those received when no PING is pending).
- **Probe suppression**: A malicious peer could send minimal traffic to keep
  `last_seen` fresh without actually being a functional participant. This is
  not addressed by the heartbeat mechanism -- it is a general protocol concern.
