## Abstract

This specification defines the `tr0` CoinJoin pit. It adds Taproot order types,
requires P2TR equal and change outputs, defines Taproot PoDLE key binding, and
defines the key-path signature format used by tr0 transactions.

## Motivation

P2TR outputs give a CoinJoin a uniform contemporary output form and let wallets
receive and later spend Taproot coins without changing pits. They also provide a
common basis for future coordinated MuSig2, PTLC, and swap constructions. A
separate pit lets takers select makers with this policy without changing the
meaning of existing offer types.

## Specification

### Offer Types

The following JMP-0001 public offer grammars are added:

```text
tr0reloffer = "!tr0reloffer" SP oid SP minsize SP maxsize SP txfee SP relfee
tr0absoffer = "!tr0absoffer" SP oid SP minsize SP maxsize SP txfee SP absfee
```

`oid`, `minsize`, `maxsize`, and `txfee` have the same grammar and semantics as
JMP-0001 offers. `relfee` is the JMP-0001 relative `cjfee`; `absfee` is the
JMP-0001 absolute `cjfee` in satoshis. A maker MUST use a distinct `oid` for
each live offer. For example:

```text
!tr0reloffer 7 50000 10000000 0 0.00025
```

A taker selects only `tr0` offers for a tr0 CoinJoin. A maker MUST NOT accept a
`!fill` for a `tr0` offer unless it can meet every requirement in this document.

### Output Policy

Every participant MUST provide its own equal output and, when it has change,
its own change output as a native SegWit v1 P2TR output:
`OP_1 <32-byte program>`. Every participant MUST verify that every output of the
transaction is P2TR before signing and MUST reject a transaction with any other
output script type.

All equal outputs MUST have the negotiated CoinJoin amount. Their common P2TR
script family is part of the tr0 anonymity-set policy. Change is distinguishable
by amount but is also P2TR to avoid a second output-script family.

### Input Policy

Every input of a tr0 transaction MUST be a native SegWit v1 P2TR output spent
through the key path. A participant MUST NOT contribute any other script type,
and every participant MUST reject a transaction containing a non-P2TR input or a
script-path witness before signing. The tr0 pit therefore never mixes with the
`sw0` pit at the input side either: a wallet that holds both families accounts
for them separately and offers only its P2TR liquidity in tr0.

Input uniformity is a pit-wide privacy policy rather than a consensus
condition. It keeps one input script family and one witness shape (exactly one
64-byte signature), so that constructions whose funding output is a P2TR
key-path spend by more than one party, such as Taproot Lightning channel
funding outputs, are indistinguishable from BIP86 single-signer inputs within
the pit.

### Fidelity Bonds

Fidelity bonds are not transaction inputs, so the input policy does not apply
to them. tr0 defines no Taproot fidelity bond. A tr0 maker proves its bond with
the existing P2WSH timelocked bond and `!tbond` proof unchanged, and a wallet
SHOULD derive it on the same path as for `sw0` (BIP84 `m/84'/coin'/0'/2/timenumber`)
so one bond weights the maker's offers in both pits. A Taproot bond would be a
new standard with its own script-path and verification risks for no clear
privacy benefit, and is left to a future proposal.

### Taproot PoDLE Binding

For a BIP86 P2TR UTXO, let `s` be the internal private scalar and `P = sG` its
internal public point. The prover MUST first apply BIP341 internal-key parity
normalization:

```text
d = s                 if has_even_y(P)
    n - s             otherwise
P_even = dG
t = int(tagged_hash("TapTweak", x(P_even))) mod n
q = (d + t) mod n
Q = qG
e = q                 if has_even_y(Q)
    n - q             otherwise
```

`n` is the secp256k1 group order and `x()` is the 32-byte x-only encoding. The
prover MUST use `e`, not `s`, `d`, or unnormalized `q`, as the secret key in the
JMP-0001 PoDLE construction. This separately normalizes the output-key parity
for the PoDLE key relation.

The verifier MUST require that the claimed UTXO scriptPubKey is exactly
`OP_1 <32-byte program>` and that its program equals `x(Q)`, where `Q = eG`.
It MUST also verify the ordinary PoDLE proof. A proof failing either check is
invalid. The TapTweak input has no Merkle root; tr0 PoDLE is for BIP86 key-path
outputs only.

The commitment sent in `!fill` retains the existing PoDLE representation: the
ASCII prefix `P` followed by lowercase `hex(SHA256(P2))`, where `P2` is the
second 33-byte compressed proof point derived from `e`. The same value is used
by commitment blacklists and `!hp2`; tr0 introduces no new commitment prefix.

### Transaction Signing

Before signing a P2TR input, a participant MUST have the exact prevout amount
and scriptPubKey for every transaction input, including counterparty inputs.
BIP341 key-path sighashes commit to this full prevout set. A participant MUST
verify the transaction outputs, fee, and all input prevouts before signing.

After JMP-0001 encryption is removed, the exact `!sig` plaintext is:

```text
!sig <base64(0x40 || signature[64] || 0x20 || output_key[32])>
```

The argument is RFC 4648 Base64 encoding of a one-byte signature length, the
signature, a one-byte public-key length, and the 32-byte x-only output key. The
length bytes MUST be `0x40` and `0x20`. The output key identifies candidate
inputs and MUST equal the matched input's P2TR witness program. When the same
key appears more than once, the receiver MUST verify the signature against each
unmatched sender input rather than assume a unique key-to-input mapping. The
output key is not placed in the witness. The signature has no sighash byte and
MUST verify under BIP341 `SIGHASH_DEFAULT`. The corresponding final witness is
exactly:

```text
[<64-byte BIP340 signature>]
```

A tr0 implementation MUST reject every 65-byte signature form, including one
with a trailing `0x00`; it MUST reject any non-default sighash type. It MUST
also reject an annex. In the final transaction a tr0 P2TR key-path witness MUST
have exactly the one signature item above, so an extra item beginning with
`0x50` or any other extra item is invalid under this pit policy.

This encoding applies to every tr0 input, because every tr0 input is a P2TR
key-path spend. The JMP-0001 `sw0` signature encoding never appears in a tr0
round.

### Fee Sizing

Fee calculation MUST use the actual transaction serialization and actual input
and output script types. A P2TR key-path input with the required witness weighs
230 weight units (57.5 vbytes), and a P2TR output weighs 172 weight units
(43 vbytes). Implementations MUST include transaction overhead and every input
and output when calculating the final vsize; they MUST NOT apply a P2WPKH-only
estimate to a tr0 transaction.

### Liquidity Pools

A maker MAY publish both tr0 and another pit's offers. It MUST account for
available liquidity separately by script family. In particular, the liquidity
advertised for tr0 MUST be calculated from P2TR liquidity, and it MUST NOT
count the same UTXO toward both tr0 and another pit's available amount. A maker
MUST update or cancel affected offers when a reserved UTXO changes availability.

## Backward Compatibility

Implementations that do not recognize `tr0reloffer` or `tr0absoffer` ignore
them and cannot participate in tr0 CoinJoins. A dual-pit maker can continue to
publish existing offers with separate order IDs and pools. The existing offer,
encryption, `!fill`, `!ioauth`, and transaction flow from JMP-0001 are otherwise
unchanged.

## Rationale

Dedicated order types make pit selection visible in the orderbook and avoid
overloading existing `sw0` semantics. Requiring P2TR key-path spends for every
input and P2TR for every output keeps one script family and one witness shape
on both sides of the transaction. Bitcoin consensus does not require this
uniformity; the pit requires it so that later extensions can hide cooperative
spends inside ordinary-looking rounds. Fixed default-sighash signatures avoid
alternate witness encodings and make the signed transaction policy unambiguous.

## Security Considerations

The two parity normalizations in Taproot derivation are required: omitting the
internal-key step gives the wrong tweak, and omitting the output-key step binds
PoDLE to the wrong secret relation. Verifiers must check both the PoDLE proof
and the exact P2TR scriptPubKey binding.

All-prevout validation is critical because BIP341 commits to every input amount
and scriptPubKey. A participant that signs without verified prevout data can be
tricked into authorizing a different transaction. Enforcing one 64-byte witness
and rejecting annexes prevents sighash ambiguity and unreviewed witness data.

Input and output uniformity is a privacy property rather than a consensus
property. A single divergent script or witness in a round tags that round, so
implementations must reject divergence before signing rather than tolerate it.
