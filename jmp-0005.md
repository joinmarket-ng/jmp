## Abstract

This specification defines `nick_auth`, an optional handshake extension
that lets a client prove ownership of its JoinMarket nick before a directory
registers it. It also defines safe duplicate-nick and connection-cleanup rules
for both authenticated and legacy clients.

## Motivation

JMP-0001 nicks are derived from a public key, and private messages are signed
with that key. The initial directory handshake, however, does not prove that
the connecting client owns the nick it claims.

A directory that accepts the handshake nick on trust can let an attacker
replace another peer's routing entry. The attacker can then redirect or drop
CoinJoin messages, make a maker unreachable, and observe routed metadata. A
stale disconnect can also remove a newer connection if cleanup is performed by
nick alone.

Existing message signatures and transaction validation prevent the attacker
from signing as the victim or directly stealing funds. This extension addresses
routing hijack, targeted denial of service, and stale registry cleanup.

## Specification

### Feature Negotiation

Clients and directories advertise support in their JMP-0001 handshake:

```json
{"features":{"nick_auth":true}}
```

The extension is negotiated only when both sides advertise the JSON boolean
`true`. A directory MUST NOT send authentication messages to a client that did
not advertise the feature.

Implementations SHOULD support these modes:

| Mode | Behavior |
|------|----------|
| `prefer_verified` | Authenticate upgraded peers and accept other peers as legacy. This is the default. |
| `require_verified` | Reject peers that cannot authenticate. |
| `disabled` | Do not negotiate authentication. Nick collision and connection-qualified cleanup rules still apply. |

In `require_verified` mode, a directory rejects a client that did not advertise
the feature using an ordinary DN_HANDSHAKE with `accepted:false`, then closes
the connection without sending an extension message.

### Authentication Flow

Subject to message-type allocation review, this extension uses:

| Type | Name | Direction |
|------|------|-----------|
| 803 | NICK_AUTH_CHALLENGE | Directory to client |
| 804 | NICK_AUTH_PROOF | Client to directory |
| 805 | NICK_AUTH_RESULT | Directory to client |

After the ordinary HANDSHAKE and DN_HANDSHAKE negotiate `nick_auth`:

1. The directory sends a fresh NICK_AUTH_CHALLENGE.
2. The client verifies the directory identity and signs the challenge. If no
   challenge arrives within 30 seconds of a DN_HANDSHAKE that advertised
   `nick_auth`, the client MUST abort the connection.
3. The directory verifies that the public key derives the claimed nick and
   that the signature is valid.
4. The directory atomically registers the verified owner, sends a successful
   NICK_AUTH_RESULT, and only then makes the owner visible. The client MUST NOT
   send application messages until it receives that result, and MUST abort the
   connection if it does not arrive within 30 seconds of sending the proof.

Authentication is pending from the moment the challenge is sent until the
successful result has been sent. While it is pending the directory MUST NOT
route messages to or from the client, publish its offers, or include it in peer
lists. Authentication failure closes the connection without falling back to
legacy registration.

### Challenge

The challenge payload is:

```json
{"challenge":"<64 lowercase hex characters>","directory-id":"<directory identity>"}
```

The challenge MUST contain 32 bytes from a cryptographically secure random
number generator. It MUST expire no later than 30 seconds after being sent and
MUST be accepted at most once.

`directory-id` identifies the directory endpoint selected by the client. For a
public directory it is the canonical lowercase Tor v3 hostname and port, for
example `<56-character-v3-label>.onion:5222`. For any endpoint that is not a v3
onion, including clearnet, LAN, VPN, and loopback addresses, no canonical
derivation exists and the identity MUST come from explicit local configuration,
for example `test:directory-a`.

The client MUST hold an expected `directory-id` before the challenge arrives,
either derived from a v3 onion endpoint or taken from local configuration. It
MUST compare the received `directory-id` against that expected value and MUST
abort on mismatch. It MUST NOT trust an identity learned only from the
challenge, and MUST NOT weaken the comparison based on the address family of
the endpoint. A client holding no expected identity MUST NOT advertise or
negotiate `nick_auth`. This prevents one directory from relaying another
directory's challenge.

### Proof

The proof payload is:

```json
{"pubkey":"<compressed public key>","signature":"<Base64 DER signature>"}
```

`pubkey` is exactly 66 lowercase hexadecimal characters encoding a compressed
secp256k1 public key.

The `<handshake-sha256>` transcript component is the lowercase SHA256 of the
exact UTF-8 bytes of the client's initial HANDSHAKE `line` value after outer
JSON string decoding. The outer frame, JSON escaping, and terminating CRLF are
not included. The client hashes the value it sent; the directory hashes the
value it received.

The signed ASCII text is:

```text
nick-auth|<challenge>|<directory-id>|<handshake-sha256>|<nick>|<pubkey>
```

No transcript component may contain `|`. `challenge`, `handshake-sha256`, and
`pubkey` are fixed-length lowercase hexadecimal, and `nick` uses the JMP-0001
nick alphabet. `directory-id` MUST match `[a-z0-9][a-z0-9.:_-]*`. A value
failing these rules MUST be rejected before signing or verifying.

This text is signed with the JMP-0001 nick-signature algorithm in a separate
domain. The client signs its ASCII bytes immediately followed by the ASCII
bytes `nick-auth-v1`, in place of the JMP-0001 `onion-network` hostid. A
nick-auth proof MUST NOT verify as a JMP-0001 message signature, and a JMP-0001
message signature MUST NOT verify as a nick-auth proof. The directory MUST:

1. Use the current connection's unexpired, unused challenge and the SHA256 of
   the exact HANDSHAKE `line` received on that connection.
2. Derive the JMP-0001 nick from `pubkey` using the protocol version negotiated
   in the handshake, and require it to equal the handshake nick. The version
   digit carried in the claimed nick MUST NOT be used as the derivation input.
3. Verify the signature using the JMP-0001 Base64, DER, and Bitcoin Signed
   Message rules.

Malformed, expired, replayed, or invalid proofs MUST be rejected.

### Result

A successful result is:

```json
{"code":"ok","verified":true}
```

A failed result uses `verified:false` and a short code such as `malformed`,
`expired`, `invalid`, or `policy`. A failure does not register the claimant or
alter an existing owner, and closes the claimant's connection.

If sending a successful result fails, the directory MUST remove the new
registration only if that connection still owns it. Because displacement has
already completed, the nick is then left unregistered and the displaced legacy
owner is not restored. Directories SHOULD keep the window between displacement
and the result send as small as possible.

### Registry Ownership

Every connection MUST have a unique generation or connection identifier.
Routing entries, offers, heartbeat state, and cleanup work MUST belong to that
exact connection, not only to its nick.

Directories MUST key routing ownership by nick for both serving and non-serving
peers. `location-string` is self-declared connection metadata, not an ownership
identifier: a directory MUST NOT reserve it, require it to be unique, or let a
location collision prevent registration of a different nick. Multiple live
peers MAY advertise the same location.

The directory MUST apply these rules atomically:

- A verified client MUST replace a legacy client using the same nick.
- A legacy client MUST NOT replace any live client using the same nick.
- A verified reconnect may replace an existing verified connection only when
  both connections present the same full public key.
- Distinct public keys that derive the same shortened nick are a collision and
  MUST be rejected.
- Disconnect, timeout, send-failure, and offer cleanup MUST act only when the
  affected connection still owns the state being removed.
- Messages MUST be routed only to the current owning connection, and a sender's
  claimed nick MUST match the nick owned by its connection.

These ownership rules apply even when authentication is disabled or not
negotiated. First-writer handling of a nick prevents a legacy attacker from
replacing a connected victim, but an attacker can still claim a legacy nick
before the victim and cause denial of service. Only authenticated nick
ownership resolves that preclaim.

A directory MUST reject a legacy collision before registration using an
ordinary DN_HANDSHAKE with `accepted:false`, then close the claimant. When a
verified owner replaces a legacy owner, the directory MUST atomically remove
the old connection's routing, offer, peer-list, and heartbeat state before
making the new owner visible.

Directories SHOULD rate-limit pending authentication and duplicate-nick
attempts.

## Rationale

### Message Types

Challenge, proof, and result use separate message types so direction and phase
are determined by the envelope before parsing the JSON payload. This follows
the existing handshake pattern and avoids splitting message identity between a
numeric type and a payload discriminator.

### Authentication Deadline

Thirty seconds is an operational upper bound, not a cryptographic freshness
requirement or a complete denial-of-service defense. It releases server and
client resources when a peer is unresponsive, misconfigured, or disconnected
mid-exchange while allowing for Tor latency. Deployments still need connection
limits and rate limiting because an attacker can open new pending exchanges.

### Signed Transcript

The proof hashes the exact client HANDSHAKE because that is the untrusted input
whose nick, location, network, version, and feature claims the directory is
about to register. Signing its hash keeps the transcript fixed-size and avoids
ambiguity from JSON reserialization. DN_HANDSHAKE is not included because it is
created by the verifier; binding the expected `directory-id` and fresh
challenge supplies the required directory and connection context without
requiring the client and directory to reproduce the response's exact encoding.

The proof payload does not repeat the challenge or handshake hash. The directory
already holds both values for the current connection and reconstructs the
expected transcript from that state; signing a different value simply produces
a signature that does not verify.

The `nick-auth-v1` suffix separates proofs from ordinary JMP-0001 message
signatures. This avoids relying on the current command set never producing a
message body with the same shape as the nick-auth transcript.

### Full Public Key Ownership

The shortened nick commits to only part of a public-key hash, so equality of
nicks cannot distinguish a legitimate reconnect from a deliberate or accidental
collision. Comparing the full public key permits reconnect by the same owner and
rejects a different key. The public key is an ownership identifier, not a
secret; it already appears in signed JMP-0001 messages.

## Backward Compatibility

`prefer_verified` permits a gradual deployment:

| Client | Directory | Behavior |
|--------|-----------|----------|
| Upgraded | Upgraded | Authenticated registration |
| Upgraded | Legacy | Ordinary legacy registration |
| Legacy | Upgraded | Ordinary legacy registration |
| Legacy | Legacy | Unchanged |

The upgraded-to-upgraded authenticated case requires the client to hold an
expected directory identity. For a non-v3-onion endpoint without an explicitly
configured identity, a `prefer_verified` client does not advertise `nick_auth`
and the connection uses ordinary legacy registration. A `require_verified`
client aborts before sending a handshake when no expected identity is available.

Joinmarket-clientserver sends an empty `features` object and ignores unknown
handshake features. An upgraded directory therefore does not send
NICK_AUTH_CHALLENGE to it and registers it through the existing protocol-v5
path.

Legacy clients on an upgraded directory gain protection from live-session
replacement and stale cleanup, but cannot prove ownership and remain vulnerable
to preclaim denial of service. Existing legacy directories remain vulnerable.

`require_verified` intentionally excludes legacy clients and directories and
SHOULD be enabled only after a coordinated migration.

## Deployment

1. Deploy connection ownership, safe cleanup, and first-writer collision rules.
2. Add `nick_auth` to clients and directories in `prefer_verified` mode.
3. Monitor mixed legacy and verified operation before considering
   `require_verified`.

## Security Considerations

The proof is bound to a fresh challenge, the exact handshake, and the selected
directory, so it cannot be reused for another connection or directory. A
malicious directory can still censor or misroute traffic because directories
remain trusted relays.

Nick authentication does not replace JMP-0001 message signatures, encryption,
fidelity-bond checks, or transaction validation. Implementations MUST continue
to perform all existing end-to-end validation.

The proof binds the peer to the exact `location-string` it advertised but does
not prove control of that endpoint. Recipients MUST treat peer-list locations as
untrusted connection hints and continue to authenticate messages by nick and
signature after changing routes.

Challenges and proofs are not secret, and logging them does not enable replay
because each challenge is fresh and single-use. Retaining the complete exchange
alongside handshake logs can still place the public key, signature, endpoint,
and handshake metadata together in durable storage, which can make retrospective
session correlation easier. Production directories SHOULD avoid retaining
complete exchanges unless they are needed for diagnostics.
