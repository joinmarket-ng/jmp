## Abstract

This specification defines two CoinJoin offer types, `tr0reloffer` and `tr0absoffer`, that let makers and takers coordinate CoinJoins over native SegWit v1 (Taproot, P2TR, BIP341) liquidity. A `tr0` offer marks a maker as Taproot-capable: it can sign Taproot key-path inputs, can produce equal-amount outputs in whatever uniform script type the taker selects, and can track and spend the outputs it receives. The taker, not the maker, chooses whether the equal-amount outputs are all P2TR or all P2WPKH. Inputs and change are unconstrained. The document also defines a Taproot PoDLE variant, the wire format for Taproot signatures, and how one wallet can serve both `sw0` and `tr0` liquidity.

## Motivation

JMP-0001 defines only SegWit v0 offers and pins every CoinJoin to P2WPKH end to end. Taproot outputs are cheaper to spend, present a uniform on-chain appearance, and unlock constructions such as silent payments (BIP352) that land funds in P2TR. A taker that receives a P2TR output currently cannot mix it. Rather than overload `sw0` with an out-of-band `address_type` hint (which legacy peers cannot filter on), this specification adds dedicated `tr0` offer types. Takers filter the orderbook for `tr0` and never attempt Taproot with a maker that did not advertise it. Legacy implementations ignore unknown offer types.

The design separates three concerns: the equal-amount output type (an anonymity-set property, uniform, chosen by the taker), input types (funding metadata with no bearing on the anonymity set, left free), and change types (already identifiable by amount, left free). This lets a taker mix a Taproot silent-payment coin and an ordinary P2WPKH coin in one transaction while still producing a clean, uniform set of equal outputs.

## Specification

### Offer Types

Two order types are added to the JMP-0001 orderbook grammar:

| Command | Capability | Fee Type |
|---------|------------|----------|
| `tr0reloffer` | Taproot-capable | Relative (fraction) |
| `tr0absoffer` | Taproot-capable | Absolute (satoshis) |

The field layout matches the `sw0` offers (`!tr0reloffer <oid> <minsize> <maxsize> <txfee> <cjfee>`); `cjfee` is a decimal fraction for `tr0reloffer` and integer satoshis for `tr0absoffer`. A maker MAY announce `tr0` and `sw0` offers together (see Mixed Wallets). A `tr0` offer is a capability advertisement, not a commitment to an output type: by advertising it a maker asserts it can sign Taproot key-path inputs, produce equal outputs in any taker-requested type (at minimum P2TR and P2WPKH), and spend what it receives. A maker that cannot do all of the above MUST NOT advertise `tr0`.

### Equal-Output Script Type

The equal-amount outputs are the anonymity set, so they MUST all share one script type within a transaction. The taker chooses that type (`p2tr` or `p2wpkh`) for the whole CoinJoin and signals it to every counterparty; makers do not get a vote. Each participant derives its single equal output as that exact type, even when it differs from the participant's own wallet type. Per-participant free choice is excluded: it would partition the equal outputs by type, and give makers a stable fingerprint.

The type is signaled in two stages. First, the offer family pre-filters selection: a `tr0` taker only contacts `tr0` makers (and a `sw0` taker only `sw0` makers), so every selected counterparty is already capable of the chosen type. Second, the concrete type is carried on the wire by appending a `cjtype=<p2tr|p2wpkh>` token to the JMP-0001 `!fill` message (`!fill <oid> <amount> <taker_pubkey> <commitment> cjtype=<type>`). A maker records the requested type on `!fill`, derives its equal output as that type during input selection, and returns the resulting address in the `cjaddr` field of its encrypted `!ioauth` reply. The taker MUST verify every `!ioauth` cjaddr matches the requested type and drop any maker whose output diverges before assembling the transaction. The token is optional and additive: a legacy maker that does not parse `cjtype=` falls back to its own wallet type, which a `sw0` taker accepts (P2WPKH) and a `tr0` taker rejects at the `!ioauth` check, so no mismatched output reaches the transaction.

### Inputs and Change

Inputs are unconstrained. Any participant MAY contribute inputs of any spendable script type in the same CoinJoin (Taproot key-path and P2WPKH), regardless of the equal-output type or the maker's offer family; it signs each input per that input's own script type. This lets a participant mix coins of different provenance (a received P2TR output, an ordinary P2WPKH coin) in one transaction instead of separate, linkable ones.

Change is also unconstrained and defaults to the participant's own wallet type. A change output is already distinguishable from the equal outputs by value, so its script type leaks nothing about the anonymity set. A user MAY direct its own change to any external address.

### Taproot PoDLE

JMP-0001 Phase 3 uses PoDLE to bind a taker to a real UTXO, committing to `P = k*G` and binding `P` to the UTXO scriptPubKey. For a Taproot key-path UTXO the committed key is the BIP86 output key `q = p + t (mod n)`, where `t = tagged_hash("TapTweak", x_only(p*G))` (empty Merkle root). The proof is generated as in JMP-0001 with `k = q`. The verifier MUST bind the proof to the UTXO by checking that `x_only(P)` equals the 32-byte program of the UTXO scriptPubKey (`OP_1 <program>`); because Taproot keys are x-only this is parity-independent. The discrete-log portion is unchanged, and a verifier MUST perform both checks. A maker without a Taproot signing engine MUST NOT advertise `tr0`, so a `tr0` taker never sends it a Taproot commitment.

### Signing

Participants sign their own Taproot key-path inputs as BIP341 key-path spends, producing a BIP340 Schnorr signature with `SIGHASH_DEFAULT` (or an explicit sighash byte for non-default types). The BIP341 sighash commits to the amounts and scriptPubKeys of all inputs, so a participant signing any Taproot input MUST know every input's value and scriptPubKey; the taker assembles this from its `!ioauth` validation and the maker from the unsigned `!tx`.

The `!sig` message (JMP-0001 Phase 4) carries one signature per input. The receiver determines the expected encoding from the input's known script type, not by guessing from the payload:

| Input type | `!sig` payload (before base64) | Witness |
|------------|-------------------------------|---------|
| P2WPKH | `<siglen><DER+sighash sig><pubkeylen><33-byte pubkey>` | `[sig, pubkey]` |
| P2TR (key-path) | `<siglen><64- or 65-byte Schnorr sig>` | `[sig]` |

For P2TR key-path the siglen byte is `64` for `SIGHASH_DEFAULT` or `65` with an explicit sighash byte, and there is no pubkey in the witness.

### Fees

A Taproot key-path input is smaller than a P2WPKH input. Implementations MUST estimate vsize using the actual per-input and per-output script types (summed over a mixed CoinJoin), not a single assumed type; sweep-mode amounts are especially sensitive.

| Element | vbytes (approx.) |
|---------|------------------|
| P2TR key-path input | 57.5 |
| P2WPKH input | 68 |
| P2TR output | 43 |
| P2WPKH output | 31 |

### Fidelity Bonds

Fidelity bonds are out of scope for this proposal. Makers continue to advertise and prove the existing JMP-0001 CLTV-timelocked P2WSH bonds; a `tr0` capability says nothing about bond script type.

### Mixed Wallets

A `tr0` maker (and any taker that wants to choose its equal-output type freely) needs a wallet that can receive and spend both P2WPKH (BIP84) and P2TR (BIP86) outputs, tracking both descriptor families and rescanning both after a restart. It MUST be able to produce an equal output of the taker-requested type and to spend whatever it later receives in that type.

### Address Encoding

P2TR addresses use `bech32m` (BIP350), witness version 1, 32-byte program. P2WPKH addresses use `bech32` (BIP173), witness version 0, 20-byte program. Human-readable parts follow BIP173/BIP350: `bc` (mainnet), `tb` (testnet/signet), `bcrt` (regtest).

## Backward Compatibility

Legacy implementations do not recognize `tr0reloffer`/`tr0absoffer` and ignore them when parsing the orderbook, so they neither announce nor select Taproot offers. A `tr0`-capable maker that also wants legacy liquidity announces `sw0` offers in addition; legacy peers see only those and negotiate the unchanged P2WPKH flow. Taproot PoDLE, equal-output-type selection, the Taproot `!sig` encoding, and Taproot inputs occur only between two `tr0`-capable peers.

## Security Considerations

PoDLE binding: verifiers MUST bind the proof key to the committed UTXO scriptPubKey (`x_only(P)` equals the Taproot program). Omitting this accepts commitments unrelated to the claimed UTXO.

Full prevout set: BIP341 signing commits to every input's amount and scriptPubKey. A participant MUST obtain authenticated prevout data for all inputs before signing or risk signing over attacker-chosen values.

Equal-output uniformity: the taker MUST enforce that every equal-amount output is the single chosen type and reject any participant whose equal output diverges. Mixing types would affect the anonymity set negatively.

Fee accuracy: incorrect vsize assumptions in a mixed CoinJoin cause fee over- or under-payment and, in sweep mode, an incorrect amount. Use script-type-aware sizing.
