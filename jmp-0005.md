## Abstract

This specification defines two CoinJoin offer types, `tr0reloffer` and `tr0absoffer`, that let makers and takers coordinate CoinJoins over native SegWit v1 (Taproot, P2TR, BIP341) liquidity. The `tr0` offer family forms a clean, separate "pit" in which every CoinJoin input, every equal-amount output, and every change output is BIP86 key-path P2TR. A `tr0` offer marks a maker as Taproot-capable: it can sign Taproot key-path inputs, produce P2TR equal-amount outputs, and track and spend the P2TR outputs it receives. The tr0 pit is independent of the SegWit v0 (`sw0`) pit; the two never share inputs, equal outputs, or change in a single transaction. The document also defines a Taproot PoDLE variant, the wire format for Taproot (Schnorr) signatures, Taproot fee sizing, and how one maker can serve both pits as separate liquidity.

## Motivation

JMP-0001 defines only SegWit v0 offers and pins every CoinJoin to P2WPKH end to end. Taproot outputs are cheaper to spend, present a uniform on-chain appearance, and unlock constructions such as silent payments (BIP352) whose outputs land in P2TR. A taker that receives a P2TR coin (for example, a silent-payment output) cannot mix it in a P2WPKH-only pit. Rather than overload `sw0` with an out-of-band address-type hint (which legacy peers cannot filter on), this specification adds dedicated `tr0` offer types that form a separate Taproot pit. Takers filter the orderbook for `tr0` and never attempt Taproot with a maker that did not advertise it. Legacy implementations ignore unknown offer types.

Following the precedent of the earlier JoinMarket pit transitions (legacy to wrapped SegWit, wrapped SegWit to native SegWit), the tr0 pit is deliberately rigid: all inputs, all equal-amount outputs, and all change are P2TR. Keeping the whole transaction uniform makes the anonymity set easy to reason about and avoids fingerprinting participants (especially makers) by script type. Isolating Taproot liquidity in its own pit costs some short-term liquidity fragmentation but preserves the hard-won uniformity gains of the existing system. Silent payments remain fully compatible: their outputs are P2TR and therefore native tr0 inputs, and a taker MAY direct its payment to a silent-payment address because the resulting output is itself P2TR and so does not break pit uniformity.

## Specification

### Offer Types

Two order types are added to the JMP-0001 orderbook grammar:

| Command | Capability | Fee Type |
|---------|------------|----------|
| `tr0reloffer` | Taproot-capable | Relative (fraction) |
| `tr0absoffer` | Taproot-capable | Absolute (satoshis) |

The field layout matches the `sw0` offers (`!tr0reloffer <oid> <minsize> <maxsize> <txfee> <cjfee>`); `cjfee` is a decimal fraction for `tr0reloffer` and integer satoshis for `tr0absoffer`. A maker MAY announce `tr0` and `sw0` offers together (see Separate Pits). By advertising a `tr0` offer a maker asserts it can sign Taproot key-path inputs, produce P2TR equal-amount outputs, and spend the P2TR outputs it receives. A maker that cannot do all of the above MUST NOT advertise `tr0`.

### Equal-Output Script Type

In the tr0 pit every equal-amount output is BIP86 key-path P2TR. The equal-amount outputs are the anonymity set, so they MUST all share this one script type within a transaction; there is no per-transaction or per-participant choice of output type. Each participant derives its single equal output as P2TR, including the taker's payment output. A taker MAY send its payment to a silent-payment (BIP352) address, since the derived output is P2TR and therefore indistinguishable from the other equal outputs.

Because the output type is fixed by the offer family, no on-the-wire type negotiation is required: a `tr0` taker contacts only `tr0` makers, every selected counterparty produces a P2TR equal output, and the taker MUST verify that every `!ioauth` `cj_address` is P2TR and drop any maker whose equal output diverges before assembling the transaction.

### Inputs and Change

Inputs are P2TR. Every participant MUST fund its contribution with BIP86 Taproot key-path UTXOs and signs each input as a key-path spend (see Signing). The tr0 pit does not mix script types on the input side: a participant holding only P2WPKH coins cannot join the tr0 pit until those coins are in P2TR, and a maker that wants both kinds of liquidity runs two separate pits (see Separate Pits).

Change is P2TR. A change output is already distinguishable from the equal outputs by value, but keeping it P2TR avoids leaking the participant's wallet type and keeps the transaction uniform. Change MUST be BIP86 key-path P2TR.

### Taproot PoDLE

JMP-0001 Phase 3 uses PoDLE to bind a taker to a real UTXO: the taker commits to `P = k*G`, proves knowledge of `k` against a second NUMS generator `J` (revealing `P2 = k*J` and a discrete-log equality proof), and binds `P` to the UTXO scriptPubKey.

For a BIP86 Taproot key-path UTXO the signing key is the tweaked output key `q = p + t (mod n)`, where `t = tagged_hash("TapTweak", x_only(p*G))` (empty Merkle root). The committed secret is `k = q`.

**Parity normalization.** PoDLE operates on 33-byte compressed points, but a Taproot output key is x-only (BIP340) and so has an implicit even Y. To reuse the JMP-0001 algorithm unchanged, the prover normalizes `k` so that `k*G` has even Y: if the compressed form of `q*G` is `03...`, the prover negates the secret, `k = n - q`, which yields the `02...` representation. All subsequent values, including `P = k*G` and `P2 = k*J`, are computed from this normalized `k`, so the commitment `H(P2)` simply uses the possibly-negated secret. The commitment is a hash, so its structure does not change. With both points in 33-byte compressed form the JMP-0001 discrete-log equality proof and its verification run exactly as before.

**Binding.** The verifier MUST bind the proof to the UTXO by checking that `x_only(P)` equals the 32-byte program of the UTXO scriptPubKey (`OP_1 <program>`). Because the program is x-only this check is parity-independent and matches regardless of the normalization above. The verifier MUST perform both the binding check and the discrete-log check.

A maker without a Taproot signing engine MUST NOT advertise `tr0`, so a `tr0` taker never sends it a Taproot commitment.

### Signing

Participants sign their Taproot key-path inputs as BIP341 key-path spends, producing a BIP340 Schnorr signature with `SIGHASH_DEFAULT` (or an explicit sighash byte for non-default types). The BIP341 sighash commits to the amounts and scriptPubKeys of all inputs, so a participant MUST know every input's value and scriptPubKey before signing; the taker assembles this from its `!ioauth` validation and the maker from the unsigned `!tx`.

The `!sig` message (JMP-0001 Phase 4) carries one signature per input. Within the tr0 pit every input is P2TR key-path:

| Input type | `!sig` payload (before base64) | Witness |
|------------|-------------------------------|---------|
| P2TR (key-path) | `<siglen><64- or 65-byte Schnorr sig>` | `[sig]` |

The siglen byte is `64` for `SIGHASH_DEFAULT` or `65` with an explicit sighash byte, and there is no pubkey in the witness. (SegWit v0 inputs use the JMP-0001 P2WPKH encoding and belong to the `sw0` pit, never the tr0 pit.)

### Fees

Every tr0 input is a Taproot key-path input and every output is P2TR, so implementations size each input at the Taproot key-path cost rather than the larger P2WPKH cost; sweep-mode amounts are especially sensitive to this difference.

| Element | vbytes (approx.) |
|---------|------------------|
| P2TR key-path input | 57.5 |
| P2TR output | 43 |

### Fidelity Bonds

Fidelity bonds are out of scope for this proposal. Makers continue to advertise and prove the existing JMP-0001 CLTV-timelocked P2WSH bonds; a `tr0` capability says nothing about bond script type.

### Separate Pits

The tr0 and sw0 offer families are independent pits. A participant operates within a single pit per transaction, and a transaction never mixes inputs, equal outputs, or change across pits. A pure `tr0` participant needs only a BIP86 (P2TR) wallet that can track and spend Taproot key-path outputs.

A maker MAY serve both pits at once by announcing `sw0` and `tr0` offers together, but it does so as two independent liquidity pools: a `sw0` fill is satisfied entirely from P2WPKH coins and produces P2WPKH outputs, and a `tr0` fill is satisfied entirely from P2TR coins and produces P2TR outputs. Such a maker tracks both the BIP84 and BIP86 descriptor families and rescans both after a restart, but it never combines them in one CoinJoin.

### Address Encoding

P2TR addresses use `bech32m` (BIP350), witness version 1, 32-byte program. Human-readable parts follow BIP350: `bc` (mainnet), `tb` (testnet/signet), `bcrt` (regtest).

## Backward Compatibility

Legacy implementations do not recognize `tr0reloffer`/`tr0absoffer` and ignore them when parsing the orderbook, so they neither announce nor select Taproot offers. A `tr0`-capable maker that also wants legacy liquidity announces `sw0` offers in addition; legacy peers see only those and negotiate the unchanged P2WPKH flow in the sw0 pit. Taproot PoDLE, the Taproot `!sig` encoding, and Taproot inputs and outputs occur only between two `tr0`-capable peers and never affect the sw0 pit.

## Rationale

The central design choice is whether the Taproot pit should be rigid (every input, equal output, and change uniformly P2TR) or flexible (mixing P2WPKH and P2TR inputs, outputs, or change within one transaction). This proposal adopts the rigid approach for the same reason the earlier legacy-to-segwit transitions did: temporarily splitting liquidity is annoying, but participants gain a lot from being reasonably confident everyone is using the same coin type, which maximizes the anonymity set and keeps the system easy to reason about. A maker with a Taproot wallet simply works in the Taproot pit; a cleanly separated pit is easier to analyze than a mixed one.

Flexibility was considered. Sending the taker's payment to an arbitrary address type has long been allowed in JoinMarket and is not, on its own, fatal to anonymity, and for Taproot outputs the on-chain appearance is in fact better than for legacy types. But mixing input types and, especially, mixing change-output types within a single transaction was judged to erode the uniformity that the pit exists to provide. Silent payments do not require this flexibility: their outputs are already P2TR, so they participate natively in a rigid BIP86 pit. The proposal therefore keeps inputs, equal outputs, and change uniformly P2TR while still letting takers spend to silent-payment (P2TR) destinations.

## Security Considerations

PoDLE binding: verifiers MUST bind the proof key to the committed UTXO scriptPubKey (`x_only(P)` equals the Taproot program). Omitting this accepts commitments unrelated to the claimed UTXO. Parity normalization affects only the prover's internal representation and does not weaken the binding, which is x-only and parity-independent.

Full prevout set: BIP341 signing commits to every input's amount and scriptPubKey. A participant MUST obtain authenticated prevout data for all inputs before signing or risk signing over attacker-chosen values.

Equal-output uniformity: the taker MUST enforce that every equal-amount output is P2TR and reject any participant whose equal output diverges. Mixing types would negatively affect the anonymity set.

Pit isolation: implementations MUST NOT combine tr0 and sw0 liquidity in one transaction. Mixing input or change script types across pits reintroduces the fingerprinting and anonymity-set fragmentation the separate pits are designed to avoid.

Fee accuracy: incorrect vsize assumptions cause fee over- or under-payment and, in sweep mode, an incorrect amount. Size every input and output at the Taproot key-path cost.
