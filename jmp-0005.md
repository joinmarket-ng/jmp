## Abstract

This specification defines the `zkp_credentials_v2` feature flag, which
introduces a KVAC-based anonymous credential scheme to the JoinMarket
CoinJoin protocol. With this feature active, the taker (acting as the
CoinJoin coordinator) does not learn which CoinJoin output and change output
belong to which maker. The mapping between a maker's inputs and its outputs
is hidden from the coordinator using keyed-verification anonymous credentials
(KVAC) as defined by the cashu-kvac construction, Pedersen amount
commitments, BulletProof-style range proofs, and an unlinkable
output-registration broadcast channel.

`v2` replaces the earlier (unshipped) `zkp_credentials_v1` draft, which
described a WabiSabi-style wire format backed by the NWabiSabi-Rust
PyO3 bindings. The credential math is unchanged in spirit (Pedersen
commitments + KVAC over secp256k1), but the concrete primitive set,
range-proof construction, and wire encoding all changed; the two
flags are not interoperable and `v1` has no implementation.

## Motivation

In the base protocol (JMP-0001) the maker reveals its CoinJoin address and
change address to the taker during the `!ioauth` phase. The taker therefore
learns the full input -> (cj_output, change_output) mapping for every maker
in the round. This is a significant privacy leak: a malicious or compromised
taker can de-anonymize every CoinJoin it coordinates, even though the
on-chain transaction itself has the same outward shape as a private one.

WabiSabi [1] showed that a coordinator can run a CoinJoin round without
learning the input/output mapping, by issuing anonymous credentials over
input registrations and verifying them at output registration time through
a separate, unlinkable channel. This specification adapts that construction
to JoinMarket's existing message channels, fidelity-bond identity model, and
two-party (taker / maker) flow.

The feature is opt-in and feature-gated; existing makers and takers that do
not advertise `zkp_credentials_v2` continue to interoperate via JMP-0001
unchanged.

## Specification

### Feature Advertisement

Peers advertise `zkp_credentials_v2` support in the handshake `features`
dict and in their `Offer.features`:

```json
{"features": {"zkp_credentials_v2": true}}
```

A maker SHOULD advertise `zkp_credentials_v2` if it supports the credential
issuance and registration flow described below. A taker that requires
input/output unlinkability MUST select only makers that advertise this
feature; mixing ZKP-capable and legacy makers in one round defeats the
privacy goal because legacy makers' mappings are still known to the taker.

### Negotiation

`zkp_credentials_v2` is negotiated per-CoinJoin via the `features=` JSON
suffix on `!fill` and `!pubkey`, in addition to the handshake advertisement.
The effective state is active iff:

1. Both peers advertised the feature in the handshake; and
2. The taker's `!fill` carries `features={"zkp_credentials_v2": true}`; and
3. The maker's `!pubkey` response also carries
   `features={"zkp_credentials_v2": true}`.

If any of these conditions fail, the peers MUST fall back to the legacy
JMP-0001 flow.

### Cryptographic Primitives

All primitives operate over the secp256k1 curve. Points are serialized in
33-byte SEC1 compressed form. Scalars are 32-byte big-endian, reduced
modulo `n` (the curve order).

This specification adopts the cashu-kvac credential construction (a
slightly rewired variant of the Chase-Meiklejohn-Zaverucha algebraic
MAC scheme, with BulletProof-style range proofs grafted on). The
reference implementation lives in the `cashu_kvac` Python package and
re-exports a thin set of Issuer / Client classes that JoinMarket NG
wraps in `jmcore.credentials`.

#### Generators

cashu-kvac fixes a public set of independent generators over secp256k1
derived deterministically via the hash-to-curve construction from
RFC 9380 (try-and-increment over SHA-256 with a domain separation
prefix). The generator set is fully specified by the cashu-kvac
crate and reproduced bit-for-bit by every conforming implementation.
JoinMarket NG does NOT introduce its own generators on top.

#### Pedersen Commitment

`commit(v, r) = v * Gv + r * Gh` for a 64-bit unsigned amount `v`
(satoshis) and a uniformly random 32-byte mask `r`, where `Gv` and
`Gh` are two of the cashu-kvac generators.

Pedersen commitments are additively homomorphic. This property is used
to verify the balance equation across blinded inputs and outputs without
learning any individual amount.

#### Range Proof

A BulletProof-style range proof over `commit(v, r)` proving
`0 <= v < 2^W`, where `W = 64` (the protocol-wide range-proof width).
`2^64` exceeds the BTC supply cap (`~2^50.9`) so any honest amount fits
and any negative or absurdly large amount is rejected. JoinMarket NG
additionally enforces `v <= MAX_AMOUNT = 21_000_000 * 10^8` at the
verifier so a malicious maker cannot claim more than the BTC supply,
even though the range proof would accept any value below `2^64`.

The proof is carried in the `range_proof` field of every real-amount
credential request. Range-proof bytes are an opaque cashu-kvac blob;
implementations MUST NOT parse it directly and MUST hand it back to
the cashu-kvac verifier unmodified. Real-amount credential requests
are approximately 5 KB; zero-amount requests do not include a range
proof and are approximately 540 bytes.

#### Keyed-Verification Anonymous Credentials (KVAC)

The taker holds an issuer keypair for one CoinJoin run. cashu-kvac
exposes the public half as an `IssuerParameters` (`Cw`, `I`) point
pair plus auxiliary generator metadata; the secret half stays inside
the Rust-side `Issuer` object. A credential certifies a Pedersen
amount commitment `Ma = commit(amount, r)` together with one-time
randomness fixed by the issuer at issuance time, so two valid
credentials over the same amount are unlinkable.

The maker proves possession of a valid credential at registration
time through a zero-knowledge "credential show" -- a non-interactive
Schnorr-style proof that the registrant knows the amount and
randomness underlying the issued credential, plus that the issuer's
MAC verifies. The full transcript hides everything except the amount
revealed at registration (which is bounded by the range proof) and
the now-revealed credential identifier (a one-time scalar that lets
the taker reject double-registration within the round).

#### Blind Issuance

cashu-kvac requests carry per-attribute blinding factors generated by
the client and discarded after the response is unblinded. The taker
therefore sees only the blinded commitments, which are statistically
independent of the unblinded values under the discrete-log assumption.

#### Balance Proof of Knowledge

For a single CoinJoin maker, the balance equation is:

```
sum(input_amounts) = cj_amount + change_amount + maker_fee
```

The maker proves in zero knowledge that the sum of its private input
amounts (committed in the credentials it holds) minus the sum of the
amounts it registers at output time minus the publicly known maker fee
equals zero. This is a Schnorr proof of knowledge of the difference of
randomness factors, since the amount terms cancel in the homomorphic sum.
cashu-kvac packs this into the `balance_proof` field of every
real-amount credential request and ties it to the `delta_amount`
field announcing the public fee component.

### Wire Protocol

All new commands are encrypted using the existing NaCl `CryptoSession`
established by `!fill` / `!pubkey`. They are PRIVMSG (685) unless noted.
Every credential payload travelling on the wire (`ZeroAmountRequest`,
`RealAmountRequest`, `CredentialsResponse`, `IssuerParameters`) is
encoded as UTF-8 JSON produced by Pydantic's `model_dump_json` over
the cashu-kvac field layout. Implementations MUST NOT introduce a
binary side-channel encoding; the JSON form is the canonical wire
form and is what the credential transcripts hash over.

#### Phase ZK-1: Issuer Setup

After `!fill` / `!pubkey`, before `!auth`, the taker broadcasts the issuer
parameters to each maker:

```
!zkpparams <epoch_id_hex> <issuer_params_b64>
```

| Field | Type | Description |
|-------|------|-------------|
| `epoch_id_hex` | string | 32-byte random hex; scopes credentials to this run |
| `issuer_params_b64` | string | base64 of the JSON-encoded cashu-kvac `IssuerParameters` (a `{"raw": "<base64 of the cashu-kvac mint-public-key blob>"}` object); typically ~140 bytes on the wire |

The taker MUST keep the cashu-kvac issuer secret for the duration of the
run and zeroize it afterward. `epoch_id` MUST be uniformly random and MUST
NOT be reused across runs.

#### Phase ZK-2: Authentication and Input Commitment

##### ZK-2a: Bootstrap (zero-credential round)

cashu-kvac enforces that every real-amount credential request presents
exactly `CREDENTIAL_NUMBER = 2` previously-issued credentials whose
summed attribute equals zero. On the first request of a run no such
credentials exist yet, so the maker opens the run with a *bootstrap*
zero-amount round that mints two zero-value credentials it can later
present when committing to its first input.

```
maker  -> !zkpboot     <epoch_id> <ZeroAmountRequest>
taker  -> !zkpbootcred <epoch_id> <CredentialsResponse>
```

| Field | Type | Description |
|-------|------|-------------|
| `epoch_id` | hex(32B) | binds the request to the run's `!zkpparams` |
| `ZeroAmountRequest` | base64 | JSON `{"amount_commitments": [...], "bootstrap_proofs": [...]}` (~540 bytes pre-base64) |
| `CredentialsResponse` | base64 | JSON `{"credentials": [...]}` (~1.5 KB pre-base64) |

`!zkpboot` is sent by the maker as soon as it has accepted
`!zkpparams` and constructed its credential client; it MAY race the
maker's own `!auth` reply on the wire. Both messages are encrypted
with the per-session shared secret already negotiated in JMP-0001.

The taker accepts each `!zkpboot` whose `epoch_id` matches the run's
issuer, mints the matching `CredentialsResponse`, and replies with
`!zkpbootcred`. The maker validates the response against the
single-use validation handle from its outgoing
`ZeroAmountRequest`; on success it stores the resulting two
zero-value credentials on the session for use in `!ioauth`. A maker
that never receives a valid `!zkpbootcred` MUST silently drop out of
the round; the taker's maker-replacement loop will detect the
missing `!ioauth` and replace the maker as usual.

##### ZK-2b: Authentication and Input Registration

The taker sends `!auth` (unchanged from JMP-0001), and the maker
responds with `!ioauth` modified as follows: the `cj_address` and
`change_address` fields are REPLACED with an input amount commitment,
and a `change_count` field is added so the taker can verify output
count downstream.

```
!ioauth <utxo_list> <auth_pubkey> <input_commits> <change_count> <btc_signature>
```

| Field | Type | Description |
|-------|------|-------------|
| `utxo_list` | string | comma-separated `txid:vout` of inputs (unchanged from JMP-0001) |
| `auth_pubkey` | hex(33B) | per-session ECDSA pubkey (unchanged from JMP-0001) |
| `input_commits` | string | comma-separated base64 `CredentialRequest` blobs (one per input; see "Input count" below) |
| `change_count` | integer | `0` if no change output, `1` if change output (used by taker to assert output structure during balance proof) |
| `btc_signature` | base64 | signature over the canonical `!ioauth` content (unchanged from JMP-0001) |

Each `input_commits` blob is the JSON-encoded `RealAmountRequest`
produced by cashu-kvac's `Client.request_real_amount(amounts=[v_i, 0],
credentials_to_present=[c1, c2])`, where `[c1, c2]` are the two
credentials the maker holds at the time of the request. The request
blob carries the following top-level JSON fields:

| Sub-field | Description |
|-----------|-------------|
| `presented` | The two `[v_in, 0]` credential MAC presentations being spent |
| `mac_proofs` | Per-credential Schnorr proofs that each presentation is a valid MAC |
| `output_commitments` | Blinded Pedersen commitments to the requested attribute pair |
| `range_proof` | BulletProof-style range proof over the output commitments (`W = 64`) |
| `balance_proof` | Schnorr proof that the randomness sum balances |
| `delta_amount` | Signed integer recording the public amount delta (negative on input rounds) |

Total size at `W = 64` is approximately 5 KB per real-amount credential
request. The range proof, balance proof, and MAC presentations are
verified atomically by the taker via cashu-kvac's
`Issuer.handle_real_amount`; implementations MUST NOT split them across
multiple wire fields.

###### Input count

A ZKP-flagged offer MUST register exactly one input per `!ioauth`. The
maker's `[c1, c2]` for that single input are the zero credentials
minted in ZK-2a.

The single-input restriction follows directly from the cashu-kvac
sequential issuance contract: every `request_real_amount` consumes
two existing credentials and mints two new ones, so committing to
input `k+1` requires the credentials issued for input `k`. Issuing
those credentials in turn requires the taker's `!zkpcred_in` reply,
which arrives only after the maker's `!ioauth`. Batching multiple
input commits into a single `!ioauth` would therefore force the
maker to either (a) fabricate intermediate credentials it has not
been issued, or (b) interleave round-trips that conflict with
JMP-0001's single-`!ioauth` handshake shape. Both options are
rejected; multi-UTXO consolidation by makers is supported by
selecting at most one UTXO at offer time and merging others outside
the CoinJoin run (e.g., via a sweep transaction in a separate
mixdepth rotation).

Takers MUST reject any ZKP `!ioauth` whose `input_commits` list does
not contain exactly one entry, and the taker's wallet selection MUST
constrain ZKP-flagged offers to single-UTXO inputs.

##### ZK-2c: Per-input close-out

For the `CredentialRequest` in `input_commits` the taker, acting as
the cashu-kvac credential issuer, returns one `CredentialsResponse`
that mints the two new credentials the maker needs to present on
the output registration round in ZK-3:

```
taker  -> !zkpcred_in <epoch_id> <CredentialsResponse_list>
```

| Field | Type | Description |
|-------|------|-------------|
| `epoch_id` | hex(32B) | binds the responses to the run's `!zkpparams` |
| `CredentialsResponse_list` | string | comma-separated base64 responses, aligned to the `!ioauth` input order |

The list shape is preserved (rather than collapsed to a single blob)
so the multi-input case remains a forward-compatible extension point;
present-day implementations MUST send and accept exactly one entry,
matching the single-input restriction stated in ZK-2b.

The maker validates each response with cashu-kvac's
`Client.handle_response`, supplying the single-use validation handle
of the corresponding `RealAmountRequest`. On success it stashes the
resulting `[v_i', 0]` credential pair for use in its output
registration round (ZK-3). The taker MUST refuse any maker that
fails to return a valid `!ioauth` after a successful bootstrap.

This direction (maker = prover/holder, taker = issuer) follows the
KVAC pattern where the coordinator role (here: the taker) issues
credentials to participants (here: the makers).

#### Phase ZK-3: Output Credential Request

Per ZK-2b every ZKP-flagged offer registers exactly one input, which
makes the maker's input-side credential pair `[v_in, 0]` available
to be presented in a single output round. The maker therefore sends
exactly one `!zkpreq` per run, covering both of its outputs (the cj
output and a change output of amount zero when no change is needed):

```
maker -> !zkpreq <epoch_id_hex> <RealAmountRequest_b64>
```

| Field | Type | Description |
|-------|------|-------------|
| `epoch_id` | hex(32B) | binds the request to the run's `!zkpparams` |
| `RealAmountRequest_b64` | string | base64 of the JSON-encoded `RealAmountRequest` covering both output amounts |

The serialized `RealAmountRequest` carries the cashu-kvac fields
already described in ZK-2b: `presented`, `mac_proofs`,
`output_commitments`, `range_proof`, `balance_proof`, and
`delta_amount`. The unified verification path proves (a) each
`output_commitments[i]` opens to a value in `[0, 2^W)`, (b) the
blinded commitments are honest blindings of the underlying amounts,
and (c) the maker's randomness sums up correctly into the balance
equation. Total size at `W = 64` is approximately 5 KB per
`!zkpreq`. Implementations MUST NOT split the request into separate
proof fields on the wire; the cashu-kvac transcript is atomic.

Single-input runs collapse the per-output split that earlier drafts
described: because the maker only ever holds one credential pair, it
cannot construct independent per-output requests without breaking
the balance proof. Forward compatibility with multi-input chaining
is reserved by keeping the wire token order `<epoch_id> <blob>`; a
future revision can promote `<blob>` to a comma-separated list once
multi-input issuance is supported.

The taker verifies the request against the issuer's parameters and the
two presented credentials (which must be the credentials it issued
in ZK-2c) and responds with one `CredentialsResponse`:

```
taker -> !zkpcred <epoch_id_hex> <CredentialsResponse_b64>
```

| Field | Type | Description |
|-------|------|-------------|
| `epoch_id` | hex(32B) | binds the response to the run's `!zkpparams` |
| `CredentialsResponse_b64` | string | base64 of the JSON-encoded `CredentialsResponse` carrying the two blinded credential MACs over the requested output commitments (~1.5 KB pre-base64) |

The maker validates the response with its single-use validation handle
from `!zkpreq` and unblinds it into the two output credentials it will
present in the registration round (ZK-4): one credential bound to the
cj output amount and one bound to the change amount (which may be
zero).

#### Phase ZK-4: Output Registration

For each output, the maker opens a fresh, isolated channel to deliver
the registration to the taker. Implementations MUST select a delivery
mode in this order of preference:

1. **Direct PRIVMSG over a fresh Tor circuit to the taker's onion
   service** (RECOMMENDED). The taker's stable onion address is
   advertised in `!zkpparams` (see below). The maker connects to that
   onion using a freshly isolated SOCKS stream
   (`IsolationCategory.ZKP_REGISTRATION_<output_index>`, distinct per
   output) with a brand-new NaCl ephemeral keypair and a random nick.
   The taker's onion is the only entity that can decrypt the
   registration; this leaks the registration's existence to no one
   else, including the directory.

2. **PUBMSG broadcast via the directory** (FALLBACK). If the taker has
   not advertised a registration onion, or the maker cannot reach it,
   the registration is sent as a PUBMSG (687) routed through the
   directory exactly like other broadcast messages. The maker MUST
   still use a fresh Tor circuit, fresh NaCl ephemeral keypair, and a
   random one-time nick. The directory sees the broadcast but cannot
   decrypt it.

In either mode the wire form of the message is the same:

```
!zkpreg <epoch_id_hex> <registration_blob_b64>
```

The taker advertises its registration mode in `!zkpparams` by adding
the optional fields `reg_onion` (the onion address, including `.onion`
suffix and port) and `reg_pubkey` (a registration-only NaCl pubkey,
distinct from the per-session pubkey, so that a registration cannot be
linked back to a particular maker session by inspection of the
recipient pubkey):

```
!zkpparams <epoch_id_hex> <issuer_pubkey_hex> [reg_onion=<addr>] [reg_pubkey=<hex>]
```

The decrypted registration contains:

| Field | Type | Description |
|-------|------|-------------|
| `address` | string | Bitcoin address (cj or change) |
| `amount` | integer | Amount in satoshis (revealed; bounded by the credential's range proof) |
| `serial` | bytes (32) | The credential's one-time identifier, revealed at registration to prevent double-spend within the run |
| `cred_show` | bytes | cashu-kvac credential-show proof of possession (~250 bytes) |
| `output_type` | enum | `"cj"` or `"change"` |

The taker verifies:

1. `cred_show` is valid against the issuer key.
2. `serial` has not been seen before in this run (uniqueness).
3. For `output_type == "cj"`, `amount == cj_amount`.
4. For `output_type == "change"`, the amount is consistent with the
   per-maker balance from `!ioauth`.

The taker collects all registrations until either:

- The number of `cj` registrations equals the number of selected ZKP-
  capable makers; and
- Each maker's accumulated change registration count is consistent with
  the `change_count` it declared in `!ioauth`.

#### Phase ZK-5: Transaction Construction

The taker constructs the unsigned CoinJoin transaction using the
registered output addresses (no per-maker tagging; the order is shuffled
exactly as in JMP-0001). The transaction proceeds through `!tx` and
`!sig` unchanged from JMP-0001.

### Anti-Sybil and Anti-DoS

- The PoDLE commitment in `!fill` is REQUIRED unchanged. ZKP credentials
  do not replace PoDLE; they hide outputs but do not by themselves
  prevent input spam.
- Each `!zkpreg` is signed (via the `cred_show`) over a transcript that
  binds it to `epoch_id`, preventing replay across runs.
- The taker MUST set a deadline (`epoch_deadline`) and reject
  registrations arriving after it.

### Failure Modes

- If a maker fails to register the expected number of outputs by the
  deadline, the taker aborts the run and excludes that maker from
  retries.
- If two `!zkpreg` messages reveal the same serial, the taker aborts
  (this can only happen by the maker double-registering or by an attacker
  forging a credential, which is hard under the underlying assumptions).
- If a balance check fails, the taker aborts and emits an `!error` to
  every participating maker.

## Rationale

### Why KVAC instead of fully blind signatures?

KVAC (Chase, Meiklejohn, Zaverucha [2]) gives a symmetric-key style
verification (the issuer is also the verifier) that is dramatically
faster and simpler than RSA-based blind signatures, while preserving the
unlinkability we need. The taker is both issuer and verifier in this
flow, so KVAC is a natural fit.

### Why a separate registration channel?

If the maker registered its outputs over the same NaCl session it used
for input commitment, the taker would trivially link them. The
registration MUST therefore arrive via an unlinkable channel:

1. The maker uses a fresh NaCl ephemeral keypair (the message contains
   a one-time pubkey, not the maker's session pubkey).
2. The transport hop is a directory PUBMSG, so the directory cannot link
   the source of the broadcast to the maker's main nick beyond the Tor
   circuit identity. Implementations SHOULD use stream isolation
   (`IsolationCategory.ZKP_REGISTRATION`) so the directory cannot
   correlate by Tor circuit either.

### Why broadcast and not direct DM to the taker?

The preferred delivery channel is *direct PRIVMSG to the taker's
onion* over a freshly isolated Tor circuit, because that is strictly
the lowest-leakage option: only the taker's onion sees that a
registration occurred, and the freshly isolated circuit prevents
correlation with the maker's main session. The PUBMSG broadcast mode
is a fallback for deployments where the taker does not (yet) run a
stable registration onion. In broadcast mode, the registration's
existence is observable to the directory, but its content is encrypted
to a registration-only NaCl pubkey unrelated to the taker's session
identity, and a fresh circuit + random nick prevents linking to the
maker's main session.

### Why range proofs at all?

Without range proofs, a malicious maker could register a negative or
huge amount that, combined with negative amounts at other outputs,
satisfies the balance equation but corresponds to no real money flow.
Although the on-chain transaction itself enforces non-negative outputs,
the *registration* layer needs to reject malformed amounts before the
transaction is built, otherwise a bad maker can DoS the run.

### Why `2^64` and not `2^32` or `2^51`?

cashu-kvac's BulletProof range proof natively supports up to 64-bit
witnesses, and the proof size depends logarithmically on `W` rather
than linearly. Choosing `W = 64` therefore costs essentially the same
on the wire as `W = 51` while removing a JoinMarket-specific quirk
(`W = 51` was an artefact of the earlier bit-commitment range proof).
JoinMarket NG additionally rejects any revealed `amount` above the
hardcoded `MAX_AMOUNT = 21_000_000 * 10^8` so the slack between
`2^64` and the BTC supply cap is not exploitable at the application
layer.

### Why don't we hide the amount at registration?

The `amount` field in `!zkpreg` is revealed because the taker must
build a Bitcoin transaction with that exact integer. Hiding the amount
would require either Confidential Transactions (a soft-fork-level
Bitcoin change) or a different mixing model (e.g. uniform-amount
outputs only). For JoinMarket's mixed-amount model, revealing the
amount at output time is unavoidable; the input/output *mapping* is
what we hide.

### Why `epoch_id` and not run_id?

`epoch_id` is reserved for the credential layer and includes the
issuer's commitment to a specific issuer key; `run_id` (JMP-0001
implicit) refers to a CoinJoin attempt. They are distinct because a
single run could in principle re-run the credential phase if it
restarts mid-flight, but in practice this v1 specifies one epoch per
run.

## Backward Compatibility

- Reference makers (joinmarket-clientserver) do not advertise
  `zkp_credentials_v2` and use the legacy `!ioauth` format. Takers
  selecting a mix of ZKP and legacy makers MUST either (a) require ZKP
  for all selected makers, or (b) fall back to legacy for the entire
  run. Per-maker hybrid mode is forbidden because it leaks the legacy
  makers' mappings to the taker.
- The unshipped `zkp_credentials_v1` draft and the present `v2` flag
  are NOT interoperable. Implementations MUST NOT advertise both
  flags simultaneously and MUST treat a `v1` advertisement as a
  legacy (non-ZKP) maker for selection purposes.
- The new commands (`!zkpparams`, `!zkpboot`, `!zkpbootcred`,
  `!zkpcred_in`, `!zkpreq`, `!zkpcred`, `!zkpreg`) are encrypted
  under the NaCl session and never sent to non-negotiated peers.
- Directories require no changes; they relay the new commands as opaque
  PRIVMSG / PUBMSG payloads.

## Security Considerations

- **Issuer key compromise**: an attacker who learns the taker's issuer
  secret `x` for an active run can forge credentials and inject fake
  registrations. The issuer key MUST be generated fresh per run, held
  only in memory, and zeroized after the run ends.
- **Tor correlation**: if the maker's main session and its `!zkpreg`
  broadcast share a Tor circuit, the directory can correlate them by
  source circuit. Implementations MUST use stream isolation for
  registrations.
- **Timing correlation**: while not a target of this specification (the
  on-chain transaction shape already identifies a JoinMarket round),
  implementations SHOULD batch and randomly delay `!zkpreg` broadcasts
  within the registration window to reduce side-channel leakage.
- **Replay**: `epoch_id` binding in every registration prevents cross-
  run replay. Within a run, the serial uniqueness check prevents
  double-registration of the same credential.
- **Range-proof soundness**: relies on the discrete-log assumption over
  secp256k1 and the random oracle model (Fiat-Shamir over a Merlin
  transcript). The construction is the BulletProof-style range proof
  shipped by the cashu-kvac crate; review status tracks upstream
  cashu-kvac.
- **Wire size**: a real-amount credential request is approximately
  5 KB and a real-amount response is approximately 1.5 KB. A typical
  run (six makers, one input commit and one output request per maker)
  therefore moves on the order of ~80 KB of credential traffic over
  the registration phase, comfortably under typical PRIVMSG fragment
  budgets. Implementations MUST send `!zkpreq` and `!ioauth` over
  PRIVMSG (or onion equivalent) and MAY split a single logical message
  across multiple PRIVMSG frames using JMP-0001 fragmentation.

implementation will be appended once stable.)
