## Abstract

This specification defines `nick_auth`, an optional handshake extension
that lets a client prove ownership of its JoinMarket nick before a directory
registers it. It also defines safe duplicate-nick and connection-cleanup rules
for both authenticated and legacy clients.

## Motivation

JMP-0001 nicks are derived from a public key, and private messages are signed
with that key. The initial directory handshake, however, does not prove that
the connecting client owns the nick it claims.

A directory that accepts the handshake nick on trust can let an attacker
replace another peer's routing entry. The attacker can then redirect or drop
CoinJoin messages, make a maker unreachable, and observe routed metadata. A
stale disconnect can also remove a newer connection if cleanup is performed by
nick alone.

Existing message signatures and transaction validation prevent the attacker
from signing as the victim or directly stealing funds. This extension addresses
routing hijack, targeted denial of service, and stale registry cleanup.

## Specification

### Feature Negotiation

Clients and directories advertise support in their JMP-0001 handshake:

```json
{"features":{"nick_auth":true}}
```

The extension is negotiated only when both sides advertise the JSON boolean
`true`. A directory MUST NOT send authentication messages to a client that did
not advertise the feature.

Implementations SHOULD support these modes:

| Mode | Behavior |
|------|----------|
| `prefer_verified` | Authenticate upgraded peers and accept other peers as legacy. This is the default. |
| `require_verified` | Reject peers that cannot authenticate. |
| `disabled` | Do not negotiate authentication. Nick collision and connection-qualified cleanup rules still apply. |

In `require_verified` mode, a directory rejects a client that did not advertise
the feature using an ordinary DN_HANDSHAKE with `accepted:false`, then closes
the connection without sending an extension message.

### Authentication Flow

Subject to message-type allocation review, this extension uses:

| Type | Name | Direction |
|------|------|-----------|
| 803 | NICK_AUTH | Directory to client challenge, or client to directory proof |
| 805 | NICK_AUTH_RESULT | Directory to client result |

NICK_AUTH is bidirectional because challenge and proof are two phases of one
exchange; the payload's `kind` field distinguishes them. NICK_AUTH_RESULT is a
separate type because it terminates the exchange with an explicit outcome.

After the ordinary HANDSHAKE and DN_HANDSHAKE negotiate `nick_auth`:

1. The directory sends a fresh NICK_AUTH challenge.
2. The client verifies the directory identity and signs the challenge.
3. The directory verifies that the public key derives the claimed nick and
   that the signature is valid.
4. The directory atomically registers the verified owner, then sends a
   successful NICK_AUTH_RESULT. The client MUST NOT send application messages
   until it receives that result.

The directory MUST NOT route messages, publish offers, or include the client in
peer lists while authentication is pending. Authentication failure closes the
connection without falling back to legacy registration.

### Challenge

The challenge payload is:

```json
{"challenge":"<64 lowercase hex characters>","directory-id":"<directory identity>","kind":"challenge"}
```

The challenge MUST contain 32 bytes from a cryptographically secure random
number generator. It MUST expire after 30 seconds and MUST be accepted at most
once. The deadline bounds resources held by peers that leave the server-driven
challenge unanswered; it is not a cryptographic freshness requirement.

`directory-id` identifies the directory endpoint selected by the client. For a
public directory it is the canonical lowercase Tor v3 hostname and port, for
example `<56-character-v3-label>.onion:5222`. Tests MAY use an explicitly
configured identity such as `test:directory-a`.

The client MUST compare `directory-id` with its selected endpoint or configured
test identity. It MUST NOT trust an identity learned only from the challenge.
This prevents one directory from relaying another directory's challenge.

### Proof

The proof payload is:

```json
{"challenge":"<challenge>","handshake-sha256":"<hash>","kind":"proof","pubkey":"<compressed public key>","signature":"<Base64 DER signature>"}
```

`pubkey` is exactly 66 lowercase hexadecimal characters encoding a compressed
secp256k1 public key.

`handshake-sha256` is the lowercase SHA256 of the exact UTF-8 bytes of the
client's initial HANDSHAKE `line` value after outer JSON string decoding. The
outer frame, JSON escaping, and terminating CRLF are not included. The client
hashes the value it sent; the directory hashes the value it received.

The signed ASCII text is:

```text
nick-auth|<challenge>|<directory-id>|<handshake-sha256>|<nick>|<pubkey>
```

This text is the JMP-0001 `message_body`. The client signs its ASCII bytes
immediately followed by the ASCII bytes `onion-network`, using the JMP-0001
nick-signature algorithm. The directory MUST:

1. Match the challenge and handshake hash to the current connection.
2. Derive the JMP-0001 nick from `pubkey` and require it to equal the handshake
   nick.
3. Verify the signature using the JMP-0001 Base64, DER, and Bitcoin Signed
   Message rules.

Malformed, expired, replayed, or invalid proofs MUST be rejected.

### Result

A successful result is:

```json
{"code":"ok","verified":true}
```

A failed result uses `verified:false` and a short code such as `malformed`,
`expired`, `invalid`, or `policy`. A failure leaves the nick unregistered and
closes the connection.

If sending a successful result fails, the directory MUST remove the new
registration only if that connection still owns it.

### Registry Ownership

Every connection MUST have a unique generation or connection identifier.
Routing entries, offers, heartbeat state, and cleanup work MUST belong to that
exact connection, not only to its nick.

Directories MUST key routing ownership by nick for both serving and non-serving
peers. `location-string` is self-declared connection metadata, not an ownership
identifier: a directory MUST NOT reserve it, require it to be unique, or let a
location collision prevent registration of a different nick. Multiple live
peers MAY advertise the same location.

The directory MUST apply these rules atomically:

- A verified client MUST replace a legacy client using the same nick.
- A legacy client MUST NOT replace any live client using the same nick.
- A verified reconnect may replace an existing verified connection only when
  both connections present the same full public key.
- Distinct public keys that derive the same shortened nick are a collision and
  MUST be rejected.
- Disconnect, timeout, send-failure, and offer cleanup MUST act only when the
  affected connection still owns the state being removed.
- Messages MUST be routed only to the current owning connection, and a sender's
  claimed nick MUST match the nick owned by its connection.

These ownership rules apply even when authentication is disabled or not
negotiated. First-writer handling of a nick prevents a legacy attacker from
replacing a connected victim, but an attacker can still claim a legacy nick
before the victim and cause denial of service. Only authenticated nick
ownership resolves that preclaim.

A directory MUST reject a legacy collision before registration using an
ordinary DN_HANDSHAKE with `accepted:false`, then close the claimant. When a
verified owner replaces a legacy owner, the directory MUST atomically remove
the old connection's routing, offer, peer-list, and heartbeat state before
making the new owner visible.

Directories SHOULD rate-limit pending authentication and duplicate-nick
attempts. Challenges, proofs, signatures, and full public keys MUST NOT be
written to logs.

## Backward Compatibility

`prefer_verified` permits a gradual deployment:

| Client | Directory | Behavior |
|--------|-----------|----------|
| Upgraded | Upgraded | Authenticated registration |
| Upgraded | Legacy | Ordinary legacy registration |
| Legacy | Upgraded | Ordinary legacy registration |
| Legacy | Legacy | Unchanged |

Joinmarket-clientserver sends an empty `features` object and ignores unknown
handshake features. An upgraded directory therefore does not send NICK_AUTH to
it and registers it through the existing protocol-v5 path.

Legacy clients on an upgraded directory gain protection from live-session
replacement and stale cleanup, but cannot prove ownership and remain vulnerable
to preclaim denial of service. Existing legacy directories remain vulnerable.

`require_verified` intentionally excludes legacy clients and directories and
SHOULD be enabled only after a coordinated migration.

## Deployment

1. Deploy connection ownership, safe cleanup, and first-writer collision rules.
2. Add `nick_auth` to clients and directories in `prefer_verified` mode.
3. Monitor mixed legacy and verified operation before considering
   `require_verified`.

## Security Considerations

The proof is bound to a fresh challenge, the exact handshake, and the selected
directory, so it cannot be reused for another connection or directory. A
malicious directory can still censor or misroute traffic because directories
remain trusted relays.

Nick authentication does not replace JMP-0001 message signatures, encryption,
fidelity-bond checks, or transaction validation. Implementations MUST continue
to perform all existing end-to-end validation.

The proof binds the peer to the exact `location-string` it advertised but does
not prove control of that endpoint. Recipients MUST treat peer-list locations as
untrusted connection hints and continue to authenticate messages by nick and
signature after changing routes.
