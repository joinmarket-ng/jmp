## Abstract

This specification defines two CoinJoin offer types, `tr0reloffer` and `tr0absoffer`, that let makers and takers coordinate CoinJoins over native SegWit v1 (Taproot, P2TR, BIP341) liquidity. The `tr0` offer family forms a clean, separate "pit" in which every CoinJoin input, every equal-amount output, and every change output is BIP86 key-path P2TR. A `tr0` offer marks a maker as Taproot-capable: it can sign Taproot key-path inputs, produce P2TR equal-amount outputs, and track and spend the P2TR outputs it receives. The tr0 pit is independent of the SegWit v0 (`sw0`) pit; the two never share inputs, equal outputs, or change in a single transaction. The document also defines a Taproot PoDLE variant, the wire format and sighash rules for Taproot (Schnorr) signatures, Taproot fee sizing, and how one maker can serve both pits as separate liquidity.

## Motivation

JMP-0001 defines only SegWit v0 offers and pins every CoinJoin to P2WPKH end to end. Taproot (P2TR) outputs present a uniform on-chain appearance and are the foundation for the JoinMarket constructions most likely to follow: key and signature aggregation (MuSig2) that makes an n-of-n cooperative spend look like an ordinary single-key spend, PTLC-based Lightning, and cross-protocol swaps. A Taproot pit lets the network accumulate Taproot liquidity ahead of those protocols, even though the immediate on-chain cost of a P2TR key-path spend is close to P2WPKH. Rather than overload `sw0` with an out-of-band address-type hint (which legacy peers cannot filter on), this specification adds dedicated `tr0` offer types that form a separate Taproot pit. Takers filter the orderbook for `tr0` and never attempt Taproot with a maker that did not advertise it. Legacy implementations ignore unknown offer types.

The tr0 pit is deliberately rigid: every input, every equal-amount output, and every change output is P2TR. The Rationale section explains this choice. This proposal does not attempt to integrate silent payments (BIP352); see Rationale for why BIP352 receiving is incompatible with multi-party CoinJoin.

## Specification

### Offer Types

Two order types are added to the JMP-0001 orderbook grammar:

| Command | Capability | Fee Type |
|---------|------------|----------|
| `tr0reloffer` | Taproot-capable | Relative (fraction) |
| `tr0absoffer` | Taproot-capable | Absolute (satoshis) |

The field layout matches the `sw0` offers (`!tr0reloffer <oid> <minsize> <maxsize> <txfee> <cjfee>`); `cjfee` is a decimal fraction for `tr0reloffer` and integer satoshis for `tr0absoffer`. A maker MAY announce `tr0` and `sw0` offers together (see Separate Pits). By advertising a `tr0` offer a maker asserts it can sign Taproot key-path inputs, produce P2TR equal-amount outputs, and spend the P2TR outputs it receives. A maker that cannot do all of the above MUST NOT advertise `tr0`.

### Equal-Output Script Type

In the tr0 pit every equal-amount output is BIP86 key-path P2TR. The equal-amount outputs are the anonymity set, so they all share this one script type within a transaction; there is no per-transaction or per-participant choice of output type. Each participant MUST derive its single equal output as P2TR, including the taker's payment output. A taker MAY send its payment to any P2TR address.

Because the output type is fixed by the offer family, no on-the-wire type negotiation is required: a `tr0` taker contacts only `tr0` makers, so every selected counterparty produces a P2TR equal output. A taker SHOULD verify that every `!ioauth` `cj_address` is P2TR. Enforcement of counterparty uniformity is RECOMMENDED but not mandatory: an implementation MAY accept a counterparty whose output type diverges (analogous to a maker accepting more fee than it requires) rather than dropping it, trading a small uniformity loss for liquidity. What an implementation MUST do is produce its *own* outputs as P2TR.

### Inputs and Change

Inputs are P2TR. Every participant SHOULD fund its contribution with BIP86 Taproot key-path UTXOs and signs each input as a key-path spend (see Signing). The tr0 pit is intended to be uniform on the input side too: a participant holding only P2WPKH coins cannot meaningfully join the tr0 pit until those coins are in P2TR, and a maker that wants both kinds of liquidity runs two separate pits (see Separate Pits). As with the equal outputs, an implementation MAY tolerate a counterparty that contributes a non-P2TR input rather than aborting; the uniformity is a target, not a consensus rule.

Change is P2TR. A change output is already distinguishable from the equal outputs by value, but keeping it P2TR avoids leaking the participant's wallet type and keeps the transaction uniform. A participant MUST derive its own change as BIP86 key-path P2TR.

### Taproot PoDLE

JMP-0001 Phase 3 uses PoDLE to bind a taker to a real UTXO. The taker commits to the UTXO's public key `P = d*G` (where `d` is the key that signs the UTXO), proves knowledge of `d` against a second NUMS generator `J` by revealing `P2 = d*J` and a discrete-log equality proof, and binds `P` to the UTXO scriptPubKey. JMP-0001 writes the committed key as `P`; for a Taproot UTXO this `P` is the on-chain output key (the key in the `OP_1 <program>` scriptPubKey), elsewhere written `Q`. To avoid clashing with the BIP341 internal key (also conventionally `P`), this section uses `P_int` for the internal key and `Q` for the output key.

**Deriving the committed scalar.** For a BIP86 Taproot key-path UTXO the committed scalar `d` is the tweaked output scalar. It MUST be computed with BIP341 internal-key normalization to even Y *before* applying the tweak:

```
P_int = p*G                          # internal key from BIP86 derivation
if P_int has odd Y:  p = n - p       # normalize internal key to even Y
t = tagged_hash("TapTweak", x_only(P_int))   # empty Merkle root
d = (p + t) mod n                    # output scalar; output key Q = d*G
```

Computing `d = p + t` without the internal-key negation yields the wrong scalar for every UTXO whose internal key has odd Y, and the binding check below then fails for those UTXOs. The committed key is then `P = Q = d*G`, and PoDLE runs with `P2 = d*J`.

**Parity normalization for PoDLE.** PoDLE operates on 33-byte compressed points, but a Taproot output key is x-only (BIP340) and so has an implicit even Y. To reuse the JMP-0001 algorithm unchanged, the prover normalizes the committed scalar so that `d*G` has even Y: if the compressed form of `Q` is `03...`, the prover negates the scalar, `d = n - d`, yielding the `02...` representation. (This is a separate step from the internal-key normalization above: that one selects which output key the UTXO has; this one chooses an even-Y representative of that key for the proof.) The prover computes `P`, `P2`, and the proof from this normalized `d`, so the commitment `H(P2)` simply uses the possibly-negated scalar. The commitment is a hash, so its structure does not change, and with both points in 33-byte compressed form the JMP-0001 discrete-log equality proof and its verification run exactly as before.

**Binding.** The verifier reads `P` from the proof and binds it to the UTXO by checking that `x_only(P)` equals the 32-byte program of the UTXO scriptPubKey (`OP_1 <program>`). Because the program is x-only this check is parity-independent and matches regardless of the normalization above. The verifier MUST perform both the binding check and the discrete-log check.

A maker without a Taproot signing engine MUST NOT advertise `tr0`, so a `tr0` taker never sends it a Taproot commitment.

### Signing

Participants sign their Taproot key-path inputs as BIP341 key-path spends. Every tr0 CoinJoin input MUST be signed with `SIGHASH_DEFAULT`, producing a 64-byte BIP340 Schnorr signature with no trailing sighash byte. All other sighash flags (`ALL`, `SINGLE`, `NONE`, and any `ANYONECANPAY` variant) are forbidden: they would let a participant avoid committing to all of the transaction's outputs and so manipulate the transaction after signing. A verifier MUST reject any input signature that is not exactly 64 bytes; in particular it MUST reject a 65-byte signature and MUST reject a trailing `0x00` byte (a `0x00` sighash suffix is consensus-invalid for Taproot).

The witness MUST NOT contain a BIP341 annex; signers MUST NOT add one and verifiers MUST reject any input witness that carries an annex (a leading `0x50` element).

The BIP341 sighash commits to the amounts and scriptPubKeys of all inputs, so a participant MUST know every input's value and scriptPubKey before signing; the taker assembles this from its `!ioauth` validation and the maker from the unsigned `!tx`.

The `!sig` message (JMP-0001 Phase 4) carries one signature per input. Within the tr0 pit every input is P2TR key-path:

| Input type | `!sig` payload (before base64) | Witness |
|------------|-------------------------------|---------|
| P2TR (key-path) | `<siglen=64><64-byte Schnorr sig><pubkeylen=32><32-byte x-only output key>` | `[sig]` |

The siglen byte is always `64`. The 32-byte x-only output key lets the receiver identify which input the signature is for and verify it; it is NOT placed in the witness (a key-path witness is the single 64-byte signature). This mirrors the JMP-0001 P2WPKH `!sig` layout, which also appends the signing pubkey. (SegWit v0 inputs use the JMP-0001 P2WPKH encoding and belong to the `sw0` pit, never the tr0 pit.)

### Fees

Every tr0 input is a Taproot key-path input and every output is P2TR, so implementations size each input at the Taproot key-path cost rather than the larger P2WPKH cost; sweep-mode amounts are especially sensitive to this difference.

| Element | vbytes (approx.) |
|---------|------------------|
| P2TR key-path input | 57.5 |
| P2TR output | 43 |

### Fidelity Bonds

Fidelity bonds are out of scope for this proposal. Makers continue to advertise and prove the existing JMP-0001 CLTV-timelocked P2WSH bonds; a `tr0` capability says nothing about bond script type.

### Separate Pits

The tr0 and sw0 offer families are independent pits. A participant operates within a single pit per transaction, and a transaction never mixes inputs, equal outputs, or change across pits. A pure `tr0` participant needs only a BIP86 (P2TR) wallet that can track and spend Taproot key-path outputs.

A maker MAY serve both pits at once by announcing `sw0` and `tr0` offers together, but it does so as two independent liquidity pools: a `sw0` fill is satisfied entirely from P2WPKH coins and produces P2WPKH outputs, and a `tr0` fill is satisfied entirely from P2TR coins and produces P2TR outputs. Such a maker tracks both the BIP84 and BIP86 descriptor families and rescans both after a restart, but it never combines them in one CoinJoin.

### Address Encoding

P2TR addresses use `bech32m` (BIP350), witness version 1, 32-byte program. Human-readable parts follow BIP350: `bc` (mainnet), `tb` (testnet/signet), `bcrt` (regtest).

## Backward Compatibility

Legacy implementations do not recognize `tr0reloffer`/`tr0absoffer` and ignore them when parsing the orderbook, so they neither announce nor select Taproot offers. A `tr0`-capable maker that also wants legacy liquidity announces `sw0` offers in addition; legacy peers see only those and negotiate the unchanged P2WPKH flow in the sw0 pit. Taproot PoDLE, the Taproot `!sig` encoding, and Taproot inputs and outputs occur only between two `tr0`-capable peers and never affect the sw0 pit.

## Rationale

**Rigid versus flexible pit.** The pit could be rigid (every input, equal output, and change uniformly P2TR) or flexible (mixing P2WPKH and P2TR within one transaction). This proposal is rigid, following the earlier legacy-to-SegWit and SegWit-to-native-SegWit transitions: temporarily splitting liquidity is inconvenient, but keeping every participant on one coin type maximizes the anonymity set and keeps the transaction easy to reason about. Sending the taker's payment to an arbitrary external address has always been allowed in JoinMarket and is not by itself fatal to anonymity, but mixing input and change script types within a transaction erodes the uniformity the pit exists to provide, so the design treats the whole transaction as uniformly P2TR.

**Enforcement is a target, not a consensus rule.** Each participant MUST produce its own outputs (equal output and change) as P2TR, and an implementation MUST NOT itself mix types in a transaction it builds. Enforcing uniformity *on counterparties*, however, is RECOMMENDED rather than mandatory: like a maker accepting more fee than it strictly requires, an implementation may choose to tolerate a slightly non-uniform counterparty in exchange for liquidity. A divergence degrades the anonymity set but does not make the transaction invalid or unsafe; the security-critical rules (PoDLE binding, `SIGHASH_DEFAULT`, full-prevout signing, no annex) are the ones that remain strict MUSTs.

**No silent payments.** An earlier draft motivated the Taproot pit partly through silent payments (BIP352). That does not work: a BIP352 receiver derives the output key from the sum of *all* of a transaction's eligible input public keys, but in a CoinJoin the inputs come from the taker and every maker, and no single party knows the private keys for the others' inputs. A taker therefore cannot compute the output key the receiver will scan for, so a silent-payment output created inside a CoinJoin cannot be detected or spent by its intended recipient. Supporting BIP352 in this setting would require a multi-party blind-Diffie-Hellman protocol that does not exist today. This proposal consequently makes no use of BIP352. (Receiving silent payments out of band and later mixing the resulting ordinary P2TR coins in the tr0 pit is unaffected: such coins are plain key-path P2TR UTXOs.)

## Security Considerations

PoDLE binding: verifiers MUST bind the proof key to the committed UTXO scriptPubKey (`x_only(P)` equals the Taproot program). Omitting this accepts commitments unrelated to the claimed UTXO. The internal-key even-Y normalization is mandatory: deriving the committed scalar as `p + t` without it produces a key that fails the binding check for odd-Y internal keys. The separate PoDLE parity normalization affects only the prover's internal representation and does not weaken the binding, which is x-only and parity-independent.

Sighash and annex: every tr0 input MUST be signed with `SIGHASH_DEFAULT`. Accepting other sighash flags would let a participant leave some outputs uncommitted and rewrite the transaction after signing; verifiers MUST reject any signature that is not exactly 64 bytes and MUST reject any input witness that carries an annex.

Full prevout set: BIP341 signing commits to every input's amount and scriptPubKey. A participant MUST obtain authenticated prevout data for all inputs before signing or risk signing over attacker-chosen values.

Equal-output uniformity: the anonymity set depends on every equal-amount output sharing one type, so each participant MUST produce its own equal output as P2TR. A taker SHOULD verify counterparties' equal outputs and MAY reject a divergent one, but enforcement is not mandatory (an implementation may favor liquidity over strict uniformity); mixing types degrades the anonymity set rather than breaking the protocol.

Pit isolation: an implementation MUST NOT itself contribute sw0 and tr0 coins (or produce both output types) within one transaction it builds. It SHOULD keep tr0 and sw0 liquidity in separate transactions; tolerating a counterparty that diverges is a liquidity-versus-uniformity trade-off, not a safety issue.

Fee accuracy: incorrect vsize assumptions cause fee over- or under-payment and, in sweep mode, an incorrect amount. Size every input and output at the Taproot key-path cost.
