## Abstract

This specification defines the `zkp_credentials_v1` feature flag, which
introduces a WabiSabi-style anonymous credential scheme to the JoinMarket
CoinJoin protocol. With this feature active, the taker (acting as the
CoinJoin coordinator) does not learn which CoinJoin output and change output
belong to which maker. The mapping between a maker's inputs and its outputs
is hidden from the coordinator using keyed-verification anonymous credentials
(KVAC), Pedersen amount commitments, and an unlinkable output-registration
broadcast channel.

## Motivation

In the base protocol (JMP-0001) the maker reveals its CoinJoin address and
change address to the taker during the `!ioauth` phase. The taker therefore
learns the full input -> (cj_output, change_output) mapping for every maker
in the round. This is a significant privacy leak: a malicious or compromised
taker can de-anonymize every CoinJoin it coordinates, even though the
on-chain transaction itself has the same outward shape as a private one.

WabiSabi [1] showed that a coordinator can run a CoinJoin round without
learning the input/output mapping, by issuing anonymous credentials over
input registrations and verifying them at output registration time through
a separate, unlinkable channel. This specification adapts that construction
to JoinMarket's existing message channels, fidelity-bond identity model, and
two-party (taker / maker) flow.

The feature is opt-in and feature-gated; existing makers and takers that do
not advertise `zkp_credentials_v1` continue to interoperate via JMP-0001
unchanged.

## Specification

### Feature Advertisement

Peers advertise `zkp_credentials_v1` support in the handshake `features`
dict and in their `Offer.features`:

```json
{"features": {"zkp_credentials_v1": true}}
```

A maker SHOULD advertise `zkp_credentials_v1` if it supports the credential
issuance and registration flow described below. A taker that requires
input/output unlinkability MUST select only makers that advertise this
feature; mixing ZKP-capable and legacy makers in one round defeats the
privacy goal because legacy makers' mappings are still known to the taker.

### Negotiation

`zkp_credentials_v1` is negotiated per-CoinJoin via the `features=` JSON
suffix on `!fill` and `!pubkey`, in addition to the handshake advertisement.
The effective state is active iff:

1. Both peers advertised the feature in the handshake; and
2. The taker's `!fill` carries `features={"zkp_credentials_v1": true}`; and
3. The maker's `!pubkey` response also carries
   `features={"zkp_credentials_v1": true}`.

If any of these conditions fail, the peers MUST fall back to the legacy
JMP-0001 flow.

### Cryptographic Primitives

All primitives operate over the secp256k1 curve. Points are serialized in
33-byte SEC1 compressed form. Scalars are 32-byte big-endian, reduced
modulo `n` (the curve order).

#### Generators

Two independent generators are used:

- `G`: the standard secp256k1 base point.
- `H`: a NUMS ("nothing up my sleeve") point derived deterministically as
  `H = hash_to_curve("jmng/zkp_credentials_v1/H")` using the same NUMS
  procedure as PoDLE (`jmcore.podle.generate_nums_point`), with the seed
  string above. `H` MUST be reproduced bit-for-bit by every implementation;
  test vectors are provided in Appendix A.

A third generator `Gv` is derived as `Gv = hash_to_curve(
"jmng/zkp_credentials_v1/Gv")`. It is used in the credential issuance MAC.

#### Pedersen Commitment

`commit(v, r) = v * G + r * H` for a 64-bit unsigned amount `v` (satoshis)
and a uniformly random 32-byte mask `r`.

Pedersen commitments are additively homomorphic: `commit(v1+v2, r1+r2) =
commit(v1, r1) + commit(v2, r2)`. This property is used to verify the
balance equation across blinded inputs and outputs without learning any
individual amount.

#### Range Proof

A bit-commitment Σ-protocol over `commit(v, r)` proving `0 <= v < 2^W`,
where `W = 51` (the protocol-wide range-proof width). 2^51 satoshis
comfortably exceeds the BTC supply cap (2^50.9), so any honest amount
fits and any negative or absurdly large amount is rejected.

The proof is a non-interactive Σ-protocol over W per-bit Pedersen
commitments `B_i = commit(b_i, r_i)`, with the Schnorr-style transcript
proving (a) each `b_i ∈ {0, 1}` and (b) `sum_i 2^i * B_i = commit(v, r)`.
The transcript is *embedded* inside the unified WabiSabi credential
request transcript (Section "Credential Issuance Transcript"); it does
not appear as a separate wire field. Concretely, every credential
request that carries a real (non-zero) amount expands by one bit
commitment per bit (33 bytes each) plus one scalar per bit-commitment
constraint, contributing ~`88 * W` bytes to the request size.

Implementations MUST use the canonical WabiSabi range-proof construction
(`range_proof_knowledge` / `range_proof_statement` in the reference
implementation); this matches WalletWasabi's audited implementation and
admits arbitrary `W ≤ 255`. JoinMarket NG fixes `W = 51`. The cost of
a real-amount credential request at `W = 51` is approximately 23.8 KB
(an unavoidable consequence of bit-decomposition range proofs in the
KVAC/CMZ family); zero-amount credential requests do not include a
range proof and are ~280 bytes.

#### Keyed-Verification Anonymous Credentials (KVAC)

The taker holds an issuer keypair `(x, X)` for one CoinJoin run, with
`X = x * G`. A credential certifies a tuple `(Ma, Ms)` where:

- `Ma = commit(amount, ra)` is a Pedersen commitment to the amount that
  the maker will register at an output.
- `Ms = serial * Gv` is a serial-number commitment binding the credential
  to a one-time serial that the maker will reveal at registration time
  (anti-double-spend within the round).

The MAC is:

```
MAC(x, Ma, Ms) = (U, V) where
    U = hash_to_curve("jmng/zkp_credentials_v1/U" || nonce) * G
    V = x * (U + Ma + Ms)
```

`U` is unique per credential and randomly sampled by the issuer.

The maker proves possession of a valid `(U, V, Ma, Ms)` at registration time
through a zero-knowledge "credential show" -- a non-interactive Schnorr
proof that the registrant knows `(serial, ra)` such that `Ma = commit(
amount_revealed, ra)` and `Ms = serial * Gv`, plus that the issuer's MAC
verifies on `(Ma, Ms)`. The full transcript hides everything except the
amount revealed at registration (which is bounded by the range proof) and
the now-revealed serial number.

#### Blind Issuance

To prevent the taker from linking the credential request to the eventual
registration, requests are *blinded*. The maker chooses random blinding
factors `(alpha, beta)`, sends `(Ma + alpha*G, Ms + beta*G)` to the taker,
the taker MACs that blinded pair, and the maker subtracts the blinding
afterward to obtain a MAC on the unblinded `(Ma, Ms)`. The taker therefore
sees only the blinded pair, which is statistically independent of the
unblinded pair under the discrete-log assumption.

#### Balance Proof of Knowledge

For a single CoinJoin maker, the balance equation is:

```
sum(input_amounts) = cj_amount + change_amount + maker_fee
```

The maker proves in zero knowledge that the sum of its private input
amounts (committed in the credentials it holds) minus the sum of the
amounts it registers at output time minus the publicly known maker fee
equals zero. This is a Schnorr proof of knowledge of the difference of
randomness factors, since the amount terms cancel in the homomorphic sum.

### Wire Protocol

All new commands are encrypted using the existing NaCl `CryptoSession`
established by `!fill` / `!pubkey`. They are PRIVMSG (685) unless noted.

#### Phase ZK-1: Issuer Setup

After `!fill` / `!pubkey`, before `!auth`, the taker broadcasts the issuer
parameters to each maker:

```
!zkpparams <epoch_id_hex> <issuer_pubkey_hex>
```

| Field | Type | Description |
|-------|------|-------------|
| `epoch_id_hex` | string | 32-byte random hex; scopes credentials to this run |
| `issuer_pubkey_hex` | string | 33-byte compressed pubkey `X = x * G` |

The taker MUST keep the issuer secret `x` for the duration of the run and
delete it afterward. `epoch_id` MUST be uniformly random and MUST NOT be
reused across runs.

#### Phase ZK-2: Authentication and Input Commitment

##### ZK-2a: Bootstrap (zero-credential round)

NWabiSabi enforces that every credential request presents exactly
`CREDENTIAL_NUMBER = 2` previously-issued credentials whose summed
attribute equals zero. On the first request of a run no such
credentials exist yet, so the maker opens the run with a *bootstrap*
zero-amount round that mints two zero-value credentials it can later
present when committing to its first input.

```
maker  -> !zkpboot     <epoch_id> <ZeroAmountRequest>
taker  -> !zkpbootcred <epoch_id> <CredentialsResponse>
```

| Field | Type | Description |
|-------|------|-------------|
| `epoch_id` | hex(32B) | binds the request to the run's `!zkpparams` |
| `ZeroAmountRequest` | base64 | bincode-serialized NWabiSabi zero-amount request |
| `CredentialsResponse` | base64 | bincode-serialized NWabiSabi response |

`!zkpboot` is sent by the maker as soon as it has accepted
`!zkpparams` and constructed its credential client; it MAY race the
maker's own `!auth` reply on the wire. Both messages are encrypted
with the per-session shared secret already negotiated in JMP-0001.

The taker accepts each `!zkpboot` whose `epoch_id` matches the run's
issuer, mints the matching `CredentialsResponse`, and replies with
`!zkpbootcred`. The maker validates the response against the
single-use validation handle from its outgoing
`ZeroAmountRequest`; on success it stores the resulting two
zero-value credentials on the session for use in `!ioauth`. A maker
that never receives a valid `!zkpbootcred` MUST silently drop out of
the round; the taker's maker-replacement loop will detect the
missing `!ioauth` and replace the maker as usual.

##### ZK-2b: Authentication and Input Registration

The taker sends `!auth` (unchanged from JMP-0001), and the maker
responds with `!ioauth` modified as follows: the `cj_address` and
`change_address` fields are REPLACED with input amount commitments,
and a `change_count` field is added so the taker can verify output
count downstream.

```
!ioauth <utxo_list> <auth_pubkey> <input_commits> <change_count> <btc_signature>
```

| Field | Type | Description |
|-------|------|-------------|
| `utxo_list` | string | comma-separated `txid:vout` of inputs (unchanged from JMP-0001) |
| `auth_pubkey` | hex(33B) | per-session ECDSA pubkey (unchanged from JMP-0001) |
| `input_commits` | string | comma-separated base64 `CredentialRequest` blobs (one per input) |
| `change_count` | integer | `0` if no change output, `1` if change output (used by taker to assert output structure during balance proof) |
| `btc_signature` | base64 | signature over the canonical `!ioauth` content (unchanged from JMP-0001) |

Each `input_commits` blob is the bincode-serialized `CredentialRequest`
issued by NWabiSabi's `request_real_amount(amounts=[v_i, 0],
credentials_to_present=[c1, c2])`, where `[c1, c2]` are the two
credentials the maker holds at the time of the request. For the
first input these are the zero credentials minted in ZK-2a; for any
subsequent input they are the two credentials minted by the
issuer's response to the previous input (see ZK-2c below). The
request blob carries:

| Sub-field | Size | Description |
|-----------|------|-------------|
| `Ma_in` | 33 bytes | Pedersen commitment to the input amount |
| `bit_commitments` | `33 * W` bytes | Per-bit Pedersen commitments of the range proof |
| `proof_transcript` | ~`55 * W` bytes | Σ-protocol response (challenges + scalars) |
| `presented` | `66 * 2` bytes | The two presented credential MACs and serial-number proofs |

Total size at `W = 51` is approximately 24 KB per input commit. The
range proof and MAC presentation are verified by the taker as part of
the unified credential request transcript verification; there is no
separate `range_proof` field on the wire.

##### ZK-2c: Per-input close-out

For each `CredentialRequest` in `input_commits` the taker, acting as
the WabiSabi credential issuer, returns one `CredentialsResponse`
that mints the two new credentials the maker needs to present on its
*next* request (or, after the maker's last input, on the output
registration round in ZK-3):

```
taker  -> !zkpcred_in <epoch_id> <CredentialsResponse_list>
```

| Field | Type | Description |
|-------|------|-------------|
| `epoch_id` | hex(32B) | binds the responses to the run's `!zkpparams` |
| `CredentialsResponse_list` | string | comma-separated base64 responses, aligned to the `!ioauth` input order |

The maker validates each response against the single-use validation
handle of the corresponding `CredentialRequest`. On success it
stashes the resulting `[v_i', 0]` credential pair for use either in
its next input request (multi-input case) or in its output
registration round (ZK-3). The taker MUST refuse any maker that
fails to return a valid `!ioauth` after a successful bootstrap; the
issuer balance is automatically credited by the input-amount delta
and is checked at the end of ZK-3.

This direction (maker = prover/holder, taker = issuer) follows the
WabiSabi pattern where the coordinator role (here: the taker) issues
credentials to participants (here: the makers).

#### Phase ZK-3: Output Credential Request

For each output the maker intends to register (cj output and optionally
change output), the maker constructs a blinded credential request:

```
!zkpreq <output_blob_list>
```

Each blob is base64-encoded and is the bincode-serialized
`RealAmountRequest` for that output. It carries:

| Sub-field | Size | Description |
|-----------|------|-------------|
| `Ma_out_blinded` | 33 bytes | Blinded Pedersen commitment to output amount |
| `Ms_blinded` | 33 bytes | Blinded serial-number commitment |
| `bit_commitments` | `33 * W` bytes | Per-bit commitments for the range proof on `Ma_out` |
| `proof_transcript` | ~`55 * W` bytes | Unified Σ-protocol response covering range, blinding, and the maker's contribution to the balance proof |

The unified transcript proves (a) `Ma_out` opens to a value in
`[0, 2^W)`, (b) `Ma_out_blinded` and `Ms_blinded` are honest blindings
of `Ma_out` and `Ms`, and (c) the maker's randomness sums up correctly
into the balance equation. Total size at `W = 51` is approximately 23.8
KB per output. Implementations MUST NOT split the range proof into a
separate field; the WabiSabi transcript is atomic.

The balance proof is computed across all of the maker's input commitments
and output commitments simultaneously (one proof per maker, not per
output). When multiple `!zkpreq` are sent (cj + change), each carries a
share of the proof such that the combined proof verifies the balance.

The taker verifies each request and responds:

```
!zkpcred <macA_blinded_list>
```

Each blob is the blinded MAC `(U_blinded, V_blinded)` over the requested
output commitments.

#### Phase ZK-4: Output Registration

For each output, the maker opens a fresh, isolated channel to deliver
the registration to the taker. Implementations MUST select a delivery
mode in this order of preference:

1. **Direct PRIVMSG over a fresh Tor circuit to the taker's onion
   service** (RECOMMENDED). The taker's stable onion address is
   advertised in `!zkpparams` (see below). The maker connects to that
   onion using a freshly isolated SOCKS stream
   (`IsolationCategory.ZKP_REGISTRATION_<output_index>`, distinct per
   output) with a brand-new NaCl ephemeral keypair and a random nick.
   The taker's onion is the only entity that can decrypt the
   registration; this leaks the registration's existence to no one
   else, including the directory.

2. **PUBMSG broadcast via the directory** (FALLBACK). If the taker has
   not advertised a registration onion, or the maker cannot reach it,
   the registration is sent as a PUBMSG (687) routed through the
   directory exactly like other broadcast messages. The maker MUST
   still use a fresh Tor circuit, fresh NaCl ephemeral keypair, and a
   random one-time nick. The directory sees the broadcast but cannot
   decrypt it.

In either mode the wire form of the message is the same:

```
!zkpreg <epoch_id_hex> <registration_blob_b64>
```

The taker advertises its registration mode in `!zkpparams` by adding
the optional fields `reg_onion` (the onion address, including `.onion`
suffix and port) and `reg_pubkey` (a registration-only NaCl pubkey,
distinct from the per-session pubkey, so that a registration cannot be
linked back to a particular maker session by inspection of the
recipient pubkey):

```
!zkpparams <epoch_id_hex> <issuer_pubkey_hex> [reg_onion=<addr>] [reg_pubkey=<hex>]
```

The decrypted registration contains:

| Field | Type | Description |
|-------|------|-------------|
| `address` | string | Bitcoin address (cj or change) |
| `amount` | integer | Amount in satoshis (revealed) |
| `serial` | bytes (32) | Revealed serial number |
| `cred_show` | bytes (~250) | Zero-knowledge proof of credential possession |
| `output_type` | enum | `"cj"` or `"change"` |

The taker verifies:

1. `cred_show` is valid against the issuer key.
2. `serial` has not been seen before in this run (uniqueness).
3. For `output_type == "cj"`, `amount == cj_amount`.
4. For `output_type == "change"`, the amount is consistent with the
   per-maker balance from `!ioauth`.

The taker collects all registrations until either:

- The number of `cj` registrations equals the number of selected ZKP-
  capable makers; and
- Each maker's accumulated change registration count is consistent with
  the `change_count` it declared in `!ioauth`.

#### Phase ZK-5: Transaction Construction

The taker constructs the unsigned CoinJoin transaction using the
registered output addresses (no per-maker tagging; the order is shuffled
exactly as in JMP-0001). The transaction proceeds through `!tx` and
`!sig` unchanged from JMP-0001.

### Anti-Sybil and Anti-DoS

- The PoDLE commitment in `!fill` is REQUIRED unchanged. ZKP credentials
  do not replace PoDLE; they hide outputs but do not by themselves
  prevent input spam.
- Each `!zkpreg` is signed (via the `cred_show`) over a transcript that
  binds it to `epoch_id`, preventing replay across runs.
- The taker MUST set a deadline (`epoch_deadline`) and reject
  registrations arriving after it.

### Failure Modes

- If a maker fails to register the expected number of outputs by the
  deadline, the taker aborts the run and excludes that maker from
  retries.
- If two `!zkpreg` messages reveal the same serial, the taker aborts
  (this can only happen by the maker double-registering or by an attacker
  forging a credential, which is hard under the underlying assumptions).
- If a balance check fails, the taker aborts and emits an `!error` to
  every participating maker.

## Rationale

### Why KVAC instead of fully blind signatures?

KVAC (Chase, Meiklejohn, Zaverucha [2]) gives a symmetric-key style
verification (the issuer is also the verifier) that is dramatically
faster and simpler than RSA-based blind signatures, while preserving the
unlinkability we need. The taker is both issuer and verifier in this
flow, so KVAC is a natural fit.

### Why a separate registration channel?

If the maker registered its outputs over the same NaCl session it used
for input commitment, the taker would trivially link them. The
registration MUST therefore arrive via an unlinkable channel:

1. The maker uses a fresh NaCl ephemeral keypair (the message contains
   a one-time pubkey, not the maker's session pubkey).
2. The transport hop is a directory PUBMSG, so the directory cannot link
   the source of the broadcast to the maker's main nick beyond the Tor
   circuit identity. Implementations SHOULD use stream isolation
   (`IsolationCategory.ZKP_REGISTRATION`) so the directory cannot
   correlate by Tor circuit either.

### Why broadcast and not direct DM to the taker?

The preferred delivery channel is *direct PRIVMSG to the taker's
onion* over a freshly isolated Tor circuit, because that is strictly
the lowest-leakage option: only the taker's onion sees that a
registration occurred, and the freshly isolated circuit prevents
correlation with the maker's main session. The PUBMSG broadcast mode
is a fallback for deployments where the taker does not (yet) run a
stable registration onion. In broadcast mode, the registration's
existence is observable to the directory, but its content is encrypted
to a registration-only NaCl pubkey unrelated to the taker's session
identity, and a fresh circuit + random nick prevents linking to the
maker's main session.

### Why range proofs at all?

Without range proofs, a malicious maker could register a negative or
huge amount that, combined with negative amounts at other outputs,
satisfies the balance equation but corresponds to no real money flow.
Although the on-chain transaction itself enforces non-negative outputs,
the *registration* layer needs to reject malformed amounts before the
transaction is built, otherwise a bad maker can DoS the run.

### Why `2^51` and not `2^32`?

`2^51 satoshis ~ 2.25e15 sat` exceeds the BTC supply cap. `2^32` would
cap individual amounts at ~42.9 BTC, which is fine for typical
JoinMarket sizes but unnecessarily restrictive. Bit-commitment range-
proof size scales linearly in the bit length (~`88 * W` bytes per real-
amount request), so 51 vs. 32 bits costs ~7 KB extra per credential
request. The protocol budgets for this; see Security Considerations
for the per-run wire-size impact.

### Why don't we hide the amount at registration?

The `amount` field in `!zkpreg` is revealed because the taker must
build a Bitcoin transaction with that exact integer. Hiding the amount
would require either Confidential Transactions (a soft-fork-level
Bitcoin change) or a different mixing model (e.g. uniform-amount
outputs only). For JoinMarket's mixed-amount model, revealing the
amount at output time is unavoidable; the input/output *mapping* is
what we hide.

### Why `epoch_id` and not run_id?

`epoch_id` is reserved for the credential layer and includes the
issuer's commitment to a specific issuer key; `run_id` (JMP-0001
implicit) refers to a CoinJoin attempt. They are distinct because a
single run could in principle re-run the credential phase if it
restarts mid-flight, but in practice this v1 specifies one epoch per
run.

## Backward Compatibility

- Reference makers (joinmarket-clientserver) do not advertise
  `zkp_credentials_v1` and use the legacy `!ioauth` format. Takers
  selecting a mix of ZKP and legacy makers MUST either (a) require ZKP
  for all selected makers, or (b) fall back to legacy for the entire
  run. Per-maker hybrid mode is forbidden because it leaks the legacy
  makers' mappings to the taker.
- The new commands (`!zkpparams`, `!zkpboot`, `!zkpbootcred`,
  `!zkpcred_in`, `!zkpreq`, `!zkpcred`, `!zkpreg`) are encrypted
  under the NaCl session and never sent to non-negotiated peers.
- Directories require no changes; they relay the new commands as opaque
  PRIVMSG / PUBMSG payloads.

## Security Considerations

- **Issuer key compromise**: an attacker who learns the taker's issuer
  secret `x` for an active run can forge credentials and inject fake
  registrations. The issuer key MUST be generated fresh per run, held
  only in memory, and zeroized after the run ends.
- **Tor correlation**: if the maker's main session and its `!zkpreg`
  broadcast share a Tor circuit, the directory can correlate them by
  source circuit. Implementations MUST use stream isolation for
  registrations.
- **Timing correlation**: while not a target of this specification (the
  on-chain transaction shape already identifies a JoinMarket round),
  implementations SHOULD batch and randomly delay `!zkpreg` broadcasts
  within the registration window to reduce side-channel leakage.
- **Replay**: `epoch_id` binding in every registration prevents cross-
  run replay. Within a run, the serial uniqueness check prevents
  double-registration of the same credential.
- **Range-proof soundness**: relies on the discrete-log assumption over
  secp256k1 and the random oracle model (Fiat-Shamir over a Strobe
  transcript). The construction is the bit-commitment Σ-protocol used
  by WabiSabi / WalletWasabi and has received external review as part
  of the WalletWasabi audits.
- **Wire size**: a real-amount credential request at `W = 51` is
  approximately 23.8 KB. A typical run (six makers, two registrations
  per maker plus a change registration) therefore moves on the order of
  300 KB of credential-request traffic over the registration phase.
  Implementations MUST send `!zkpreq` and `!ioauth` over PRIVMSG (or
  onion equivalent) and MAY split a single logical message across
  multiple PRIVMSG frames using JMP-0001 fragmentation.
