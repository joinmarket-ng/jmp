## Abstract

This specification defines the `neutrino_compat` feature flag, which enables
makers to provide extended UTXO metadata (scriptPubKey and block height)
alongside their CoinJoin inputs. This metadata allows takers using light
client backends (such as Neutrino compact block filters) to verify maker UTXOs
without querying the full blockchain.

## Motivation

The standard JoinMarket protocol transmits UTXOs in `txid:vout` format during
the `!ioauth` phase. Verifying these UTXOs requires looking up the transaction
output on the blockchain to obtain the scriptPubKey and confirmation status.

Full node backends can perform this lookup directly. However, light client
backends based on BIP 157/158 compact block filters (Neutrino) need the
scriptPubKey to construct the filter match set and the block height to
determine the rescan starting point. Without this metadata, a Neutrino taker
cannot verify maker UTXOs and must reject the CoinJoin.

By having makers include this metadata in `!ioauth`, Neutrino takers can
verify UTXOs using only compact block filter downloads, eliminating the need
for a full node or trusted third-party API.

## Specification

### Feature Advertisement

Peers advertise `neutrino_compat` support in the handshake `features` dict:

```json
{"features": {"neutrino_compat": true}}
```

A maker SHOULD advertise `neutrino_compat` if it can provide scriptPubKey and
block height metadata for its own wallet UTXOs. Both full-node and Neutrino-
backed makers can provide this metadata, since it comes from the maker's own
wallet state.

A taker using a Neutrino backend MUST require `neutrino_compat` from its
selected makers. Makers that do not advertise this feature MUST be filtered
out during maker selection.

### Extended UTXO Format

When both the taker and maker support `neutrino_compat`, the UTXO list in the
`!ioauth` message uses the extended format:

| Format | Syntax | Example |
|--------|--------|---------|
| Legacy | `txid:vout` | `a1b2...f3:0` |
| Extended | `txid:vout:scriptpubkey:blockheight` | `a1b2...f3:0:0014abc...def:800000` |

Fields:

| Field | Type | Description |
|-------|------|-------------|
| `txid` | string | 64-character hex transaction ID |
| `vout` | integer | Output index (0-based) |
| `scriptpubkey` | string | Hex-encoded scriptPubKey of the output |
| `blockheight` | integer | Block height where the transaction was confirmed |

The extended format is used in the comma-separated UTXO list within `!ioauth`:

```
!ioauth txid1:vout1:spk1:height1,txid2:vout2:spk2:height2 <auth_pub> <cj_addr> <change_addr> <sig>
```

### Negotiation

Feature negotiation for `neutrino_compat` happens at two levels:

1. **Handshake**: Both peers advertise the feature. This is informational and
   used for peerlist filtering and maker selection.

2. **Per-CoinJoin** (optional): The taker MAY include a features JSON suffix
   in the `!fill` message, and the maker MAY respond with features in
   `!pubkey`. The effective feature set is the intersection.

If both peers support `neutrino_compat`, the maker MUST use the extended UTXO
format in `!ioauth`. If either peer does not support it, the legacy format
MUST be used.

### Validation

Implementations receiving extended UTXOs SHOULD validate:

- `txid` is exactly 64 hex characters
- `vout` is a non-negative integer not exceeding 2^32 - 1
- `scriptpubkey` is a valid hex string of reasonable length (4-200 hex chars)
- `blockheight` is a non-negative integer

Invalid metadata SHOULD cause the CoinJoin to be aborted for that maker.

## Rationale

### Why embed metadata in the protocol?

An alternative would be for Neutrino takers to query a block explorer API for
UTXO details. This approach was rejected because:

1. It introduces a trusted third party, undermining JoinMarket's trust model
2. API calls leak information about which UTXOs the taker is interested in
3. API availability and rate limits could disrupt CoinJoin coordination

### Why not use a separate message?

Embedding metadata in the existing `!ioauth` UTXO format avoids adding new
message types. Legacy implementations parse only the `txid:vout` portion and
ignore extended fields (they never see them because the feature is negotiated).

### Why include block height?

Neutrino clients download compact block filters sequentially. The block height
tells the client where to start scanning for the UTXO, avoiding a full rescan
from genesis.

## Backward Compatibility

- The reference implementation (joinmarket-clientserver) does not advertise
  `neutrino_compat` and always uses the legacy UTXO format. This is fully
  compatible -- Neutrino takers simply exclude these makers during selection.
- [joinmarket-rs](https://github.com/joinmarket-rs/joinmarket-rs) does not implement this feature.
- The extended UTXO format is only used when both peers have negotiated the
  feature, so legacy peers never encounter it.
- A full-node taker works with all makers regardless of `neutrino_compat`
  support, since it can look up UTXO metadata itself.
